# AI Workflow 方案调研

## 核心问题

团队已经可以直接使用 Codex 或完整的 Agent 研发框架，为什么还需要 AIW？

## 结论

AIW 不与这些工具竞争编码能力。它补充的是复杂需求进入 Coding Agent 前后的轻量编排：固定来源、分开事实和疑问、记录人工结论、拆开发单元、控制上下文并汇总开发进度。

## 三条现有路径

### 直接使用 Codex

优点是门槛最低、迭代最快。缺点是复杂需求的来源、人工结论和多次调用之间的交接主要依赖聊天和个人操作。

AIW 继续使用 Codex 作为执行器，不重写代码分析和修改能力。

### Trellis

优点是完整的 Agent 研发工作框架，覆盖任务、Spec、Skill、Hook 和子任务。对于希望一次引入完整执行框架的团队，它更直接。

AIW 的差异是更窄、更轻：围绕真实需求来源和业务仓库，先处理模糊结论，再按独立开发单元调用已有 Codex。它不要求团队采用另一套完整 Agent 工作空间。

## AIW 的 MVP 差异

```text
来源快照
  → 事实与疑问分开
  → 人工决定本期继续或延期
  → 方案和开发单元
  → 每个单元独立上下文与 worktree
  → 汇总开发进度
```

这条链路主要避免三件事：

- 模糊需求被流程包装成看似完整的错误结论。
- 大需求把全部资料和全部验证一次性塞入上下文。
- Agent 运行完成被误解成已经测试、验收或上线。

## 为什么先做轻量 MVP

当前目标是尽快进入真实试用。测试验收平台、完整影响图、哈希链、自动策略和多 Agent 都会显著增加失败点，且尚未证明是用户完成开发任务的必要条件。因此它们全部留到后续能力阶段。
