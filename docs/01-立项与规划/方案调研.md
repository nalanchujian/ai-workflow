# AI Workflow 方案调研

## 调研结论

MVP 采用 `aiw + Superpowers + Codex`：

- Codex 继续承担代码分析、修改和验证；
- Superpowers 继续提供可复用的通用研发方法；
- `aiw` 只承担团队级的来源、任务事实、审批、失效传播和最小可信上下文治理。

Trellis 是完整 Agent Harness 的能力对标对象，而不是 `aiw` 的同级替代方案。治理要求较低、无需版本化事实和审批失效传播时，可将其作为降级选项评估。

本文只回答“为什么选择这条路径”。是否投入试点见[立项申请](立项申请.md)，用户如何使用见[产品设计](../03-方案设计/产品设计.md)，系统集成边界见[架构设计](../03-方案设计/架构设计.md)。

## 评估标准

比较不以功能数量、是否开源或单次生成速度为首要标准，而以复杂研发任务能否满足以下约束为准：

1. **业务仓库优先**：任务事实可随 Git 共享，不迁移到新的云端平台。
2. **方法可治理**：使用的方法可审阅、版本锁定，并能追溯某次运行的实际内容。
3. **变更可控**：阶段产物、审批和依赖关系可表达；上游变化可使下游结论失效。
4. **上下文可信**：来源、注入文件与版本可追溯，不将聊天记录或不可信资料直接混入执行。
5. **MVP 成本可控**：不新增云端服务、账号体系、运行集群或多 Agent 调度。
6. **执行器可替换**：工作流不绑定单一模型或 Agent；Codex 只是第一个 Adapter。

## 三条路径对比

| 路径 | 已解决的核心问题 | 相对 `aiw` 的缺口或成本 | 当前关系 |
|---|---|---|---|
| 直接使用 Codex CLI、`AGENTS.md` 和 Skills | 在真实代码仓库中理解、修改和测试代码 | 缺少团队共享的来源快照、审批事实、任务依赖和失效记录 | 复用为执行层，不重复建设编码能力 |
| Superpowers | 为 Coding Agent 提供通用研发方法和 Skill | 不管理团队级来源 revision、审批事实与失效传播 | 复用为方法论来源，由阶段技能锁定引用 |
| Trellis | 提供任务、Spec、Skill、Hook、子 Agent 与多平台工作流 | 若要达到 `aiw` 的治理契约，需要持续改造任务模型、上下文注入与执行门禁；与 `.aiw/` 叠加会形成双重事实源 | 能力对标对象；低治理要求时可作为降级选项，MVP 不依赖 |

## 推荐组合与职责边界

```text
Superpowers：通用研发方法
        ↓ 由阶段技能按版本、哈希引用
aiw：版本化来源、任务事实、审批、失效、受控上下文与运行清单
        ↓ 通过 Adapter 提供一次受控运行
Codex CLI：分析代码、修改代码、调用工具和运行验证
```

这不是用 `aiw` 替代 Codex 或 Superpowers，而是补齐它们不以团队级事实治理为核心的部分。业务代码的提交、评审、发布和 CI/CD 仍保持在既有工程体系中。

## Trellis 的对标与降级边界

Trellis 可以组织完整的 Coding Agent 工作流，但如果让它承担 `aiw` 的治理职责，至少要持续解决三类改造：

1. 将来源 revision、阶段产物哈希、审批证据与失效规则纳入其任务模型；
2. 将“仅允许已提交、已确认、未失效输入”落实到上下文注入和执行门禁；
3. 避免 Trellis 自身任务文件与 `.aiw/` 同时成为同一任务的事实源。

因此，Trellis 不是可直接替换 `aiw` 的现成方案。若未来需要集成，只能由 `aiw` 保持审批、revision 与失效事实的唯一所有权，并通过单向 Adapter 交给 Trellis 执行；不能让两套工作流共同写入同一任务事实。

## 何时复核当前选择

应重新评估路径，而不是预设长期自研，出现以下任一情况时触发复核：

- 现有工具能以更低总成本满足来源、审批、失效与追溯要求；
- 试点未改善返工、可追溯性或端到端交付结果；
- 需求超出本机单 Agent 边界，需要长时间运行、多 Agent 协作、服务化调度或跨团队状态共享；
- Codex 以外的执行器更符合团队的安全、成本或工程环境要求。
