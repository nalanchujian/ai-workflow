# AI Workflow 方案调研

## 本文要回答的决策问题

当团队已经可以使用 Codex 等 Coding Agent 时，是否还需要投入一个 `aiw`？

**结论：需要。** `aiw` 的目标是形成一种以 Git 为共享事实源的 AI 研发工作方式；MVP 以轻量、Git 原生的研发变更治理能力实现这一目标。它不替代 Coding Agent、通用研发方法或现有项目协作体系，而是解决复杂需求进入 AI 执行后，团队仍缺少的三件事：结论是否可信、变更后哪些工作必须重做、谁能够依据这些结论继续推进。

MVP 推荐采用 `aiw + Superpowers + Codex` 的分层协作模式：Codex 负责代码分析、修改和验证等工程执行；Superpowers 提供通用研发方法论；`aiw` 负责管理来源、任务事实、关键决策、变更失效与可信上下文。是否批准 MVP、投入边界和停止条件见[立项申请](立项申请.md)；本文只说明为什么应选择这条路径。

## 先判断：团队缺的不是另一个“会写代码的 AI”

Coding Agent 已能在真实仓库中分析、生成和修改代码，但复杂研发交付的成本并不只发生在代码生成阶段。需求来自在线文档、讨论和代码现状；它们会变化，且由多人、多个 Agent 在多个阶段使用。若这些输入和中间结论只存在于会话、临时文件或个人记忆中，就会出现三类管理问题：

| 管理问题 | 典型后果 | 现有编码能力为什么无法自然解决 |
|---|---|---|
| **结论不可追溯** | 无法回答某个方案、实现或测试结论基于哪一版需求、由谁确认。 | Coding Agent 的目标是完成一次调用，不负责把跨阶段依据沉淀为团队事实。 |
| **变更不可控** | 需求或方案变化后，旧计划、实现和测试仍可能被继续使用，返工范围靠人工判断。 | 代码修改工具不维护“上游变化—下游失效”的任务依赖。 |
| **上下文不可信** | 新人或新 Agent 只能重新阅读大量资料；不完整、过期或不可信资料可能直接进入执行。 | 检索、聊天和提示词无法替代已确认的最小执行依据。 |

因此，本项目不是为提升单次代码生成比例立项，而是为了降低复杂 AI 研发中的返工、误用旧结论和交接成本。

## 现有路径为什么不足

现有工具各自解决重要问题，但没有一条路径同时把“当前任务的事实、决策和变更影响”变成可共享、可审阅的工程依据。

| 路径 | 已经解决什么 | 对管理问题仍缺少什么 | 与 aiw 的关系 |
|---|---|---|---|
| 直接使用 Codex CLI、`AGENTS.md` 和 Skills | 在真实代码仓库中分析、修改和测试代码。 | 缺少团队共享的来源快照、审批记录、任务依赖和失效范围。 | 执行层；aiw 不重复建设编码能力。 |
| Superpowers | 提供需求澄清、计划、测试等通用研发方法。 | 不管理某个业务需求的来源 revision、决策证据和下游失效。 | 方法论来源；aiw 按版本锁定并补充任务约束。 |
| Trellis | 提供完整 Agent 工作流、任务、Spec、Skill、Hook 与子 Agent 能力。 | 若要满足本项目的 Git 事实、审批和失效契约，仍需持续改造其任务模型、上下文与执行门禁；与 `.aiw/` 并存还会形成双重事实源。 | 能力对标对象；低治理要求时可作为降级选项，MVP 不依赖。 |
| TencentDB Agent Memory | 将对话、技能、文档知识和代码图谱沉淀为可共享、可检索的团队记忆。 | 记忆资产不等于本次需求的权威依据；不以阶段 DAG、审批证据和变更后的重做范围为核心模型，且其服务化部署超出本机 CLI MVP 边界。 | 互补的知识层；未来可提供候选上下文，MVP 不依赖。 |

**核心判断：** 这些工具可以让 Agent 更会做事、更了解团队，却不会自动保证“这次任务现在还能依据什么继续做”。以 Trellis 为例，它侧重提供完整的 Agent 执行框架；`aiw` 侧重管理当前任务的可信事实、决策门禁和变更影响。两者的区别不在于谁能完成更多 Agent 功能，而在于谁对任务事实的有效性和下游重做范围负责。

## aiw 补上的关键能力

`aiw` 将一个复杂需求从资料进入到测试验证完成的过程，变成一条可检查的事实链：

```text
需求来源快照
    → 需求澄清与确认
    → 技术方案
    → 实施计划与确认
    → 实现、验证、测试证据
```

每一环都保留在业务仓库的 `.aiw/` 中，并通过 Git 与现有代码审查流程共享。这不是增加一套脱离研发的流程表单，而是将 AI 纳入从需求到验证的完整协作过程，形成以下五项核心价值：

| 能力 | 管理价值 |
|---|---|
| **组织能力标准化** | 将经验证的行业方法论、业务规则和研发流程沉淀为统一技能包，降低个人表达能力差异带来的 AI 应用效果波动。 |
| **研发事实资产化** | 将需求、方案、审批、代码变更和验证结果沉淀为可追溯、可复用的研发事实资产，并为后续分析提供结构化基础。 |
| **AI 交付规范化** | 将需求版本、执行规则、变更边界与审批责任纳入统一治理，自动识别需求变化的影响范围，避免旧结论继续进入交付。 |
| **可信上下文管理** | Agent 只使用当前任务所需、已确认且未失效的信息，减少过期资料和无关上下文对交付质量的影响。 |
| **开放生态适配** | 面向不同业务场景、研发工具和团队规范提供可配置、可扩展的接入能力，使 AIW 能够随组织需求持续演进。 |

这五项价值共同回答：AI 参与复杂研发后，团队如何稳定复用方法、判断结论是否仍然可信、在变化后明确重做范围，并让每次交付留下可复用的事实资产，同时适配组织既有的研发生态。

## 为什么选择“本机 + Git + 单 Agent”的 MVP

第一阶段不应直接建设云端编排平台、多 Agent 调度、账号体系或知识平台。这样做会把项目从“验证治理价值”扩大为“重建研发基础设施”。

MVP 选择本机 CLI、单 Agent、固定主干与按业务单元闭环的交付模型，以及现有 Git 仓库，原因是：

1. **复用现有工程事实源。** 任务资料与代码在同一业务仓库中审阅，不引入新的协作系统和迁移成本。
2. **复用成熟执行与方法。** Codex 和 Superpowers 已分别承担执行与通用方法，aiw 只增加必要的编排约束。
3. **先验证管理收益。** 先观察来源是否可追溯、变更是否正确触发重做、关键结论是否能被后续成员复用，再决定是否服务化或自动化。
4. **保持可退出性。** `.aiw/` 是普通 Git 文件；停止使用不会锁定业务代码、发布流程或团队协作数据。

MVP 会沉淀结构化任务事实和运行证据，为后续分析提供基础；跨任务的返工原因、审批耗时和技能使用效果分析属于团队级复用阶段，不作为 MVP 的交付承诺。

MVP 的固定主干、交付单元确认点与自动化演进方向由[发展规划](发展规划.md)定义；它们是验证治理能力的最小载体，而不是长期流程的上限。

## 推荐的职责划分

```text
团队知识与历史经验      → TencentDB Agent Memory（可选、后续）
通用研发方法            → Superpowers
当前任务的事实与决策    → aiw
代码分析、修改与测试    → Codex CLI
代码评审、发布与 CI/CD  → 现有工程体系
```

边界必须明确：来自记忆检索、聊天或外部文档的内容只能是候选信息；只有被 `aiw` 快照、形成任务产物并按规则确认后，才能成为下游执行依据。`aiw` 不接管代码提交、评审、发布或线上运维。

## 不选择的路线

- **只使用 Coding Agent：** 启动最快，但无法系统处理跨阶段依据、确认和变更影响，复杂需求的治理成本仍由人承担。
- **直接以 Trellis 作为治理平台：** 可以获得更完整的 Agent 框架，但为满足本项目的事实契约需要较大改造，也会提前引入超出 MVP 的平台复杂度。
- **以 Agent Memory 代替任务治理：** 可以提升知识复用，却不能保证某次执行只使用当前有效的结论，无法承担变更后的失效与重做责任。
- **自建全栈 AI 研发平台：** 能力想象空间最大，但投入、集成和组织变革成本最高，不适合作为首个验证阶段。

## 结论与后续阅读

建议批准的不是“一套新的 AI 开发平台”，而是一个小范围、可验证的治理层 MVP：在不改变现有 Git、Codex、代码评审和发布方式的前提下，验证复杂 AI 研发任务是否能获得更清晰的事实链和更可控的变更处理。
