# AI Workflow 立项申请

## 决策请求

批准 AIW MVP 在一个真实开发团队和一个业务仓库中试用，验证它能否降低复杂需求进入 AI 开发后的理解偏差、上下文整理成本和重复返工。

## MVP 投入边界

```text
来源快照
  → 事实登记 + 决策登记
  → 技术方案
  → 开发计划
  → 独立开发单元
  → 开发进度汇总
```

MVP 只做到代码开发完成，不覆盖业务测试、验收、PR、发布和运维。运行方式限定为开发者本机、单 Agent 和既有 Git 协作流程。

## 要解决的问题

1. AI 是否把模糊或缺失信息当成确定结论？
2. 需求较大时，是否能拆成小上下文开发单元，而不是一次塞入全部资料？
3. 团队能否看到本期采用了哪些结论、哪些内容延期，以及各开发单元当前进度？
4. 开发失败时，是否能够保留诊断而不污染业务工作区？

## 核心投入

- 通用来源接入与快照。
- 事实和疑问分离。
- 两级人工决策：本期继续或延期；本期继续再选具体方案。
- 方案和结构化开发计划。
- 开发单元依赖图、独立 worktree 和进度汇总。
- Git 中可共享的任务事实和本机运行记录。

## 不投入

- 云端调度、账号权限、多 Agent、知识平台。
- 业务测试与验收平台。
- 复杂影响图、跨节点业务 ID、产物哈希链和通用交接协议。

## 试点指标

- 能否从真实需求稳定推进到代码开发完成。
- 模糊问题是否在开发前被发现并确认。
- 大需求是否可以按开发单元持续推进而不频繁超出上下文。
- 相比直接使用 Codex，返工和手工整理上下文是否减少。
- 开发者是否愿意继续使用，且流程成本可接受。

## 继续或停止

- 继续：真实任务能够稳定闭环，至少一项效率或可追溯指标改善，使用成本可接受。
- 停止或收缩：主流程仍频繁因平台规则失败，开发者需要持续人工修复 AIW 自身，或直接使用现有工具成本更低。

下一阶段是否增加测试验收、自动策略或团队平台能力，由[发展规划](发展规划.md)的进入条件决定。
