# AI Workflow 立项申请

## 决策请求

建议批准 `aiw` 的 MVP 试点：在一个开发团队、一个真实业务仓库和一类中等复杂度需求中，验证“Git 原生的 AI 研发变更治理”是否能降低返工、提高可追溯性，且不显著拉长端到端交付周期。

| 需要批准的事项 | 建议边界 |
|---|---|
| 试点对象 | 一个开发团队、一类中等复杂度研发需求 |
| 运行方式 | 开发者本机、单 Agent、现有 Git 协作流程 |
| 核心投入 | 任务事实、来源快照、审批、失效传播和最小可信上下文 |
| 不纳入范围 | 云端服务、账号体系、多 Agent 调度、新聊天系统、替代 CI/CD 或代码评审 |
| 决策依据 | 总交付周期、返工、可追溯性和使用成本，而非代码生成量 |

本申请只回答“是否值得投入、以什么边界投入、何时继续或停止”。为什么采用当前技术路径见[方案调研](方案调研.md)，用户如何协作见[产品设计](../03-方案设计/产品设计.md)，系统如何实现见[架构设计](../03-方案设计/架构设计.md)。

MVP 只是整体演进的第一阶段；从团队级复用到组织级治理的方向与进入条件见[发展规划](发展规划.md)。

## 要解决的业务问题

复杂研发需求通常跨越资料理解、方案、计划、实现和验证。仅依赖聊天记录、个人经验与手工交接时，团队无法稳定回答四个问题：

1. 当前结论依据哪些来源，是否仍然有效？
2. 哪些关键结论已由谁确认？
3. 上游变化后，哪些计划、实现或测试必须重做？
4. 某次 AI 执行实际使用了哪些方法、资料与上下文？

现有 Coding Agent 已能提高单次分析和编码速度，但不能天然沉淀这四类团队事实。结果是复杂任务容易出现上下文遗漏、审批不可复核、变更后继续使用旧结论，以及问题发生后无法复原执行条件。

## 拟投入的 MVP

`aiw` 是运行在开发者本机、以 Git 共享任务事实的 AI 研发变更治理 CLI。它不替代 Codex 编码，也不重写通用研发方法；它将来源、阶段产物、审批、依赖、失效和运行清单固化为团队可审阅的事实，再将受控上下文交由 Codex 执行。

MVP 聚焦四项能力：

- 将业务需求资料固化为可审阅的来源快照，并记录版本变化；
- 将复杂任务拆为固定研发阶段，保留阶段产物、依赖关系和变更失效；
- 在需求澄清、实施计划和最终测试设置人工确认；
- 记录一次运行使用的来源、技能、审批与上下文清单，使结果可追溯。

详细的产品边界、角色和任务旅程以[产品设计](../03-方案设计/产品设计.md)为准；MVP 的可验证行为以[MVP需求与验收规范](../02-需求定义/MVP需求与验收规范.md)为准。

## 预期价值与试点指标

试点不以“调用次数”或“生成代码量”作为成功标准，而以复杂任务的整体交付效果为准。

| 维度 | 验证问题 |
|---|---|
| 过程可控性 | 关键结论是否有明确产物、审批和责任人？ |
| 可追溯性 | 是否能复原一次运行使用的来源、技能、审批和上下文？ |
| 交付效率 | 从需求确认到验证完成的总周期、重复整理上下文时间是否改善？ |
| 质量 | 因理解偏差、遗漏上下文或上游变化造成的返工是否减少？ |
| 使用成本 | 开发者是否愿意在复杂任务中持续使用，而非绕开流程？ |

## 风险、控制方式与前提

| 风险 | MVP 控制方式 |
|---|---|
| 技能质量不稳定 | 通过 Git 审阅、版本锁定和显式选择管理；不执行技能附带脚本。 |
| 不可信来源影响执行 | 仅接入显式来源，使用快照、大小限制和提示词隔离；敏感资料先脱敏。 |
| 上下文陈旧或过长 | 只注入当前阶段需要、已确认且未失效的输入。 |
| 被误解为全自动研发 | 保留人工审批；业务代码质量、代码审查和发布仍由原有工程流程负责。 |
| 审批身份不足 | MVP 将审批作为 Git 协作记录；高可信场景由受保护分支、CODEOWNERS 或 PR 审批补强。 |
| 试点范围失控 | 限制为单团队、单 Agent、单类需求；未证明收益前不扩大范围。 |

来源、提示词、日志与凭据的具体限制以[安全规范](../03-方案设计/安全规范.md)为准。

## 阶段门槛与退出条件

| 阶段 | 继续投入的条件 | 停止或收缩的条件 |
|---|---|---|
| MVP 验证 | 能稳定保留来源、产物、审批和运行追溯链路 | 基础事实无法稳定落入业务仓库，或使用成本明显不可接受 |
| 团队试用 | 返工或上下文整理成本下降，且不产生新的交付瓶颈 | 开发者持续绕开流程，或交付周期显著变长 |
| 扩大范围 | 与直接使用 Codex 的同类任务相比，可追溯性和整体交付结果有明确改善 | 现有工具能以更低总成本满足同等治理要求，或试点未产生可验证收益 |

## 需要管理层确认的事项

1. 批准以“本机单 Agent + Git 共享任务事实”为边界开展 MVP，而非建设新的 Agent 平台。
2. 指定试点团队、需求类型和技术负责人，技术负责人负责关键产物的审批。
3. 同意以端到端交付结果、返工与可追溯性作为阶段性验收依据。
4. 同意在试点数据不支持继续投入时停止扩大范围。
