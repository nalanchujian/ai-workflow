# AI Workflow 发展规划

## 核心问题

本文回答：MVP 用起来之后，AIW 何时才应该扩展更多能力。

## 阶段一：开发工作流 MVP

目标是证明以下链路可以在真实业务仓库稳定使用：

```text
来源 → 事实/决策 → 方案 → 开发计划 → 开发单元 → 开发进度
```

进入下一阶段前必须满足：

- 至少一个真实团队持续使用。
- 大部分任务可以在不修改 AIW 源码的情况下完成。
- 开发单元拆分明显降低上下文和返工成本。
- 用户能理解每个命令和状态，不依赖维护者陪跑。

本阶段不增加业务验证、测试、验收、自动审批、多 Agent 或云端服务。

## 阶段二：工程闭环

只有当“代码开发完成后如何验证”成为真实高频问题时，才评估：

- 项目测试能力发现与配置。
- 开发单元级验证和测试。
- 浏览器、契约、集成等不同证据类型。
- 明确区分开发完成、验证完成和可交付。

该阶段必须单独设计，不能把旧的测试/验收复杂模型直接恢复到 MVP。

## 阶段三：团队复用

只有当多个成员和多个项目稳定复用相同工作流时，才评估：

- 技能准入、兼容和发布治理。
- 更多来源和执行器 Adapter。
- 自动决策策略和团队汇总视图。
- 与代码托管、CI 或身份系统集成。

## 阶段四：组织级治理

只有 Git 原生模式无法满足跨团队审计和策略一致性时，才评估中心服务、权限模型和组织级运营能力。

## 决策原则

- 先证明当前阶段价值，再增加复杂度。
- 新能力必须解决真实试点问题，而不是补齐想象中的边界场景。
- Codex 和现有工程平台能解决的能力不在 AIW 重建。
- 业务仓库中的任务事实始终是团队共享依据。
