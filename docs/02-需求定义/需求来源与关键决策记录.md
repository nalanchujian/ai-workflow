# AI Workflow 需求来源与关键决策记录

## 用途与边界

本文记录 MVP 需求从何而来、哪些关键取舍已经确认、哪些假设仍须通过试点验证。它回答“为什么当前 MVP 要这样定义”，是[需求与验收规范](MVP需求与验收规范.md)的决策依据，不重复定义功能、命令参数或技术实现。

本文是项目级需求记录，不替代业务仓库 `.aiw/` 中针对具体研发任务的来源快照、审批与变更事实。

## 使用规则

1. 新增或调整 MVP 范围前，先记录对应的来源、决策、影响范围和验证方式。
2. 已确认决策只能通过新增修订记录改变，不覆盖原决策；被替代的决策保留原编号并标注状态。
3. 尚未验证的判断必须标为“待验证”，不得被当作已确认需求或架构事实。
4. 功能行为以[需求与验收规范](MVP需求与验收规范.md)为准；本记录只维护其来源与取舍理由。

## 已确认的关键决策

| ID | 决策 | 原因 | 影响范围 | 状态 |
|---|---|---|---|---|
| DEC-01 | `aiw` 定位为 Git 原生的 AI 研发变更治理层，而非代码生成工具或通用 Agent 平台。 | 核心问题是复杂任务的事实、审批、失效与追溯，而不是重复建设编码能力。 | 全部文档与 MVP 范围 | 已确认 |
| DEC-02 | MVP 采用 `aiw + Superpowers + Codex`。 | Codex 执行工程操作，Superpowers 提供通用方法，`aiw` 补齐团队级治理。 | 技能、Adapter、实施计划 | 已确认 |
| DEC-03 | Trellis 是能力对标对象；仅在低治理要求场景作为降级选项，不作为 MVP 依赖或同级替代方案。 | 若要达到 `aiw` 的事实、审批和失效治理契约，需要持续改造其任务模型、上下文注入与执行门禁。 | 方案调研、架构边界 | 已确认 |
| DEC-04 | MVP 采用固定七阶段，并在澄清、计划和最终测试后设置人工审批。 | 以最少关卡确保关键结论可审阅，不将业务判断交给 Agent。 | 工作流、任务模型、CLI | 已确认 |
| DEC-05 | 来源快照、阶段产物、审批和去敏运行清单随业务仓库 Git 共享；原始日志、完整提示词和凭据只保留本机。 | 兼顾团队可追溯性与敏感信息边界。 | 上下文包、安全、Adapter | 已确认 |
| DEC-06 | Lark 来源通过已配置 MCP Server 读取；`aiw` 负责快照、revision、审计和失效，不管理 Lark 凭据。 | 复用现有受控接入能力，避免把凭据和原始响应写入仓库。 | Lark连接器、任务模型、安全 | 已确认 |
| DEC-07 | MVP 止于测试验证完成，不覆盖 PR、发布、运行监控或运维。 | 先验证研发变更治理闭环，不扩大为工程平台。 | MVP 范围、发展规划、实施计划 | 已确认 |
| DEC-08 | 无法直接执行的疑问必须在澄清/计划阶段前置为“选项 + 取舍 + AI 推荐”，并只阻塞受影响工作单元。 | 防止问题在测试末端才暴露，也避免一个外部依赖冻结整个需求。 | 决策登记、工作单元、任务状态、验收 | 已确认 |
| DEC-09 | 流程闭环与交付就绪分离；未通过验收只能修复或显式风险接受。 | 防止“测试报告写了阻塞，但任务仍显示完成”造成错误交付信号。 | 测试产物、审批、任务状态 | 已确认 |

## 待验证假设与试点依据

| ID | 假设 | 验证方式 | 通过信号 | 不通过后的动作 |
|---|---|---|---|---|
| HYP-01 | 对复杂任务固化来源、审批和失效会减少返工或上下文整理成本。 | 与直接使用 Codex 的同类任务对照。 | 返工、整理成本或可追溯性有明确改善，且总交付周期不显著恶化。 | 收缩范围或停止扩大 MVP。 |
| HYP-02 | 开发者愿意为复杂任务执行额外的创建、提交和审批操作。 | 试点访谈与任务完成数据。 | 试点成员持续使用，未普遍绕开流程。 | 简化任务粒度或退出该类场景。 |
| HYP-03 | Git 共享事实足以满足 MVP 的团队协作与审批记录需求。 | 检查审批可复核性、冲突和身份可信度。 | 团队能复原事实链，并可借助现有 Git 流程满足责任要求。 | 评估受保护分支、CODEOWNERS、PR 审批或后续组织级能力。 |
| HYP-04 | 已配置 Lark MCP 能稳定提供可固化的需求正文。 | 使用授权 Lark 文档创建、刷新并审阅快照。 | 快照可复查、无凭据泄露，内容变化可触发下游失效。 | 限制来源范围或补充连接器能力。 |

## 当前范围变更规则

下列变化必须更新本文，并同步审查[需求与验收规范](MVP需求与验收规范.md)及受影响的方案设计文档：

- 新增、删除或改变 MVP 的主要能力、非目标或验收场景；
- 改变固定阶段、审批点、事实存储边界或来源类型；
- 改变 Superpowers、Codex、Trellis 或 Lark MCP 的职责边界；
- 将 MVP 的结束边界扩展到 PR、发布、运营或多 Agent 调度。
