# MVP 需求与验收规范

## 核心问题

本文回答：AIW 的 MVP 必须实现什么，达到什么结果才可以进入真实试用。

这里的“验收”是对 AIW 产品本身的验收，不是让 AIW 在用户任务中验收业务代码。当前用户工作流只覆盖到代码开发完成。

## MVP 目标

用户能够从真实需求来源创建任务，澄清事实和业务决策，生成技术方案，将方案拆成多个开发单元，并由 Codex 在隔离工作区逐个完成代码修改。

```text
来源快照
  → 可选 Figma 设计分析
  → 事实登记 + 决策登记
  → 技术方案
  → 开发计划
  → 独立开发单元
  → 开发进度汇总
```

## 必须实现的能力

### R-01 来源接入

- `task init` 接受本地文件或通用文档地址。
- 在线地址由内部路由选择公开网页或已配置连接器。
- 来源内容固化到业务仓库；可显式刷新。

### R-02 需求澄清

- `clarify` 只产出事实登记和决策登记。
- 事实保留来源位置，不创建事实 ID。
- 每个待决事项只表达一个业务问题，并提供一至两个 AI 方案。

### R-02A 可选设计分析

- `task init --design <Figma URL>` 只登记设计来源并增加独立 `design-analysis` 节点，不在初始化时读取设计稿。
- 运行设计节点时由 Codex 使用已登录的 Chrome 打开 Figma 父节点，通过原生 `Copy as PNG` 取得完整图片，并按绿色容器、编号和留白裁成逻辑业务块；不使用浏览器截图作为设计资产，不修改 Figma 文件。
- AIW 不配置或调用 Figma MCP；浏览器未登录、无权限或不可控制时必须明确失败，不得猜测设计内容。
- 设计节点只输出截图文件和最小截图索引，不生成设计总结或规则；后续开发单元只接收自身引用的图片。
- 不提供 `--design` 时保持原有流程。

### R-03 人工决策

- `task review` 先选择“本期继续”或“延期处理”。
- 本期继续必须选择一个具体方案。
- 延期事项从本期方案和计划中排除，并在决策登记中聚合保存。

### R-04 方案与计划

- `solution` 只读取事实登记和本期决策。
- `plan` 只读取技术方案，并生成结构化开发计划。
- 开发计划可声明多个开发单元及其依赖；未知、自依赖和循环依赖必须被拒绝。
- 界面开发单元可声明截图引用；纯逻辑单元不携带无关图片。

### R-05 开发执行

- 每个开发单元使用独立 Git worktree。
- Codex 只收到当前开发单元所需上下文。
- 成功后将业务补丁发布到用户工作区；失败不污染用户工作区。
- 开发结果只记录代码修改、变更文件、未解决问题和风险，不宣称测试或验收通过。

### R-06 状态与留痕

- 每次命令完成后输出下一条精准的 `task review`、`task approve` 或 `task run <node-name>` 命令；开发单元名称使用 `development-unit-<英文语义名>`。
- `task status` 显示主干节点、开发单元和汇总进度。
- 不属于当前仓库或任务范围的叶子开发单元可由用户注明原因后忽略；忽略记录保留，且不伪装成开发完成。
- `.aiw/` 保存任务状态、来源、产物、人工决策、审批和去敏运行证据。
- `~/.aiw/runtime/` 保存本机日志和临时执行区。
- 所有改变任务事实的命令使用任务锁和状态版本，避免并发覆盖。

## MVP 不包含

- 业务代码验证、自动化测试和验收结论。
- AC、事实 ID、决策 ID及跨节点影响图。
- 通用 Handoff 文件或任务产物哈希链。
- 快速/标准双路径、多 Agent、云端调度、身份权限、PR 和发布管理。

## 产品验收场景

1. 新用户安装、初始化并通过 `doctor`。
2. 从本地文件、公开 URL 或已配置的在线文档创建任务。
3. 提供 Figma 地址时独立完成设计分析；未提供时直接进入需求澄清。
4. 用户按照 CLI 输出的精准命令推进任务，无需自行判断或记忆下一个节点 ID。
5. 澄清产物只有事实和决策两类 YAML。
6. 人工选择延期后，延期内容不进入方案和计划。
7. 计划可生成一个或多个开发单元，并按依赖解锁。
8. 开发单元失败时源业务工作区不出现该次业务改动；成功时补丁发布到源工作区。
9. 全部开发单元完成或被明确忽略后，任务显示“开发完成”，并分别统计完成与忽略数量，但不显示“测试通过”或“验收通过”。

自动化测试、类型检查、构建和包检查用于验证上述 AIW 行为。
