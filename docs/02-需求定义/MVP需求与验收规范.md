# MVP 需求与验收规范

## 核心问题

MVP 是否能让开发者以一个需求来源为起点，把模糊信息转化为可确认事实，并以不超过上下文预算的方式完成可信交付？

MVP 的唯一目标链路是：

```text
来源快照
  → 事实/疑问拆分
  → 决策关卡
  → 业务单元图
  → 单元交付（代码 + 验证 + 测试 + 验收）
  → 汇总交付状态
```

终点不是“生成代码”或“流程节点都打勾”，而是：每个当前业务单元都有可追溯的代码变更、工程验证、测试和验收结论；全部单元闭环后，任务给出明确的交付状态与未覆盖风险。

## 范围

MVP 支持：

1. `aiw init` 初始化本机默认工作流和文档连接器映射；
2. 用通用 URL 或本地文件创建需求任务并固化来源快照；大文档的自动章节/领域索引属于当前 MVP 的后续缺口；
3. 将来源中的信息分为已确认事实、推断、待确认疑问和外部依赖；
4. 使用已锁定的团队技能完成澄清、方案和计划，并在澄清阶段逐项记录人工业务结论或外部等待；
5. 在澄清产出事实、验收项和待决结论后，建议快速修改或标准需求；无法可靠判断时默认走标准需求；
6. 从计划自动生成一个或多个业务交付单元，并维护需求、决策、AC 与单元之间的影响关系；
7. 在每个单元一次运行中完成开发、工程验证、测试、验收和交接；
8. 汇总区分运行状态、验收状态和交付状态，而非将 AI 运行结束表述为任务完成；
9. 通过 Git 事实、产物哈希、运行证据和审批记录保证可追溯；
10. 支持来源刷新、外部决策解除、重跑和按风险接受关闭；
11. 通过 `doctor`、`status`、`runtime` 提供环境检查、下一步和运行记录。
12. 同一任务的运行、来源刷新、审批和决策必须串行执行，并拒绝任何基于过期任务状态的覆盖写入。

MVP 不支持云端调度、身份权限、多人并发运行、PR/发布运维自动化，或无证据的在线文档读取。

## 验收标准

### AC-01：来源可信且可切片

- 输入 HTTP(S) 地址或本地文件后，AIW 能按规则选择来源读取器；
- 来源快照、元数据与任务记录的 SHA-256 一致；
- 快照被手动改写或来源更新后，下游不能静默继续。
- 当来源超过单次澄清预算时，AIW 必须先生成章节/领域索引和可追溯片段，而不是把完整原文直接塞入后续上下文。

### AC-02：事实、疑问与决策可确认

- `clarify` 产出摘要、问题、验收清单和决策登记；
- 每项关键输入必须能区分为已确认事实、推断、待确认疑问或外部依赖；推断不能被伪装成已确认事实；
- 每次人工选择只解决一个业务结论，并留存操作者、时间、选项和说明；
- 未处理决策不能进入方案阶段。

### AC-03：计划可执行

- `plan` 产出实施计划和严格校验的 `work-breakdown.yaml`；
- 每个 AC 有唯一覆盖方式；本期或外部等待的 AC 只归属一个交付单元；
- 每个交付单元只能引用项目已声明或自动发现的测试能力；AIW 在计划阶段完成健康检查，测试环境不可用时不得进入开发；
- 澄清阶段为每个 AC 固定证据类型；计划必须固定 `AC → 测试能力 → 测试目标 → 证据类型`，且测试能力必须支持该类型。UI 交互类 AC 必须使用组件交互或浏览器证据，API 类 AC 必须使用契约或集成证据，只有纯逻辑 AC 才允许单元测试；
- 计划审批后为每个业务单元生成 `delivery-<unit-id>` 节点和最小上下文。
- 需求、事实、决策、AC 与交付单元之间存在可计算、带哈希的影响关系；交付单元运行前必须校验该关系仍与当前计划一致。
- 新增会改变方案的外部事实或来源刷新时，系统必须保守地重新澄清/规划；不得假装可以根据未切片的整篇来源安全地局部放行。
- 快速修改只允许在单来源、快照不超过 12,000 字、单一 AC、无决策且全部事实为已确认高可信时选择；它跳过独立 `solution`，但 `plan` 必须生成唯一、无依赖、无决策的交付单元。任一条件不满足时只能采用标准需求。

### AC-04：单元交付闭环

- 每个交付单元在一次运行中完成代码、工程验证、测试和所属 AC 的验收；
- 产出 `delivery.md`、由 Codex 声明的 `acceptance-intent.yaml`、由 AIW 写入的 `test-results.yaml`、`acceptance-results.yaml` 和 Handoff；
- AIW 在 Codex 完成代码后执行计划锁定的验证命令，保存原始 stdout/stderr、退出码和哈希；AIW（而非 Codex）根据验收意图与真实测试记录生成 AC 的 `passed`、`failed` 或 `blocked` 结论；
- 交付阶段不得重新选择 AC 对应的测试；实际测试记录的测试能力、目标、证据类型和 AC 引用必须与批准计划完全一致，否则该 AC 不能通过；
- 不存在全局 `verify`、`test` 节点，也不将所有单元的上下文汇总到最后；
- 跨单元验收通过独立集成交付单元表达。

### AC-05：事实与审批可信

- 下游运行前校验来源、上游产物、成功运行和审批事实的哈希；
- 未提交的任务事实不能作为下游输入；
- 重跑校验成功后覆盖当前节点结果，运行证据仍保留在独立运行目录；
- 交付单元普通审批只允许其 AC 全部通过；风险接受必须带责任人、原因和到期时间。
- 同一任务的节点运行、来源刷新、审批和决策同时发起时，只能有一个命令取得任务锁；其他命令不得部分写入任务事实。
- 每次 `task.yaml` 更新必须递增 `stateVersion`；读取后的版本已变化时，过期写入必须失败，来源刷新结果不能被较早启动的节点完成状态覆盖。

### AC-06：上下文受控且可继续拆分

- 默认上下文使用 Handoff 和当前单元上下文，不重复注入完整上游 Markdown；
- 上下文超预算时给出占用诊断，不能静默截断已批准事实；
- 大需求通过领域切片、更多交付单元和集成交付单元控制规模，而不是全局验证汇总；
- 某个单元仍超预算时，AIW 必须生成可执行的继续拆分建议，而不是只输出“上下文超限”。

### AC-07：流程成本与状态表达可用

- `doctor` 显示 Git、Codex、默认工作流、方法来源和文档连接器的可用状态；
- `status` 显示清晰的业务单元名称和唯一下一步；
- 用户能理解当前任务被建议采用快速修改或标准需求的原因；仅在快速条件全部满足时才可选快速修改，否则固定采用标准需求；
- 状态页同时区分“节点运行完成”“验收通过”和“整体可交付/风险已接受/尚未评估”；
- 用户只需要日常使用 `init`、`task init`、`task run`、`task review`、`task approve`；决策解除、风险关闭和技能升级为高级入口。
