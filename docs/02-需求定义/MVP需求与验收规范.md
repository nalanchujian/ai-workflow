# MVP 需求与验收规范

## 核心问题

MVP 是否能让开发者以一个需求来源为起点，完成一组可信、可控、可追责的业务交付单元？

MVP 的终点不是“生成代码”，而是：每个当前业务单元都拥有可追溯的代码变更、工程验证、测试和验收结论；全部单元闭环后，任务给出明确交付状态。

## 范围

MVP 支持：

1. `aiw init` 初始化本机默认工作流和文档连接器映射；
2. 用通用 URL 或本地文件创建需求任务，并固化来源快照；
3. 使用已锁定的团队技能完成澄清、方案和计划；
4. 在澄清阶段逐项记录人工业务结论或外部等待；
5. 从计划自动生成一个或多个业务交付单元；
6. 在每个单元一次运行中完成开发、工程验证、测试、验收和交接；
7. 通过 Git 事实、产物哈希、运行证据和审批记录保证可追溯；
8. 支持来源刷新、外部决策解除、重跑和按风险接受关闭；
9. 通过 `doctor`、`status`、`runtime` 提供环境检查、下一步和运行记录。

MVP 不支持云端调度、身份权限、多人并发运行、PR/发布运维自动化，或无证据的在线文档读取。

## 验收标准

### AC-01：来源可信

- 输入 HTTP(S) 地址或本地文件后，AIW 能按规则选择来源读取器；
- 来源快照、元数据与任务记录的 SHA-256 一致；
- 快照被手动改写或来源更新后，下游不能静默继续。

### AC-02：需求结论可确认

- `clarify` 产出摘要、问题、验收清单和决策登记；
- 每次人工选择只解决一个业务结论，并留存操作者、时间、选项和说明；
- 未处理决策不能进入方案阶段。

### AC-03：计划可执行

- `plan` 产出实施计划和严格校验的 `work-breakdown.yaml`；
- 每个 AC 有唯一覆盖方式；本期或外部等待的 AC 只归属一个交付单元；
- 计划审批后为每个业务单元生成 `delivery-<unit-id>` 节点和最小上下文。

### AC-04：单元交付闭环

- 每个交付单元在一次运行中完成代码、工程验证、测试和所属 AC 的验收；
- 产出 `delivery.md`、`acceptance-results.yaml` 和 Handoff；
- 不存在全局 `verify`、`test` 节点，也不将所有单元的上下文汇总到最后；
- 跨单元验收通过独立集成交付单元表达。

### AC-05：事实与审批可信

- 下游运行前校验来源、上游产物、成功运行和审批事实的哈希；
- 未提交的任务事实不能作为下游输入；
- 重跑保留旧 revision 和运行证据，仅切换当前有效版本；
- 交付单元普通审批只允许其 AC 全部通过；风险接受必须带责任人、原因和到期时间。

### AC-06：上下文受控

- 默认上下文使用 Handoff 和当前单元上下文，不重复注入完整上游 Markdown；
- 上下文超预算时给出占用诊断，不能静默截断已批准事实；
- 复杂需求通过更多交付单元而不是全局验证汇总来控制规模。

### AC-07：可用性

- `doctor` 显示 Git、Codex、默认工作流、方法来源和文档连接器的可用状态；
- `status` 显示清晰的业务单元名称和唯一下一步；
- 用户只需要日常使用 `init`、`task init`、`task run`、`task review`、`task approve`；决策解除、风险关闭和技能升级为高级入口。
