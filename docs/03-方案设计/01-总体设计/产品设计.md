# AI Workflow 产品设计

## 产品命题

`aiw` 面向承担复杂研发需求的开发者、技术负责人和技能维护者。它把原本散落在聊天、在线文档和个人经验中的关键事实，组织为 Git 可审阅的任务产物、审批和执行依据，使团队能够在 AI 参与研发时明确：什么仍然有效、谁已确认、变化后必须重做什么。

本文只回答“谁在什么场景下如何使用 aiw”。命令参数见[CLI 命令参考](../03-接入与接口/CLI命令参考.md)，状态与失效规则见[任务模型规范](../02-核心规范/任务模型规范.md)，系统边界见[架构设计](架构设计.md)。

## 适用边界

### 适用场景

- 依据在线需求文档实现中等复杂度功能；
- 跨前端、后端和测试，需要先形成统一实施计划的变更；
- 需要复用团队已验证的分析、设计或测试方法的任务；
- 需求、方案或来源可能变更，且需要明确重做范围的任务。

### 不适用场景

- 无需沉淀来源、方案或审批的小型即时修改；
- 日常即时沟通、代码评审、发布管理或 CI/CD；
- 期望由 AI 自动决定业务结论、替代技术负责人审批的场景。

小修改可以直接沿用现有工程流程与 Codex；`aiw` 只在治理收益大于额外操作成本时介入。

## 用户与责任

| 角色 | 关心的问题 | 主要责任 | 不负责 |
|---|---|---|---|
| 任务发起开发者 | 如何稳定推进需求并减少重复整理？ | 创建任务、提供来源、选择技能、推进节点，并在业务仓库完成开发 | 代替技术负责人批准关键结论 |
| 技术负责人 | 哪些结论可以作为后续工作的依据？ | 审阅澄清、计划和最终测试的当前 revision；批准或要求修订 | 代替开发者进行日常编码 |
| 技能维护者 | 团队方法如何持续复用且不失控？ | 维护阶段技能、上游方法引用、版本和验证要求 | 为每个业务任务直接修改产物 |
| `aiw` | 如何保证过程事实可追溯？ | 管理快照、任务状态、依赖、审批、上下文和运行清单 | 判断业务结论、自动批准或执行 Git 提交 |
| Codex | 谁完成真实工程操作？ | 在指定业务仓库中分析、修改代码和运行测试 | 管理任务事实、绕过审批或自行选择技能 |

## 端到端任务旅程

```text
需求资料
  ↓ 固化为可审阅的来源快照
需求澄清
  ↓ 技术负责人确认当前结论
技术方案与实施计划
  ↓ 技术负责人确认可实施的计划
实现与工程验证
  ↓
验收测试
  ↓ 技术负责人确认最终证据
完成；或因上游变化回到受影响节点重新推进
```

该旅程的核心不是要求每一步都由 AI 完成，而是在进入下一步前确认当前输入可信。固定阶段、默认产物与审批点以[研发工作流阶段规范](../02-核心规范/研发工作流阶段规范.md)为准。

## 产物、审批与协作规则

| 任务阶段 | 团队需要得到的结果 | 协作规则 |
|---|---|---|
| 来源接入 | 可复查的资料快照及其版本 | 在线资料变化必须显式刷新，不能静默覆盖已有结论。 |
| 需求澄清 | 需求摘要、待确认问题和验收依据 | 当前 revision 经技术负责人确认后，才可进入方案。 |
| 方案与计划 | 技术取舍、风险、实施步骤 | 计划经确认后，才可作为实现输入。 |
| 实现与验证 | 业务改动、工程验证与修复记录 | 仍遵循团队既有提交、评审和 CI 流程。 |
| 验收测试 | 可审阅的测试证据 | 当前 revision 确认后，任务才完成。 |

团队共同遵守以下规则：

1. 关键结论必须沉淀为任务产物，不以聊天记录作为权威上下文。
2. 未确认或已失效的上游产物不得作为下游输入。
3. 来源、需求或方案改变时，修订真实原因节点并按影响范围重新推进，不手工拼接旧结论。
4. 技能通过独立技能仓库审阅和版本管理；单个任务不得修改已锁定的技能。
5. 业务仓库中的 `.aiw/` 只保存共享任务事实，不保存令牌、完整提示词、原始 Agent 输出或本机路径。

## 常见协作场景

### 需求资料更新

开发者刷新来源后，系统根据内容变化创建新的来源版本，并使依赖该来源的已开始节点失效。团队重新运行受影响节点，并重新确认必要结论；不会将更新后的需求与旧方案混用。

### 实现中发现方案缺口

开发者应回到产生缺口的方案、计划或更早节点修订结论，再继续后续工作。临时实现不能替代已经失效的计划或验收依据。

### 紧急小修改

若变更无需跨阶段协作、无关键审批且不需要长期追溯，团队可以直接使用现有开发流程。是否进入 `aiw` 由任务复杂度和治理收益决定，而不是机械强制。
