# 产品设计

## 核心问题

本文回答：用户如何借助 AIW，把一份需求资料推进为一组完成代码修改的开发单元。

## 用户价值

直接与 Coding Agent 对话时，复杂需求容易出现三类问题：不确定内容被包装成确定结论、超长上下文阻塞执行、流程运行完成被误认为结果已经可信。

AIW 在 MVP 中采用一条更窄的链路：

```text
先固定来源
  → 再分开事实与疑问
  → 人工确认本期结论
  → 再形成方案和开发计划
  → 可选：把用户提供的设计图片切割并绑定开发单元
  → 最后按业务单元修改代码
```

## 日常使用

1. 用户在业务仓库创建任务，AIW 固化需求来源；有关联设计稿时可同时传入一张或多张本地导出图片。
2. 用户执行 CLI 输出的下一条精准命令。
3. AIW 依次提示具体的 `task run`、`task review` 或 `task approve` 命令，完成事实和决策、人工确认、方案、计划与开发单元。
4. 开发计划仍需用户显式批准；节点 ID 由 CLI 直接给出，不要求用户自行判断。
5. 用户可通过 `task status` 查看开发单元汇总进度。

## 人工关卡

MVP 只有两个人工动作：

- 需求决策：澄清节点完成后，CLI 明确提示执行 `task review <task-id>`。
- 计划批准：`task approve <task-id> plan`，确认开发单元划分。

技术方案不单独审批；开发单元完成后也不做 AIW 审批。后续是否增加自动策略或工程验收，待 MVP 真实使用后再决定。

## 产物

- 来源快照：Markdown，保留可阅读的来源内容。
- 设计截图（可选）：PNG/JPEG；最小 YAML 索引保留截图 ID、来源图片、类型、用途、图片路径和绑定的开发单元。
- 事实登记：YAML，供人和程序读取。
- 决策登记：YAML，保存待决、本期结论和延期事项。
- 技术方案：Markdown，适合审阅。
- 开发计划：YAML，供程序生成开发单元图。
- 开发结果：Markdown，说明实际代码修改和风险。

## 产品边界

AIW 不取代 Codex，不替代项目管理工具，也不在 MVP 中判断业务代码是否已经测试或验收通过。任务状态“开发完成”只表示计划内开发单元都完成了代码修改。
