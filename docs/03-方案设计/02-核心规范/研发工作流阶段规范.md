# 研发工作流阶段规范

## 核心问题

复杂研发需求如何既不把模糊需求包装为完整计划，也不把全部上下文汇总到最后，还能完成可追溯的交付？

答案是：AIW 先把来源内容拆为事实与疑问，再经过决策门禁形成业务单元图；计划批准后按业务边界生成独立的**交付单元**。交付单元不是“只写代码”的子任务，而是最小可审阅交付闭环：代码实现、工程验证、验收测试和验收结论必须在同一次单元运行中完成。

## 工作流

```text
intake（AIW 原生）
  → clarify（事实/疑问拆分与决策确认）
  → solution（技术方案）
  → plan（实施计划与业务单元划分）
  → delivery-<unit-id>（按依赖关系执行；每个单元独立审批）
  → 汇总交付状态
```

`verify`、`test` 不再是全局节点。它们曾把所有实施单元的方案、代码说明和验证证据重新汇总，容易造成上下文超限，也让“谁对哪个验收项负责”不清晰。

## 入口路由

需求澄清完成后，AIW 基于已固化的来源、事实、验收项和待决结论给出路径建议：

| 建议路径 | 适用条件 | 最小闭环 |
|---|---|---|
| 快速修改 | 范围明确、没有接口/权限/业务规则不确定性，且可由一个单元验证 | 单一交付单元的代码、测试、验收和变更证据 |
| 标准需求 | 不满足快速修改条件的全部需求 | 本规范中的完整主干与一个或多个交付单元 |

快速修改仅在**单来源、快照不超过 12,000 字、单一 AC、没有决策项、全部事实为已确认且 high 可信度**时可选。它只省略独立的 `solution` 节点，仍必须经历 `plan → 单一交付单元 → 汇总交付状态`，并保留同样的 Git、测试、验收和审批事实。快速计划必须只有一个无依赖、无决策、无外部等待的交付单元。只要出现未确认业务规则、接口、权限、数据口径、多个验收项或跨单元依赖，AIW 只能采用标准需求。开始计划前，快速修改可通过再次 `task review` 升级为标准需求；不允许由标准需求降级为快速修改。

## 固定主干

| 节点 | 目的 | 必须产物 | 审批 |
|---|---|---|---|
| `intake` | 固化来源快照；在连接器支持时按用户指定章节读取 | `sources/requirements/r<revision>/snapshot.md`、`meta.json`、`task.md`、来源操作 Handoff | 不需要 |
| `clarify` | 区分事实、推断、疑问、外部依赖，形成验收项、证据类型和待决业务结论 | `brief.md`、`questions.md`、`acceptance.md`、`acceptance.yaml`、`decision-register.yaml`、Handoff | `task review` |
| `solution` | 形成可实施技术方案 | `solution.md`、Handoff | 默认不需要 |
| `plan` | 定义交付单元、依赖、AC 归属，以及 AC 到测试能力、测试目标和证据类型的固定映射 | `implementation-plan.md`、`work-breakdown.yaml`、Handoff | `task approve` |

标准需求使用完整主干。快速修改在 `task review` 选择后将 `solution` 标记为已跳过，并让 `plan` 直接依赖 `clarify`；它不是另一套技能或另一种验收规则。

## 交付单元

计划获批后，AIW 读取 `work-breakdown.yaml`，为每个 `units[]` 生成 `delivery-<unit-id>` 节点；即使只有一个单元，也不会暴露通用 `implement` 节点。

每个交付单元必须：

- 只接收本单元上下文、必要上游 Handoff、已批准计划和任务事实；
- 完成代码修改、工程验证、测试和本单元验收；
- 生成逻辑产物 `delivery.md`（含测试计划）和 `acceptance-intent.yaml`；AIW 在 Codex 退出后生成 `test-results.yaml` 与唯一正式的 `acceptance-results.yaml`。正式物理路径统一位于 `artifacts/<delivery-node-id>/`；
- 只认领其 `acceptanceRefs` 中的验收项；
- 只能执行批准计划锁定的测试映射，不得把 UI、API 或集成验收改成更弱的单元测试；
- 在结果通过后由 `aiw task approve <task-id> delivery-<unit-id>` 审批。

一个 AC 只能归属一个交付单元。若某项验收需要多个业务单元共同验证，计划必须新增一个依赖这些单元的“集成交付单元”，由它独立完成该 AC 的验证和审批，不能让多个单元共同认领同一 AC。

证据类型由澄清阶段固定：UI 交互使用组件交互或浏览器证据，API 契约使用契约或集成证据，纯逻辑才允许单元测试。计划只能在项目已声明支持相应类型的测试能力中选择；交付完成后，AIW 将真实测试记录与批准映射逐字段核对，不一致即不能通过验收。

计划必须维护“来源 → 事实/决策 → AC → 交付单元”的影响关系，用于校验引用、展示影响和约束交付单元。当前来源快照尚未具备领域级可比较片段，因此来源正文变化时会保守地使全部下游失效并重新澄清；只有 `execution-only` 类型的外部条件解除可以局部解锁对应单元。自动来源分片完成后，才允许依据可追溯片段计算更小的失效范围。

## 状态和结果

- 计划批准前，只有主干节点可运行。
- 计划批准后，独立且无阻塞的交付单元可同时处于就绪状态；MVP 对同一任务一次只允许一个变更命令执行。节点运行、来源刷新、审批和决策共用任务锁，并由 `task.yaml.stateVersion` 拒绝过期写入，避免运行完成状态覆盖来源刷新或人工确认结果。
- 单元依赖的外部条件未满足时，仅阻塞对应单元；无关单元继续推进。
- Agent 正常退出只表示“运行完成”；其 AC 有真实测试和证据才表示“验收通过”。
- 所有当前交付单元完成并审批后，任务结束。
- 所有单元的 AC 都通过时交付状态为“可交付”；若某单元以 `close-with-risk` 关闭，则为“风险已接受”；尚无足够证据时必须显示“尚未评估”或“存在阻塞”。

## 重跑与变更

`aiw task run` 同时用于首次运行、失败重试和覆盖式重跑。校验成功的重跑会覆盖节点当前产物、Handoff 和审批事实，并使下游当前结果失效；每次运行的日志、Diff 和失败证据仍保留在各自的运行目录。

当前 Codex 直接修改业务仓库工作区。运行前工作区必须干净；运行失败后业务改动可能继续存在，AIW 会保留变更证据并阻止下一次运行建立错误基线，用户需先检查并处理这些改动。当前没有独立 worktree 或“验证通过后自动合入”能力。

需求变化只能通过来源刷新触发：`aiw task source refresh`。来源刷新或重新执行 `clarify` 会清除当前工作方式选择、恢复标准拓扑，并要求重新评估后再选择。外部等待解除并带来接口、规则或口径等新事实时，必须记录事实并重跑 `solution → plan`；不能直接放行旧交付单元。

来源刷新从重新读取来源开始到新快照、Handoff、节点失效和 `task.yaml` 更新完成，全程持有任务锁。刷新期间不能启动节点、审批或解除决策；已经持锁运行的节点存在时，刷新也必须拒绝执行。用户等待当前命令结束后重试即可。

## 方法来源

标准模板锁定四项技能：

- `requirements-clarification`：复用 Superpowers 的 brainstorming；
- `technical-solution`：复用 brainstorming；
- `implementation-planning`：复用 writing-plans；
- `typescript-web-implementation`：复用 test-driven-development，并在单元内完成工程验证与验收测试。

技能版本、工作流模板版本与 Git tag 的关系由《技能包规范》和 skills 仓库的《工作流版本发布指南》定义。
