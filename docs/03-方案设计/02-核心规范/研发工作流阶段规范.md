# 研发工作流阶段规范（v1）

## 目的

本规范定义 `aiw` 管理复杂研发任务的固定七阶段、各阶段目的、逻辑输入、必须产物、默认审批点和方法论引用。它不定义任务状态机、审批记录格式、上下文目录或失效算法。

`aiw` 不重新定义通用研发方法。每个阶段通过版本锁定的技能引用 Superpowers 等上游方法论；`aiw` 仅补充当前任务的输入、产物、审批和审计约束。

MVP 工作流终点为“测试验证完成并获人工批准”。代码评审、合并、发布和线上运维继续使用团队既有流程，不属于 `aiw`。

## 默认工作流

```text
intake
  → clarify → 人工审批
  → solution
  → plan → 人工审批
  → implement
  → verify
  → test → 人工审批
```

七个阶段 ID 是固定的。`task init` 初始创建线性主干；计划获批后，AIW 根据 `work-breakdown.yaml` 自动保留一个 `implement` 工作单元，并在需要时增加 `implement-*` 子节点。所有当前实施工作单元完成前，`verify` 不会开始。

任务创建时，发起人选择一个团队工作流模板；模板一次锁定 `clarify` 至 `test` 的六阶段技能。后续节点直接使用该锁定，只有例外情况才重新绑定单个节点技能。模板结构与锁定规则以《技能包规范》和《任务模型规范》为准。

## 阶段定义

| 节点 | 目的 | 输入 | 必须产物 | 默认审批 | 方法论引用 |
|---|---|---|---|---:|---|
| `intake` | 固化任务和来源 | 用户任务、显式来源 | 来源快照、来源元数据 | 否 | 无；由 `aiw` 原生完成 |
| `clarify` | 澄清目标、范围、问题和验收 | 原始任务、来源快照 | `brief.md`、`questions.md`、`acceptance.md` | 是 | `superpowers:brainstorming` |
| `solution` | 形成技术方案、边界、取舍和风险 | 已批准的需求产物 | `solution.md` | 否 | `superpowers:brainstorming` 的方案设计方法 |
| `plan` | 拆分实施步骤、依赖和测试方式 | 需求产物、方案 | `implementation-plan.md`、`implementation-context.md`、`work-breakdown.yaml` | 是 | `superpowers:writing-plans` |
| `implement` | 按工作单元在业务仓库完成代码修改 | 已批准的验收标准与本单元实施上下文 | `implementation.md` 或 `subtasks/<node-id>.md`；业务代码由项目仓库保存 | 否 | `superpowers:using-git-worktrees`、`test-driven-development`、`executing-plans` |
| `verify` | 检查实现是否符合工程约束，并修复发现的问题 | 已批准方案、实施计划、实现说明；业务仓库 | `verification.md` | 否 | `superpowers:systematic-debugging`、`verification-before-completion` |
| `test` | 对照验收标准完成最终测试并汇总证据 | 已批准需求、方案、验收标准、验证结果；业务仓库 | `test-report.md` | 是 | `superpowers:verification-before-completion` |

`solution` 不单独设置默认人工审批：它作为 `plan` 的输入，技术负责人应在审批 `implementation-plan.md` 时一并审阅 `solution.md`。高风险任务可在任务模板中将 `solution.requiresApproval` 显式设为 `true`。

## 阶段产物与审批

阶段产物均为 Git 共享任务事实。`questions.md` 可以保留未决问题，但 `clarify` 获批前必须明确不阻塞后续阶段的问题及其假设；`implementation.md` 不复制业务代码或替代 Git 提交记录；`test-report.md` 必须逐项对应 `acceptance.md`。

默认审批节点为 `clarify`、`plan` 和 `test`。`solution` 不单独设置默认人工审批：技术负责人应在审批 `implementation-plan.md` 时一并审阅 `solution.md`；高风险任务可显式设为需审批。

审批记录、状态迁移和“待审产物及状态必须提交”规则以《任务模型规范》为准。

## 最小上下文规则

业务代码始终由 Codex 在 `projectRoot` 内按需读取，不复制进任务上下文。每次运行仅选择该阶段逻辑输入中当前 revision、已满足审批条件的任务事实；`intake` 不调用 Agent。具体文件路径、Context Manifest、用户附加项、预算与注入顺序以《上下文包规范》为准。

## 方法论引用与组合

阶段技能可以通过 `methodSources` 声明其复用的上游方法论：

```yaml
name: requirements-clarification
version: 1.0.0
phases: [clarify]
methodSources:
  - id: superpowers:brainstorming
    version: 6.2.0
    source: bundled:superpowers
```

`methodSources` 的规则如下：

1. 每项必须包含稳定 ID、版本和可解析来源；安装后记录其来源标识、解析 revision 与内容 SHA-256。新标准技能的内置来源清单和解析以《技能包规范》为准。
2. 阶段技能只允许增加当前节点的输入、产物、禁止事项和验证要求；不得复制、修改或伪造上游方法论正文。
3. Runner 依次注入不可变运行约束、节点契约、上游方法论、阶段技能叠加层、用户任务和来源/产物数据。
4. 上游方法、阶段技能、来源和任务产物均必须出现在 Context Manifest；任何版本、哈希或阶段不匹配都必须拒绝运行。
5. 上游方法与阶段叠加层发生冲突时，以 `aiw` 的不可变运行约束和节点契约为准；技能不得绕过审批、路径、预算或 sandbox 限制。

MVP 将 `methodSources` 作为强制记录：阶段技能只解析团队包内置并已安装的方法副本，不自动扫描、下载或更新上游技能，且不能静默替换已锁定的方法版本；不支持 `configured:` 来源。

## 修订与失效

来源或任一阶段产物出现新 revision 后，必须按《任务模型规范》的 DAG 规则使已开始的下游节点失效；旧产物不能再作为默认输入。若 `test` 需要修改代码，开发者必须修订 `implement` 或更早的真实原因节点，不得只修改 `test-report.md`。

## 分阶段接入

固定七阶段是最终默认模型，但团队可按以下顺序启用，降低试点风险：

| 接入阶段 | 启用范围 | 验证目标 |
|---|---|---|
| 第一阶段：需求与方案治理 | `intake → clarify → solution → plan` | 验证来源快照、需求审批、方案与计划的可追溯性 |
| 第二阶段：受控实现 | 增加 `implement` | 验证 Codex Adapter 与 Superpowers 实施方法在真实仓库中的协作 |
| 第三阶段：质量闭环 | 增加 `verify → test` | 验证工程检查、验收证据与最终审批闭环 |

未启用的后续阶段不能被标记为完成或假定通过；试点任务可在已启用阶段结束，并明确记录其未覆盖范围。

## 后续自动门禁方向

MVP 的 `clarify`、`plan`、`test` 使用人工审批，且不得绕过。后续阶段可以为满足明确适用条件的标准化任务引入版本化策略自动门禁，逐节点人工审批不再是完成任务的必要条件。

自动门禁只替换“如何作出通过或退回决定”，不改变七阶段产物、revision、失效传播和运行证据的要求。每次自动决定必须记录所用策略版本、判定输入、决定结果和时间，并可被随时观测；策略未命中、输入不完整或出现异常时必须停止自动推进并形成待处理记录。

## 非目标

- 不将 Superpowers 的每一个技能都建成独立任务节点；
- 不替代代码评审、PR、发布、CI/CD 或线上运维；
- 不要求所有小型改动进入七阶段工作流；
- MVP 不允许 Agent 自动跳过阶段、人工审批或失效检查；后续自动模式也不得绕过阶段、版本化决策门禁或失效检查。
