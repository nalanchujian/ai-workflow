# 研发工作流阶段规范

## 核心问题

复杂研发需求如何既不把模糊需求包装为完整计划，也不把全部上下文汇总到最后，还能完成可追溯的交付？

答案是：AIW 先把来源内容拆为事实与疑问，再经过决策门禁形成业务单元图；计划批准后按业务边界生成独立的**交付单元**。交付单元不是“只写代码”的子任务，而是最小可审阅交付闭环：代码实现、工程验证、验收测试和验收结论必须在同一次单元运行中完成。

## 工作流

```text
intake（AIW 原生）
  → clarify（事实/疑问拆分与决策确认）
  → solution（技术方案）
  → plan（实施计划与业务单元划分）
  → delivery-<unit-id>（按依赖关系执行；每个单元独立审批）
  → 汇总交付状态
```

`verify`、`test` 不再是全局节点。它们曾把所有实施单元的方案、代码说明和验证证据重新汇总，容易造成上下文超限，也让“谁对哪个验收项负责”不清晰。

## 入口路由

进入固定主干前，MVP 应基于来源、变更范围、外部依赖和风险给出路径建议：

| 建议路径 | 适用条件 | 最小闭环 |
|---|---|---|
| 快速修改 | 范围明确、没有接口/权限/业务规则不确定性，且可由一个单元验证 | 单一交付单元的代码、测试、验收和变更证据 |
| 标准需求 | 有可明确的来源与验收项，可能需要少量决策 | 本规范中的完整主干与一个或多个交付单元 |
| 复杂需求 | 跨领域、跨模块、外部依赖多，或来源超过单次上下文预算 | 来源切片、原子决策、业务单元图与集成交付单元 |

建议不是绕过治理的许可。只要发现未确认的业务规则、接口、权限、数据口径或跨单元依赖，就必须升级到标准或复杂路径，并记录升级原因。

## 固定主干

| 节点 | 目的 | 必须产物 | 审批 |
|---|---|---|---|
| `intake` | 固化来源、章节/领域索引和快照 | `sources/requirements/r<revision>/snapshot.md`、`meta.json`、来源索引、Handoff | 不需要 |
| `clarify` | 区分事实、推断、疑问、外部依赖，形成验收项和待决业务结论 | `brief.md`、`questions.md`、`acceptance.md`、`acceptance.yaml`、`decision-register.yaml`、Handoff | `task review` |
| `solution` | 形成可实施技术方案 | `solution.md`、Handoff | 默认不需要 |
| `plan` | 定义交付单元、依赖、验证方式和 AC 归属 | `implementation-plan.md`、`work-breakdown.yaml`、Handoff | `task approve` |

## 交付单元

计划获批后，AIW 读取 `work-breakdown.yaml`，为每个 `units[]` 生成 `delivery-<unit-id>` 节点；即使只有一个单元，也不会暴露通用 `implement` 节点。

每个交付单元必须：

- 只接收本单元上下文、必要上游 Handoff、已批准计划和任务事实；
- 完成代码修改、工程验证、测试和本单元验收；
- 生成 `artifacts/delivery.md`（含测试计划）和 `artifacts/acceptance-results.yaml`；AIW 在 Codex 退出后生成 `artifacts/test-results.yaml`；
- 只认领其 `acceptanceRefs` 中的验收项；
- 在结果通过后由 `aiw task approve <task-id> delivery-<unit-id>` 审批。

一个 AC 只能归属一个交付单元。若某项验收需要多个业务单元共同验证，计划必须新增一个依赖这些单元的“集成交付单元”，由它独立完成该 AC 的验证和审批，不能让多个单元共同认领同一 AC。

计划必须维护“来源片段 → 事实/决策 → AC → 交付单元”的影响关系。来源或决策变化时，系统据此只使相关方案、计划或交付单元失效；不能因无关变更让全部工作重做，也不能让受影响单元继续采用旧结论。

## 状态和结果

- 计划批准前，只有主干节点可运行。
- 计划批准后，独立且无阻塞的交付单元可并行就绪；MVP Runner 仍一次运行一个节点，避免同一任务事实并发写入。
- 单元依赖的外部条件未满足时，仅阻塞对应单元；无关单元继续推进。
- Agent 正常退出只表示“运行完成”；其 AC 有真实测试和证据才表示“验收通过”。
- 所有当前交付单元完成并审批后，任务结束。
- 所有单元的 AC 都通过时交付状态为“可交付”；若某单元以 `close-with-risk` 关闭，则为“风险已接受”；尚无足够证据时必须显示“尚未评估”或“存在阻塞”。

## 重跑与变更

`aiw task run` 同时用于首次运行、失败重试和覆盖式重跑。重跑不会删除历史产物、Handoff、审批或运行证据；新 revision 仅切换“当前有效版本”，并使下游当前版本失效。

需求变化只能通过来源刷新触发：`aiw task source refresh`。如果外部等待解除并带来接口、规则或口径等新事实，必须记录事实并重跑 `solution → plan`；不能直接放行旧交付单元。

## 方法来源

标准模板锁定四项技能：

- `requirements-clarification`：复用 Superpowers 的 brainstorming；
- `technical-solution`：复用 brainstorming；
- `implementation-planning`：复用 writing-plans；
- `typescript-web-implementation`：复用 test-driven-development，并在单元内完成工程验证与验收测试。

技能版本、工作流模板版本与 Git tag 的关系由《技能包规范》和 skills 仓库的《工作流版本发布指南》定义。
