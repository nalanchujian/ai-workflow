# 研发工作流阶段规范

## 核心问题

本文回答：每个阶段读取什么、产出什么、何时进入下一步。

## 固定主干

```text
intake → [design-analysis] → clarify → solution → plan → development units
```

### intake：接入资料

- 生成者：AIW。
- 输入：通用文档地址或本地文件，可选章节。
- 输出：来源快照和来源元数据。
- 完成方式：`task init`；不能通过 `task run intake` 重跑。
- 需求变化：使用 `task source refresh`，并让下游重新执行。

### clarify：澄清需求

- 生成者：Codex。
- 输入：来源快照；存在设计稿时同时读取设计目录和设计规则。
- 输出：事实登记、决策登记。
- 人工动作：澄清节点完成后执行 CLI 给出的 `task review <task-id>`。
- 规则：一次决策只处理一个业务问题；延期事项退出当前流程。

### design-analysis：分析设计稿（可选）

- 生成者：Codex；节点运行时使用已登录的 Chrome 打开 Figma。
- 输入：需求快照、任务登记的 Figma 父节点地址。
- 输出：设计目录 YAML、设计规则 YAML、中文设计上下文 Markdown。
- 规则：先建立页面和状态目录，再按需读取代表性节点；AIW 不使用 Figma MCP；浏览器不可访问时明确失败；不修改业务代码，不替代需求澄清。

### solution：形成技术方案

- 生成者：Codex。
- 输入：事实登记、本期已确认决策；存在设计稿时同时读取设计目录和规则。
- 输出：中文技术方案 Markdown。
- 规则：不读取延期事项作为本期范围，不生成验收编号或实施单元。

### plan：制定开发计划

- 生成者：Codex。
- 输入：技术方案；存在设计稿时同时读取设计目录和规则。
- 输出：结构化开发计划 YAML。
- 人工动作：`task approve <task-id> plan`。
- 规则：只拆代码开发单元；每个单元使用唯一的 `development-unit-<英文 kebab-case 描述>` 名称，依赖只能引用同一计划中的单元名称且不能循环。

### development：开发单元

- 生成者：Codex。
- 输入：当前开发单元 YAML；界面单元使用已登录的 Chrome 按 `designReferences` 精确读取对应 Figma 节点。
- 输出：业务代码和开发结果 Markdown。
- 执行：独立 Git worktree。
- 日常入口：执行 CLI 给出的 `task run <task-id> <development-unit-name>` 精准命令，例如 `development-unit-main-list-export`。
- 例外入口：确认开发单元不属于当前仓库或任务范围时，执行 `task ignore` 并记录原因；运行中的单元不能忽略。
- 规则：只负责开发，不执行或宣称验证、测试、验收与生产交付。

## 完成语义

- 节点完成：该节点产物通过结构校验并成功保存。
- 开发单元完成：该单元代码补丁已发布到用户工作区，开发结果已保存。
- 任务开发完成：所有当前开发单元均已完成或已忽略；状态页必须分别统计两类结果。

以上状态均不等于测试通过、验收通过或已上线。
