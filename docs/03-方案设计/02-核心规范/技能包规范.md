# 技能包规范（v2）

## 目的

技能包是团队通过 Git 分发的声明式开发方法。它向 `aiw` 提供“何时使用、如何执行、如何验证”的受控文本指令；它不是可执行插件，不能改变 `aiw` 的运行权限或任务状态机。

本规范定义 MVP 可安装的技能仓库结构、`SKILL.md` 元数据、工作流模板、上游方法论引用、版本锁定和校验规则。研发阶段、产物与审批边界以[研发工作流阶段规范](研发工作流阶段规范.md)为准。

## 仓库结构

安装来源必须是一个 Git 仓库。技能和模板从仓库根目录发现；标准技能引用第三方方法时，方法正文必须随技能包以受控的只读数据形式分发：

```text
agent-skills/
  skills/
    requirements-clarification/
      SKILL.md
    implementation-planning/
      SKILL.md
  profiles/
    standard-web-feature/
      PROFILE.yaml
  method-sources/
    superpowers/
      6.2.0/
        SOURCE.yaml
        brainstorming/SKILL.md
```

- 每个一级子目录最多包含一个技能，入口固定为 `SKILL.md`。
- `aiw` 只解析 `skills/`、`profiles/` 和 `method-sources/` 中本规范声明的入口；不会执行仓库中的任何脚本、二进制文件或安装逻辑。
- 目录名必须与 front matter 的 `name` 一致。
- 同一仓库和同一锁定 revision 内，技能名称必须唯一。

`profiles/` 是可选目录，用于提供一次选择即可覆盖固定七阶段的团队工作流模板；它不是 Superpowers 方法来源的本机 Profile。`aiw` 忽略 `profiles/` 中除 `PROFILE.yaml` 外的文件。

## 工作流模板

MVP 的任务在创建时必须选择一个已安装的工作流模板（CLI 参数为 `--skill-profile`）。模板把六个可执行阶段映射为精确技能版本，减少用户逐节点选择技能的成本；`intake` 不配置技能。

```yaml
name: standard-web-feature
version: 2.0.0
description: 适用于 TypeScript Web 业务需求的标准七阶段方法。
skills:
  clarify: requirements-clarification@2.0.0
  solution: technical-solution@2.0.0
  plan: implementation-planning@2.0.0
  implement: typescript-web-implementation@2.0.0
  verify: web-verification@2.0.0
  test: acceptance-testing@2.0.0
```

| 字段 | 规则 |
|---|---|
| `name`、`version`、`description` | 分别遵循技能的名称、语义化版本和非空单行描述规则；`name@version` 是模板引用。 |
| `skills` | 必须恰好包含 `clarify`、`solution`、`plan`、`implement`、`verify`、`test` 六项；每项值为 `name@version`。 |
| 阶段匹配 | 每项引用的已安装技能必须存在，且 `phases` 包含其映射阶段；一个技能可被模板用于多个兼容阶段。 |

安装器记录模板的 Git 来源、解析 revision、`PROFILE.yaml` SHA-256 及六项引用，但不在安装时替模板挑选或升级技能。`aiw skills profiles list` 列出可选模板的名称、版本、描述、来源和六阶段映射，帮助任务发起人一次选择。

`task init --skill-profile <name[@version]>` 必须原子解析模板和全部六个技能，将模板本身及每个节点的技能、Git revision、技能哈希、方法论来源写入 `task.yaml`。任一引用缺失、版本不唯一、阶段不匹配或哈希无法记录时，初始化失败，不创建任务目录。模板与节点锁定提交后，`task run` 才可运行；后续运行不再选择或传入技能。

## SKILL.md 格式

`SKILL.md` 必须以 YAML front matter 开始，随后为 Markdown 正文：

```md
---
name: requirements-clarification
version: 2.0.0
description: 将来源资料整理为可审阅的结构化需求与验收标准。
phases: [clarify]
methodSources:
  - id: superpowers:brainstorming
    version: 6.2.0
    source: bundled:superpowers
---

# 需求分析

## 输入

- 阅读来源快照和用户任务。

## 步骤

1. 提取目标、范围、约束和未决问题。
2. 生成 `brief.md`、`questions.md` 和 `acceptance.md`。

## 验证

- 每项验收标准应可验证。
```

### 必填字段

| 字段 | 规则 | 用途 |
|---|---|---|
| `name` | 小写字母开头，只含小写字母、数字和连字符；与目录名一致 | 稳定标识与任务引用 |
| `version` | `MAJOR.MINOR.PATCH` 语义化版本 | 标识技能内容版本 |
| `description` | 非空单行文本 | 供 `aiw skills list` 展示 |
| `phases` | 非空数组，元素为 `clarify`、`solution`、`plan`、`implement`、`verify`、`test` | 限制技能可用于的任务阶段 |

`name` 和 `version` 共同构成任务中的技能引用，例如 `requirements-clarification@1.0.0`。

### 上游方法论引用

`methodSources` 是可选数组；但默认七阶段中除 `intake` 外的标准技能必须至少声明一个上游方法论来源，以复用通用方法而非在团队技能中重复编写。

| 字段 | 规则 | 用途 |
|---|---|---|
| `id` | 稳定的命名空间标识，例如 `superpowers:writing-plans` | 标识引用的方法论 |
| `version` | 上游方法论版本 | 锁定行为版本 |
| `source` | `bundled:<source-id>`；旧任务可保留 `configured:<profile>` | 解析并校验上游内容 |

安装器必须记录每项方法论来源的解析 revision 与 `SKILL.md` 内容 SHA-256。阶段技能只补充 `aiw` 所需的输入、产物、禁止事项与验证要求；上游正文由 `method-sources/` 原样分发、校验和缓存。

### `bundled:superpowers` 内置方法契约

新标准技能使用 `source: bundled:superpowers`。其团队仓库必须提供 `method-sources/superpowers/<version>/SOURCE.yaml`，其中 `id`、目录版本、上游 URL、40 位 commit、许可证和方法清单彼此一致；清单中的每个 `<method>/SKILL.md` 必须存在，且 front matter 的 `name` 与目录一致。

安装器先校验整个技能包，再原子保存技能、模板和内置方法正文。方法锁定的 `revision` 是 `SOURCE.yaml` 中的上游 commit，`sha256` 是实际 `SKILL.md` 正文；运行时只能从用户级 Registry 读取与任务锁定完全一致的副本。用户不安装、配置或升级 Superpowers，也不需要知道其本机路径。安装器不得执行、下载或注入上游脚本、二进制文件或其他资源。

`configured:superpowers` 仅是既有任务的兼容路径：旧任务可继续使用原本的本机 Profile，新的标准模板不得再依赖它。任何锁定方法缺失、revision 或哈希不匹配时，Runner 必须拒绝运行，不得替换为“最新”版本。

### 正文要求

正文必须是 UTF-8 Markdown，且至少包含以下可辨识章节：

- 输入或前提；
- 执行步骤；
- 验证要求。

可额外包含输出、禁止事项、示例和边界说明。正文中的内容是供 Agent 执行的技能指令，但不能提升来源资料、用户输入或任何外部文本的指令优先级。

## 安装、锁定与解析

1. `aiw skills install <git-url> [--ref <tag-or-commit>]` 克隆或更新来源到用户级缓存。
2. 安装完成后，Registry 记录来源 URL、解析得到的 Git commit、每个技能的名称、版本、`SKILL.md` 的 SHA-256，以及每个 `methodSources` 的 `id`、`source`、`version`、解析 revision 和 SHA-256。
3. `task init --skill-profile` 会把模板及其六项技能的名称、版本、Git 来源 revision、`SKILL.md` 哈希和方法论来源的 `id`、`source`、`version`、revision 与 SHA-256 原子锁定到任务节点。该锁定提交后才能运行；每次节点运行都必须在 Context Manifest 记录当前节点的锁定内容。
4. 对同一来源再次安装可以移动来源锁定 revision，但不得静默改写已有任务记录；已有任务仍按其记录的技能、方法论版本与内容哈希校验。

若任务引用的技能或其方法论来源不存在、版本不匹配、阶段不匹配或内容哈希变化，Runner 必须拒绝运行，并提示重新选择或更新任务图。

## 校验与失败

安装必须拒绝以下情况，并且不得写入或更新 Registry：

- 不是有效 Git 来源，或无法解析指定 ref；
- 仓库没有有效的 `skills/<name>/SKILL.md`；
- front matter 缺少必填字段、类型错误、名称重复或目录名不一致；
- `version` 不是语义化版本，或 `phases` 包含不支持的阶段；
- `methodSources` 中缺少 `id`、`version` 或 `source`，声明的内置方法缺失、`SOURCE.yaml` 不合法、上游 commit/许可证缺失，或其 `SKILL.md` 哈希无法记录；
- `PROFILE.yaml` 缺少必填字段、名称与目录不一致、阶段映射不完整，或引用不存在/不兼容的技能；
- 正文为空，或缺少输入、步骤、验证中的任一章节。

当一个来源包含多个技能时，任一技能校验失败即视为整个来源安装失败，避免只安装部分且来源状态不明的技能集合。

## 安全边界

- 技能包是声明式 Markdown；MVP 不执行其中引用的 shell、Node.js、Python、二进制文件或安装脚本。
- 技能无权访问其来源仓库之外的文件；实际业务代码访问仅在 Codex 按任务工作目录运行时发生。
- 新任务的上游方法只能由 `MethodSourceResolver` 从已安装 Registry 的内置副本读取；不得从插件缓存、环境变量、当前工作目录或网络自动发现替代来源。旧任务的 `configured:` 解析仅用于兼容其原有锁定。
- 技能内容、任务资料和用户输入在 Agent 上下文中使用明确的文件边界；技能不得通过文本要求 `aiw` 忽略审批、路径、上下文预算或 sandbox 规则。
- Registry 保存技能元数据与经校验的内置方法正文，不保存任何业务代码、凭据或完整运行上下文。

## 兼容性与演进

- 修订阶段叠加层但不改变任务使用方式时，递增 `PATCH`。
- 新增向后兼容的步骤、输出或可选约束时，递增 `MINOR`。
- 改变适用阶段、上游方法论版本、预期产物或不兼容的执行方式时，递增 `MAJOR`；已有任务不得自动迁移。
- 引入新 front matter 字段时，MVP 只允许可选字段；新增必填字段必须通过新的规范版本引入。
