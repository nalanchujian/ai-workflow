# 任务模型规范（v1）

## 目的

任务模型将一个复杂需求表示为 Git 共享、可追溯的有向无环图（DAG）。它负责子任务依赖、审批、重试与上游变更后的下游失效；不负责定义通用研发方法或调用 Agent。

默认节点、阶段产物、审批点和最小上下文以[研发工作流阶段规范](研发工作流阶段规范.md)为准；本规范定义其在任务状态机中的持久化和执行约束。

## 存储位置

每个任务位于业务仓库根目录的 `.aiw/tasks/<task-id>/task.yaml`。`.aiw/config.yaml`、任务来源、阶段产物、审批记录和运行清单均为**共享任务事实**：必须纳入 Git，供任务发起者、审批人和后续执行者在同一分支上审阅。

`task-id` 必须匹配 `[a-z][a-z0-9-]{1,63}`，并在仓库内唯一。技能缓存、完整 Agent 输出、临时提示词与会话运行态只保存在用户目录的 `~/.aiw/`，不得写入共享任务目录。

```yaml
schemaVersion: aiw.task/v1
id: refund-123
title: 实现退款功能
repository: .
status: active # active | blocked | completed | cancelled
skillProfile:
  name: standard-web-feature
  version: 1.0.0
  registrySource:
    url: git@github.com:your-org/agent-skills.git
    revision: a1b2c3d4
  sha256: <profile-yaml-sha256>
nodes:
  intake:
    title: 接入资料
    phase: intake
    dependsOn: []
    status: completed
    revision: 1
    outputs: [sources/requirements/r1/snapshot.md, sources/requirements/r1/meta.json]
  clarify:
    title: 澄清需求
    phase: clarify
    dependsOn: [intake]
    skill: # 由 skillProfile 在初始化时锁定
      name: requirements-clarification
      version: 1.0.0
      registrySource: {url: git@github.com:your-org/agent-skills.git, revision: a1b2c3d4}
      sha256: <skill-md-sha256>
      methodSources:
        - id: superpowers:brainstorming
          source: configured:superpowers
          version: 6.2.0
          revision: 6.2.0
          sha256: <method-skill-md-sha256>
    requiresApproval: true
    status: ready
    revision: 0
    outputs: [artifacts/brief.md, artifacts/questions.md, artifacts/acceptance.md]
# solution、plan、implement、verify、test 均省略；它们各自拥有与 clarify 相同结构的完整技能锁定。
approvalRefs: []
events: []
```

## 工作流模板与技能锁定

`task init --skill-profile <name[@version]>` 必须一次选择并锁定整个任务的六阶段方法链。它将工作流模板以及 `clarify` 至 `test` 的精确技能锁定写入 `task.yaml`；调用者只需提交一次，后续 `task run <task-id> <node-id>` 直接使用该节点锁定的技能。这样“本次任务采用何种方法”与实际执行一样，是可审阅的 Git 事实，而不是某台机器上当时恰好安装的最新技能。

节点锁定的最小结构如下：

```yaml
skill:
  name: requirements-clarification
  version: 1.0.0
  registrySource:
    url: git@github.com:your-org/agent-skills.git
    revision: a1b2c3d4
  sha256: <skill-md-sha256>
  methodSources:
    - id: superpowers:brainstorming
      source: configured:superpowers
      version: 6.2.0
      revision: 6.2.0
      sha256: <method-skill-md-sha256>
```

- `task run` 不接收技能参数，只按节点锁定的 Git revision、技能哈希和方法论哈希读取内容。
- `task skill rebind` 是例外变更：仅可作用于 `pending`、`ready`、`failed` 或 `invalidated` 节点，必须给出原因。已完成节点必须先 `task revise`；等待审批的节点必须先由审批人作出决定。重新绑定仅替换该节点的锁定，会记录旧、新锁定和原因，并使所有已开始的下游节点失效；任务仍保留其原始工作流模板记录。
- 本机 Registry、Superpowers Profile 或任一哈希不再匹配节点锁定时，Runner 必须拒绝运行；不得自动升级或选择替代技能。

## 节点状态

`status` 只描述节点的执行状态；审批决定单独保存在 `approvals` 中，避免将 `approved` 与 `completed` 混为一谈。

```text
pending → ready → running → awaiting_approval → completed
                  │                 │
                  ├→ failed         ├→ pending  (changes requested)
                  └→ cancelled      └→ completed (approved)

任意节点 → invalidated（已使用的上游 revision 改变）
invalidated → pending（重新规划或确认后）
```

- `pending`：依赖、人工输入或规划尚未满足。
- `ready`：所有依赖均为 `completed`，可开始执行。
- `running`：Runner 已启动一次 Agent 调用。
- `awaiting_approval`：节点已产出结果，等待人工决定。
- `completed`：节点已成功结束；若要求审批，则已经批准。
- `failed`：Agent 调用或产物校验失败；保留错误信息与运行记录。
- `invalidated`：上游输出发生新 revision，旧产物不可再作为当前任务依据。
- `cancelled`：用户终止；不得自动重试。

## 审批

审批是一份不可变的共享任务事实，位于 `approvals/<node-id>/r<node-revision>.yaml`；`task.yaml` 仅引用其路径。它必须绑定该 revision 的全部输出哈希：

```yaml
nodeId: clarify
nodeRevision: 1
artifactHashes:
  artifacts/brief.md: sha256:<hex>
  artifacts/questions.md: sha256:<hex>
  artifacts/acceptance.md: sha256:<hex>
decision: approved # approved | changes_requested
actor: jeffrey
at: 2026-08-12T12:00:00Z
note: 验收标准已补齐
```

只有 `awaiting_approval` 节点可接受审批。审批前，待审产物和该节点的 `awaiting_approval` 状态必须已经提交到当前 Git 分支；审批后，审批文件与状态变化也必须提交，Runner 才允许运行下游节点。`approved` 将节点转为 `completed`；`changes_requested` 将节点转为 `pending`，并创建下一次执行所需的修订说明。审批记录必须引用确切的 `nodeRevision`，不能批准已过期的产物。`changes_requested` 的 `note` 必填，写入 `revisions/<node-id>/r<node-revision + 1>.md`；该文件与审批记录、状态变化一起提交后，才可重新运行该节点。技能锁定在修改请求后保持不变，除非后续显式重新绑定。

MVP 记录的 `actor` 是 Git 协作中的声明性身份，不单独构成强身份认证。需要组织级审批可信度时，应由受保护分支、CODEOWNERS、签名提交或 Git 平台的 PR 审批提供保障；`aiw` 不伪造或替代这些机制。

## 依赖与失效传播

- 节点可运行的前提是所有 `dependsOn` 节点均为 `completed`。
- 一次节点成功运行会使其 `revision` 加一，并记录实际产物的哈希。
- 已完成节点的新 revision、来源快照刷新、技能重新绑定、或人工将节点退回修改时，编排器必须递归标记所有已开始的下游节点为 `invalidated`。
- `invalidated` 节点的旧产物只读保留，不能被自动注入。用户必须重新运行或明确取消该节点。
- 失效传播仅沿 DAG 出边进行；节点不能依赖自身或形成环。创建或更新任务时必须检测环。
- `test` 发现需要修改业务代码时，必须修订 `implement` 或更早的真实原因节点；不得仅修改测试报告后继续审批。

## 默认图的持久化约束

默认节点 ID、阶段顺序、产物与审批点以《研发工作流阶段规范》为唯一来源。`task init` 将该定义持久化为线性 DAG；`intake` 不调用 Agent。MVP 仅支持单 Agent、单节点串行运行，DAG 只表达顺序与阻塞关系，不表示并发调度。

未来可在 `implement` 范围内持久化多个依赖节点，例如 `schema`、`api`、`ui` 和 `migration`；这些节点全部完成后才能进入 `verify`。

## 命令触发的领域事件

CLI 是领域事件的调用入口；本规范只定义事件对共享任务事实和节点状态的影响。命令参数、输出、错误行为与调用示例以[CLI命令参考](../03-接入与接口/CLI命令参考.md)为准。

| 领域事件 | 任务事实与状态变化 |
|---|---|
| 初始化任务 | 原子创建固定七阶段 DAG、来源快照、工作流模板和六项节点技能锁定；来源快照成功后，`intake` 为 `completed`，`clarify` 评估为 `ready`。 |
| 重新绑定技能 | 记录旧、新技能锁定与原因；当前节点保持待执行，所有已开始下游节点进入 `invalidated`。 |
| 来源产生新 revision | 保留旧快照，更新 `intake` 当前输出，并递归使已开始的下游节点 `invalidated`；内容未变时不产生事件。 |
| 开始节点运行 | 已就绪节点由 `ready` 进入 `running`；预演运行不改变节点状态。 |
| 节点运行结束 | 成功节点进入 `completed`，默认需要审批的节点进入 `awaiting_approval`；失败或取消分别进入 `failed`、`cancelled`。 |
| 批准审批 | 当前 revision 的审批事实绑定全部产物哈希；节点由 `awaiting_approval` 进入 `completed`。 |
| 审批要求修改 | 写入 `changes_requested` 审批事实和下一 revision 的修改说明；当前节点进入 `pending`，所有已开始的下游节点进入 `invalidated`。 |
| 主动修订节点 | 非审批场景下将当前节点置为 `pending` 并写入修改说明；所有已开始的下游节点进入 `invalidated`；旧产物和历史事件保留。 |
| 查询任务 | 不改变任何任务事实或节点状态。 |

## 验证规则

解析时必须拒绝重复节点 ID、未知依赖、环、非法状态、缺少产物路径，以及任务根目录外的产物路径。默认任务必须有一份包含名称、版本、来源 revision 和哈希的工作流模板锁定，且所有可执行节点必须有技能名称、版本、来源 revision、技能哈希和全部方法论来源锁定；`intake` 不得有技能。默认任务必须包含七个固定节点、正确的线性依赖、阶段对应的产物路径和 `clarify`、`plan`、`test` 三个审批点。所有状态迁移、模板选择、技能重新绑定、审批、失效和运行结果都写入 `events`，以便复现。Runner 还必须拒绝使用未提交的上游产物、审批记录或任务模板/本节点技能锁定进入下游节点。
