# 任务模型规范

## 核心问题

本文回答：任务有哪些节点和状态，开发计划如何变成可执行开发单元。

## 任务事实

`task.yaml` 是任务状态的唯一权威来源，使用 `aiw.task/v3`。它记录：

- 任务 ID、仓库和整体状态；
- 锁定的工作流模板、阶段技能、方法来源和 Git revision；
- 来源引用；
- 节点、依赖、状态、输出路径和当前开发技能；
- 审批引用、事件和单调递增的 `stateVersion`。

技能和方法来源保留内容哈希，用于确认安装内容没有变化。任务产物本身不维护哈希链。

## 节点

初始节点固定为：

```text
intake → clarify → solution → plan
```

计划批准后，AIW 根据开发计划生成：

```text
development-unit-main-list-metrics
development-unit-main-list-export
development-unit-share-link-theme
```

每个名称由计划显式声明，格式为 `development-unit-<英文 kebab-case 描述>`。它同时作为 CLI 参数、任务节点 ID、单元上下文文件名和开发结果目录名；中文标题只用于展示。没有依赖的单元直接依赖 `plan`，有依赖的单元通过语义名称引用对应开发节点。只有全部依赖完成后才可执行。

## 节点状态

- `pending`：等待上游。
- `ready`：可以执行。
- `running`：正在执行。
- `awaiting_approval`：等待人工确认；当前只用于 `clarify` 和 `plan`。
- `completed`：节点当前结果完成。
- `failed`：最近一次运行失败，可直接重跑。
- `invalidated`：上游变化，需要重跑。
- `cancelled`：运行被取消。

## 整体状态

- `active`：仍有可推进或等待中的节点。
- `blocked`：没有可推进节点且存在失败或失效。
- `completed`：全部主干和开发节点完成；用户界面显示“开发完成”。
- `cancelled`：任务已取消。

## 重跑与失效

- `task run` 既用于首次执行也用于重跑。
- 重跑上游节点时，其下游当前结果失效。
- 重跑计划会移除旧计划生成的开发节点，并由新计划重新生成。
- 当前结果直接覆盖，不维护第几次执行或第几次审批的业务版本；运行目录仍保留每次执行诊断。

## 并发一致性

所有修改任务事实的命令使用同一任务锁。`stateVersion` 每次更新递增；写入前若版本已变化，拒绝旧状态覆盖新状态。
