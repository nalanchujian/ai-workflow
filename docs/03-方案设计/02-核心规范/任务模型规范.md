# 任务模型规范

## 核心问题

任务事实、业务单元、审批和重跑如何保持同一条可审计链？

`task.yaml` 是任务当前有效状态的索引；实际产物、决策、审批和运行证据保存在任务目录中，均应提交到业务仓库的 `.aiw/`。

## 任务目录

```text
.aiw/tasks/<task-id>/
  task.yaml                         # 当前节点图、当前 revision、来源与技能锁定
  task.md                           # 任务标识和来源说明
  sources/requirements/r<n>/        # 不可变需求快照与元数据
  artifacts/<node-id>/r<n>/         # 不可变的节点产物
  artifacts/clarify/r<n>/fact-register.yaml # 正式事实登记：事实类型、可信度和来源证据
  artifacts/work-units/r<n>/        # 由计划生成的单元上下文
  impact-graphs/plan-r<n>.yaml      # 来源 → 事实 → 决策 → AC → 交付单元的当前影响图
  handoffs/<node-id>/r<n>.yaml      # 结构化交接包
  approvals/<node-id>/r<n>.yaml     # 审批事实与产物哈希
  decisions/<decision-id>/r<n>.yaml # 人工确认的业务结论
  risk-acceptances/<node-id>/r<n>.yaml
  runs/<run-id>/                    # Prompt 清单、Diff、结果与运行证据
```

历史 revision 永不删除。`task.yaml` 只指定当前 revision；重跑、来源刷新或重新规划只切换当前指针，并使受影响下游节点失效。

`fact-register.yaml` 是需求事实的唯一结构化登记：每项事实标记为 `confirmed`、`inferred`、`unresolved` 或 `external_dependency`，并绑定来源快照与定位信息；`confirmed` 只能使用 `high` 可信度，其余类型不能伪装成高可信事实。`acceptance.yaml` 和 `decision-register.yaml` 分别以 `factRefs` 说明验收依据和待确认依据。计划获批时生成 `impact-graphs/plan-r<n>.yaml`，`task.yaml.impactGraph` 只指向当前有效图及其 SHA-256。

来源索引/领域分片仍是后续能力：完整快照目前负责追溯和澄清输入，超大来源尚未自动生成可选切片。

## 节点模型

固定主干节点为 `intake`、`clarify`、`solution`、`plan` 和内部锚点 `implement`。锚点只保存计划阶段锁定的交付技能，不直接面向用户执行。

计划获批后，系统生成业务节点：

```yaml
delivery-list-export:
  title: 主列表导出
  phase: implement                 # 内部执行阶段名；对用户展示为交付单元
  generatedFromPlanRevision: 1
  workUnitId: list-export
  verificationCommands: [pnpm test -- list-export]
  dependsOn: [plan]
  acceptanceRefs: [AC-02]
  decisionRefs: [DEC-EXPORT-01]
  outputs:
    - artifacts/delivery.md
    - artifacts/test-results.yaml
    - artifacts/acceptance-results.yaml
  requiresApproval: true
```

规则：

- 每个由计划生成的交付单元必须有至少一个 `acceptanceRefs`；
- 每个交付单元必须声明 `workUnitId`、`decisionRefs` 和至少一条 `verificationCommands`，并在影响图中与对应的事实、AC、决策和测试命令完全一致；
- 每个 AC 在 `work-breakdown.yaml.acceptanceCoverage` 中只能有一条处理声明；
- `implement`、`waiting_external` 的 AC 必须且只能归属一个交付单元；
- 跨单元验证用依赖其他单元的“集成交付单元”表达；
- `verify`、`test` 不是节点类型，也不存在全局汇合节点。

## 节点状态

`pending → ready → running → awaiting_approval → completed` 是正常路径。失败为 `failed`，取消为 `cancelled`，上游变更后为 `invalidated`，被新版计划替代的节点为 `superseded`。

`intake` 在任务创建时已完成。`clarify`、`plan` 和所有交付单元都需要人工留痕确认；MVP 不做身份鉴权，任何操作者均可执行确认命令，但操作者、时间、产物哈希和说明都会记录。

## 运行和审批完整性

运行前必须校验：

- 需求快照的当前 SHA-256 与 `task.yaml`、`meta.json` 一致；
- 依赖节点当前产物的 SHA-256 与成功运行和审批事实一致；
- 交付单元的 `workUnitId`、AC 和决策引用与当前 `impact-graphs/plan-r<n>.yaml` 一致；
- 所有作为下游依据的 `.aiw` 任务事实已提交 Git；
- 业务工作树能建立可信基线。

运行后保存允许范围、Git 基线、Diff、补丁、结果和上下文清单。交付单元中，Codex 只在 `delivery.md` 的“测试计划”声明测试 ID 与命令，并给出验收判断；AIW 会在 Codex 退出后作为唯一测试执行者运行已批准计划的 `verificationCommands`，将原始 stdout/stderr 写入 `runs/<run-id>/tests/`，并生成 `test-results.yaml`。每个 `passed` AC 必须引用其中退出码为 `0` 的测试 ID；审批时会同时校验测试记录、证据哈希、交付报告中的测试计划和验收结果。每个交付单元的 `acceptance-results.yaml` 只能包含该单元的 AC；普通审批要求这些 AC 全部 `passed`。存在 `failed` 或 `blocked` 时，只能修复重跑，或使用：

```bash
aiw task close-with-risk <task-id> <delivery-node-id> \
  --owner "<责任人>" --reason "<接受原因>" --expires-at "<ISO 时间>"
```

风险接受只关闭对应单元，并将任务交付状态标记为“风险已接受”。

## 决策和外部条件

`clarify` 必须先将输入划分为四类：已确认事实、推断、待确认疑问、外部依赖。只有已确认事实和已经记录人工结论的决策可作为后续方案依据；推断必须保留来源与可信度，疑问和外部依赖必须进入决策登记或阻塞关联单元。

每个决策只能对应一个独立业务结论和一个 AC。用户通过 `task review` 逐项选择“本期继续”或“等待外部条件”；前者可选 AI 推荐或人工结论。

外部条件解除分为两类：

- `execution-only`：只恢复执行时机，方案、计划和验收不变，可直接解锁受影响单元；
- `replan`：新增接口、规则、字段口径或权限事实。必须记录结构化事实，随后使 `solution`、`plan` 和所有下游交付单元失效，重新生成后才可执行。

任务图记录来源、事实、决策、AC 与交付单元之间的影响边，并由 SHA-256 绑定到当前计划。`execution-only` 仅解除显式阻塞的单元；任何新增接口、规则、字段口径或权限事实都属于 `replan`，必须保守地从 `solution` 重新规划。来源刷新同样先重新澄清，因为当前快照尚未具备可安全比较的领域级变更片段；不得仅凭图上的候选单元静默放行旧方案。

## 重跑规则

所有非 `intake` 节点都使用 `aiw task run` 重跑。已完成或待审批节点重跑会创建新 revision，不覆盖历史内容；当前节点和下游当前版本失效。来源变化不允许直接编辑下游产物，只能通过 `task source refresh` 触发。
