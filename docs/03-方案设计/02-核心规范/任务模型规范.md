# 任务模型规范（v2）

## 目的

任务模型将一个复杂需求表示为 Git 共享、可追溯的有向无环图（DAG）。它负责子任务依赖、审批、重试与上游变更后的下游失效；不负责定义通用研发方法或调用 Agent。

默认节点、阶段产物、审批点和最小上下文以[研发工作流阶段规范](研发工作流阶段规范.md)为准；本规范定义其在任务状态机中的持久化和执行约束。

## 存储位置

每个任务位于业务仓库根目录的 `.aiw/tasks/<task-id>/task.yaml`。`.aiw/config.yaml`、任务来源、阶段产物、审批记录和运行清单均为**共享任务事实**：必须纳入 Git，供任务发起者、审批人和后续执行者在同一分支上审阅。

`task-id` 由 `task init` 以 UTC 日期时间自动生成，格式为 `task-YYYYMMDD-HHmmss-SSS`，必须匹配 `[a-z][a-z0-9-]{1,63}` 并在仓库内唯一；调用者不能手动指定。共享 `task.yaml` 中的 `repository` 固定为相对值 `.`，不得写入创建者机器的绝对路径。技能缓存、完整 Agent 输出、临时提示词与会话运行态只保存在用户目录的 `~/.aiw/`，不得写入共享任务目录。

```yaml
schemaVersion: aiw.task/v2
id: task-20260813-120000-000
title: 实现退款功能
repository: .
status: active # active | partially_blocked | blocked | completed | cancelled
deliveryStatus: not_assessed # not_assessed | ready | not_ready | risk_accepted
skillProfile:
  name: standard-web-feature
  version: 1.0.0
  registrySource:
    url: git@github.com:your-org/agent-skills.git
    revision: a1b2c3d4
  sha256: <profile-yaml-sha256>
nodes:
  intake:
    title: 接入资料
    phase: intake
    dependsOn: []
    status: completed
    revision: 1
    outputs: [sources/requirements/r1/snapshot.md, sources/requirements/r1/meta.json]
  clarify:
    title: 澄清需求
    phase: clarify
    dependsOn: [intake]
    skill: # 由 skillProfile 在初始化时锁定
      name: requirements-clarification
      version: 1.0.0
      registrySource: {url: git@github.com:your-org/agent-skills.git, revision: a1b2c3d4}
      sha256: <skill-md-sha256>
      methodSources:
        - id: superpowers:brainstorming
          source: bundled:superpowers
          version: 6.2.0
          revision: 6.2.0
          sha256: <method-skill-md-sha256>
    requiresApproval: true
    status: ready
    revision: 0
    outputs: [artifacts/brief.md, artifacts/questions.md, artifacts/acceptance.md, artifacts/acceptance.yaml, artifacts/decision-register.yaml]
# solution、plan、implement、verify、test 均省略；它们各自拥有与 clarify 相同结构的完整技能锁定。
approvalRefs: []
decisions: []
events: []
```

节点的 `outputs` 继续声明其完整 Markdown/YAML 工作产物。每次非 `intake` 节点运行还隐式声明一个版本化输出 `handoffs/<node-id>/r<node-revision + 1>.yaml`；成功后节点 revision 递增，该 Handoff 与普通产物哈希一起记录在 `succeed` 事件中。`intake` 初始化完成时原生写入 `handoffs/intake/r1.yaml`。

## 工作流模板与技能锁定

`task init` 必须一次选择并锁定整个任务的六阶段方法链。调用者可显式传入 `--skill-profile <name[@version]>`，省略时使用本机默认模板；它将工作流模板以及 `clarify` 至 `test` 的精确技能锁定写入 `task.yaml`。后续 `task run <task-id> <node-id>` 直接使用该节点锁定的技能。这样“本次任务采用何种方法”与实际执行一样，是可审阅的 Git 事实，而不是某台机器上当时恰好安装的最新技能。

节点锁定的最小结构如下：

```yaml
skill:
  name: requirements-clarification
  version: 1.0.0
  registrySource:
    url: git@github.com:your-org/agent-skills.git
    revision: a1b2c3d4
  sha256: <skill-md-sha256>
  methodSources:
    - id: superpowers:brainstorming
      source: bundled:superpowers
      version: 6.2.0
      revision: 6.2.0
      sha256: <method-skill-md-sha256>
```

- `task run` 不接收技能参数，只按节点锁定的 Git revision、技能哈希和方法论哈希读取内容。
- 本机 Registry、Superpowers Profile 或任一哈希不再匹配节点锁定时，Runner 必须拒绝运行；不得自动升级或选择替代技能。

## 节点状态

`status` 只描述流程是否可推进；`deliveryStatus` 单独描述交付是否满足验收，避免将“流程已闭环”误写成“可发布”。审批决定单独保存在 `approvals` 中，避免将 `approved` 与 `completed` 混为一谈。

```text
pending → ready → running → awaiting_approval → completed
                  │                 │
                  ├→ failed         ├→ pending → ready  (依赖满足时自动重新评估)
                  └→ cancelled ───→ running（再次执行同一 `task run`）
                                      └→ completed (approved)

任意节点 → invalidated（已使用的上游 revision 改变）
invalidated → pending → ready（重新规划或确认后，依赖满足时自动重新评估）
blocked → pending | ready（关联决策被解决或豁免）
blocked → superseded（关联决策被拆期）
```

- `pending`：依赖、人工输入或规划尚未满足；依赖满足后由状态机重新评估。
- `blocked`：节点依赖某个明确记录的决策；只阻塞该节点及其汇合下游，不阻塞无关工作单元。
- `ready`：所有依赖均为 `completed`，可开始执行。
- `running`：Runner 已启动一次 Agent 调用。
- `awaiting_approval`：节点已产出结果，等待人工决定。
- `completed`：节点已成功结束；若要求审批，则已经批准。
- `failed`：Agent 调用或产物校验失败；保留错误信息与运行记录。
- `invalidated`：上游输出发生新 revision，旧产物不可再作为当前任务依据。
- `cancelled`：用户终止；保留取消原因、日志和变更证据。提交取消记录后，可使用相同的 `task run` 重新执行该非 `intake` 节点；重跑会覆盖该节点及下游的当前任务产物，但不会删除历史运行记录。
- `superseded`：旧计划自动生成的实施子任务已被新版计划替代；保留其产物与事件用于审计，但不再阻塞当前任务图。

## 决策与交付状态

`clarify` 必须同时生成 `artifacts/acceptance.md` 与 `artifacts/acceptance.yaml`。后者使用 `aiw.acceptance-catalog/v1`，列出本期全部 AC 的 ID、标题和可验证描述，是计划与测试逐项对账的唯一机器可读来源。`clarify` 还必须生成 `artifacts/decision-register.yaml`。它只保存 AI 提出的决策问题、选项、取舍、推荐与选项的明确处理结果；人工实际选择以不可变事实 `decisions/<decision-id>/r<revision>.yaml` 保存，并在 `task.yaml.decisions` 留下当前索引。选项的 `effect` 只能是 `resolved`、`waiting_external`、`deferred` 或 `waived`，`task review` 必须按该声明写入状态，不能根据选项名称猜测。这样建议可修订，选择也可追溯。

每个决策项必须关联验收项和实施工作单元。计划使用 `work-breakdown.yaml.units[].blockedBy` 引用决策 ID：`proposed` 或 `waiting_external` 使对应单元成为 `blocked`；`resolved` 或 `waived` 解锁该单元；`deferred` 将该单元标为 `superseded` 并从验证汇合边移除。`work-breakdown.yaml.acceptanceCoverage` 必须为验收清单中的每个 AC 声明唯一去向：本期实施需关联引用该 AC 的工作单元；外部等待需关联当前等待决策和被阻塞单元；拆期或风险豁免需关联带说明的同状态决策。计划审批会校验这份对账，遗漏或不一致时不得生成实施图。决策命令不修改无关节点。

`test` 还必须生成 `artifacts/acceptance-results.yaml`。只有全部验收项为 `passed`、`deferred` 或 `waived` 时，普通 `task approve ... test` 才能将 `deliveryStatus` 置为 `ready`。存在 `failed` 或 `blocked` 项时，普通审批必须拒绝；若业务明确接受风险，只能用 `task close-with-risk` 写入 `risk-acceptances/test/r<revision>.yaml`，状态为 `risk_accepted`。流程状态 `completed` 仅表示节点图已闭环，不表示不存在风险。

## 审批

审批是一份不可变的共享任务事实，位于 `approvals/<node-id>/r<node-revision>.yaml`；`task.yaml` 仅引用其路径。它必须绑定该 revision 的全部输出哈希：

```yaml
nodeId: clarify
nodeRevision: 1
artifactHashes:
  artifacts/brief.md: sha256:<hex>
  artifacts/questions.md: sha256:<hex>
  artifacts/acceptance.md: sha256:<hex>
  artifacts/acceptance.yaml: sha256:<hex>
decision: approved
actor: jeffrey
at: 2026-08-12T12:00:00Z
note: 验收标准已补齐
```

新版本任务的 `artifactHashes` 还必须包含对应 `handoffs/<node-id>/r<node-revision>.yaml` 的哈希；审批人批准的是完整工作产物和结构化交接包的同一 revision。

只有 `awaiting_approval` 节点可接受审批。审批前，待审产物和该节点的 `awaiting_approval` 状态必须已经提交到当前 Git 分支；审批后，审批文件与状态变化也必须提交，Runner 才允许运行下游节点。审批只接受当前产物，不提供“要求修改”分支；需要改变结论时必须更新需求来源，或在 `clarify` 的决策确认中形成新的事实，再从来源刷新后的 `clarify` 重跑。审批记录必须引用确切的 `nodeRevision`，不能批准已过期的产物。

MVP 记录的 `actor` 是 Git 协作中的声明性身份，不单独构成强身份认证。需要组织级审批可信度时，应由受保护分支、CODEOWNERS、签名提交或 Git 平台的 PR 审批提供保障；`aiw` 不伪造或替代这些机制。

## 依赖与失效传播

- 节点可运行的前提是所有 `dependsOn` 节点均为 `completed`。
- 一次节点成功运行会使其 `revision` 加一，并记录实际产物的哈希。
- 来源快照刷新时，编排器保留旧产物并短暂标记受影响下游为 `invalidated`，随后将它们重新排队；首个受影响节点在依赖满足后变为 `ready`。
- `invalidated` 节点的旧产物只读保留，不能被自动注入；它不是人工修订入口。
- 失效传播仅沿 DAG 出边进行；节点不能依赖自身或形成环。创建或更新任务时必须检测环。
- `test` 发现需求或范围问题时，必须更新原始需求并刷新来源；不得仅修改测试报告、方案或实现产物后继续审批。

## 默认图的持久化约束

默认节点 ID、阶段顺序、产物与审批点以《研发工作流阶段规范》为唯一来源。`task init` 将该定义持久化为线性主干；`intake` 不调用 Agent。计划审批先校验 `acceptanceCoverage` 覆盖全部验收项，再解析 `work-breakdown.yaml`：一个工作单元复用 `implement`；多个工作单元自动生成 `implement-*` 节点、每单元 `allowedPaths`、上下文摘要和依赖边，并让 `verify` 汇合等待全部当前单元。工作单元只由计划自动生成。来源刷新后，新图从新的澄清与计划结果重新生成；旧决策和审批文件仅保留为历史记录，`task.yaml` 的当前决策与审批引用必须清空，避免新来源沿用旧结论。DAG 因此表达并行可行性和汇合阻塞；MVP Runner 仍一次只运行一个节点，以避免同一任务事实被并发写入。Runner 在本机运行目录按任务取得文件锁；同一任务已有运行时，新的运行或预演必须失败，不得等待、抢占或并发写入任务事实。

如果 AIW 进程异常退出，陈旧执行锁可被回收；锁回收后的首次运行若发现节点仍为 `running`，必须自动转为 `failed` 并记录失败原因，而不是永久阻塞。提交失败证据后，用户可直接再次执行同一 `task run`；新运行使用新 `runId`，不会覆盖旧证据。

例如可在 `implement` 范围内持久化 `schema`、`api`、`ui` 和 `migration` 子节点；`verify` 显式依赖这些叶子，只有全部完成后才能进入验证。

## 命令触发的领域事件

CLI 是领域事件的调用入口；本规范只定义事件对共享任务事实和节点状态的影响。命令参数、输出、错误行为与调用示例以[CLI命令参考](../03-接入与接口/CLI命令参考.md)为准。

| 领域事件 | 任务事实与状态变化 |
|---|---|
| 初始化任务 | 原子创建固定七阶段 DAG、来源快照、工作流模板和六项节点技能锁定；来源快照成功后，`intake` 为 `completed`，`clarify` 评估为 `ready`。 |
| 重新绑定技能 | 记录旧、新技能锁定与原因；当前节点保持待执行，所有已开始下游节点进入 `invalidated`。 |
| 新增实施子任务 | 写入实施子节点、其依赖和汇合边；节点继承任务已锁定的实施技能，可独立设置审批；汇合节点保持等待直到新叶子完成。 |
| 来源产生新 revision | 保留旧快照，更新 `intake` 当前输出；受影响下游重新排队，`clarify` 在依赖满足后进入 `ready`；内容未变时不产生事件。 |
| 开始节点运行 | 已就绪、已失败、已取消、已完成或待审批的非 `intake` 节点进入 `running`；已取消、已完成或待审批属于覆盖式重跑，先清除当前节点及下游的有效产物、审批和状态。预演运行不改变节点状态。 |
| 节点运行结束 | 成功节点先校验完整工作产物和对应 revision 的结构化交接包，再进入 `completed`；默认需要审批的节点进入 `awaiting_approval`；失败或取消分别进入 `failed`、`cancelled`。 |
| 批准计划 | 当前 revision 的审批事实绑定全部产物哈希；`plan` 由 `awaiting_approval` 进入 `completed`，AIW 校验工作单元声明、生成实施摘要并自动物化当前实施 DAG。 |
| 选择决策 | 将 AI 推荐、人工选项、责任人或拆期说明写为不可变决策事实；只重新评估该决策关联的工作单元。 |
| 风险关闭测试 | 对未通过或阻塞验收项记录责任人、原因和到期时间；测试节点闭环但交付状态为 `risk_accepted`。 |
| 迁移历史 Handoff | 仅为已完成节点补齐对应 revision 的 Handoff 与迁移审计记录；不重跑节点、不改变节点状态、revision 或既有审批。 |
| 查询任务 | 不改变任何任务事实或节点状态。 |

## 验证规则

解析时必须拒绝重复节点 ID、未知依赖、环、非法状态、缺少产物路径，以及任务根目录外的产物路径。默认任务必须有一份包含名称、版本、来源 revision 和哈希的工作流模板锁定，且所有可执行节点必须有技能名称、版本、来源 revision、技能哈希和全部方法论来源锁定；`intake` 不得有技能。默认任务必须包含七个固定节点、正确的线性依赖、阶段对应的产物路径和 `clarify`、`plan`、`test` 三个审批点。所有状态迁移、模板选择、技能重新绑定、审批、失效、运行结果和历史 Handoff 迁移都写入 `events`，以便复现；迁移不改变节点状态、revision 或审批决定。Runner 还必须拒绝使用未提交的上游产物、审批记录或任务模板/本节点技能锁定进入下游节点。
