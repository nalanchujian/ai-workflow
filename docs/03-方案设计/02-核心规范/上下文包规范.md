# 上下文规范

## 核心问题

本文回答：每次独立 Codex 会话读取哪些内容，如何控制上下文大小。

## 原则

- 每次 `task run` 都是独立 Codex 会话。
- AIW 自己组合上下文，不依赖上一轮聊天记录或 Codex 自动压缩。
- 默认只注入当前节点直接需要的事实。
- 完整历史产物保留在 `.aiw/` 供追溯，但不默认拼接进后续上下文。
- 不生成通用 `handoff.yaml`。

## 各节点默认上下文

- `clarify`：来源快照。
- `solution`：事实登记、已确认本期决策。
- `plan`：技术方案，只负责拆分开发单元，不读取或分配设计图片。
- `design-analysis`：已批准的开发计划、开发单元清单和用户提供的全部本地设计图片；图片通过 `--image` 传入。
- `development-unit-*`：当前开发单元 YAML；AIW 通过 `--image` 只注入设计节点绑定给该单元的截图，不注入其他单元图片。

此外统一注入：

- 当前阶段技能；
- 该技能实际引用的 Superpowers 方法；
- 运行安全约束；
- 由 AIW Schema 生成的产物协议和暂存输出路径。

YAML 示例由程序序列化，文本值使用引号，避免“冒号 + 空格”被误读为键值对象。`plan` 额外注入针对本次暂存文件的只读格式校验命令；它直接使用 AIW 内置 Schema，不依赖业务仓库安装校验工具，也不新增用户操作步骤。最终接收产物时仍再次校验。

## 额外上下文

用户可通过 `task run --include <path>` 注入项目内文件。路径必须在项目中，不能越界或通过符号链接逃逸。

## 预算

默认上限由本机配置 `context.maxTokens` 控制，默认 `20000`。运行前按来源、任务事实、技能、方法和运行开销分别估算。超预算时停止并显示构成，不静默截断关键事实。

开发计划应通过拆分单元降低开发节点上下文，而不是把完整需求、方案和全部代码一次性注入。

## 存储边界

- 业务仓库 `.aiw/` 保存来源和阶段产物。
- 本机运行目录保存完整提示词、日志、上下文清单和临时工作区。
- 共享结果不得包含凭据、完整环境变量或本机绝对敏感路径。
