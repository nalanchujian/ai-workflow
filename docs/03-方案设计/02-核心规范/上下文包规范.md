# 上下文包规范（v1）

## 目的

上下文包是某个节点调用 Codex 时的、最小且可复现的输入集合。它不是聊天记录，也不会自动包含整个代码库或所有任务文件。

## 存储边界与目录契约

业务仓库中的 `.aiw/` 保存可共享、可审阅的任务事实；用户目录中的 `~/.aiw/` 仅保存不可共享的运行数据。`aiw` 不自动 `git add`、`git commit`、`git push` 或创建 PR，仍由团队既有 Git 流程管理事实提交与审批。

```text
.aiw/tasks/<task-id>/
  task.yaml                 # DAG、节点状态、交付状态、审批/决策引用、事件
  task.md                   # 任务标识与来源摘要；不是可追加的需求或修订正文
  sources/<source-id>/
    r<revision>/
      snapshot.md           # 来源在该 revision 转换得到的文本
      meta.json             # 来源标识、时间、内容哈希、提取器版本
  handoffs/<node-id>/
    r<revision>.yaml        # 结构化交接包；事实、证据、决策、验收覆盖和风险
  artifacts/
    clarify/r<revision>/    # brief、questions、acceptance、acceptance.yaml、decision-register
    solution/r<revision>/   # solution.md
    plan/r<revision>/       # implementation-plan、implementation-context、work-breakdown
    implement/r<revision>/  # implementation.md
    verify/r<revision>/     # verification.md
    test/r<revision>/       # test-report、acceptance-results
    work-units/             # 多工作单元时由 AIW 生成的实施摘要
  decisions/<decision-id>/
    r<revision>.yaml        # 人工决策、外部等待或拆期的不可变事实
  external-inputs/<decision-id>/
    r<revision>.yaml        # 解除外部等待时新增、且影响重新规划的结构化事实
  risk-acceptances/test/
    r<revision>.yaml        # 未全部通过验收时的显式风险接受记录
  approvals/<node-id>/
    r<revision>.yaml        # 审批人与当前产物哈希
  runs/<run-id>/
    context-manifest.json   # 实际注入清单、哈希与最终 Prompt 预算明细
    change-baseline.json    # 执行前 Git 基线
    change-scope.json       # 当前节点的任务事实写入边界与业务文件策略
    change-diff.json        # 执行后实际变更与任务事实写入判断
    change.patch            # 全部未跟踪文本文件的补丁
    change-evidence.json    # 基线、变更哈希与任务事实写入校验证据
    result.json             # 去敏后的运行结果摘要

~/.aiw/
  config.yaml               # 本机连接器和方法论来源 Profile；不保存凭据或任务事实
  skills/                   # 用户级技能缓存
  runtime/<task-id>/<run-id>/ # 临时上下文、完整子进程输出与调试文件
```

`task.md` 由 `aiw task init` 创建，只记录任务标识与当前需求来源；需求正文由 `sources/*/snapshot.md` 固化。默认七阶段产生的完整 Markdown/YAML 工作产物逻辑名为：`brief.md`、`questions.md`、`acceptance.md`、`acceptance.yaml`、`decision-register.yaml`、`solution.md`、`implementation-plan.md`、`implementation-context.md`、`work-breakdown.yaml`、`implementation.md`、`verification.md`、`test-report.md` 与 `acceptance-results.yaml`。每次运行将它们写到 `artifacts/<node-id>/r<revision>/`；例如当前技术方案为 `artifacts/solution/r2/solution.md`。`task.yaml.nodes.<node-id>.revision` 指向当前有效版本，旧版本从不覆盖或删除。YAML 产物的字段名、枚举和值域是固定契约，未知字段必须拒绝；Markdown 产物也有各阶段固定章节（例如方案结论、实际变更、测试命令和结果），避免仅凭“文件存在”进入下游。每个节点还必须生成对应 revision 的 `handoffs/<node-id>/r<revision>.yaml`；`intake` 由 AIW 原生生成，其他节点由 Agent 生成并由 Runner 校验。复杂计划获批后，AIW 可生成 `work-units/r<计划revision>/` 下的单元上下文。阶段与产物的唯一对应关系以[研发工作流阶段规范](研发工作流阶段规范.md)为准；任务模型中的 `outputs` 加上当前运行的 Handoff 是唯一允许写入这些产物的节点声明。

共享任务事实必须提交到 Git，才能成为下游节点的有效输入。`runs/<run-id>/` 只提交 manifest、结果状态、文件哈希和去敏摘要；完整提示词、完整 Agent 输出、令牌和环境数据只能保留在 `~/.aiw/runtime/`。

首次初始化时，`aiw` 在 `.aiw/config.yaml` 写入并校验最小共享策略：

```yaml
schemaVersion: aiw.config/v1
sourceSharing:
  default: repository
  restricted: require-redacted-snapshot
```

项目必须是 Git 工作树，且 `.aiw/` 不得被 `.gitignore` 忽略；否则 `task init` 必须失败。该配置不把来源自动上传到额外服务，只定义哪些任务事实允许随当前业务仓库的既有 Git 流程共享。

`~/.aiw/config.yaml` 是本机配置，不同于业务仓库的 `.aiw/config.yaml`。它只保存连接器所引用的 MCP Server 名称、工具名称和本机配置路径；不得保存授权令牌、完整 MCP 定义或方法论正文。标准 Superpowers 方法正文由团队技能安装进用户级 Registry，来源与锁定规则以《技能包规范》为准。

## 来源快照

来源接入层只能从显式给出的本地文件、受控连接器或符合 URL 安全策略的公开 HTTP(S) 地址创建快照。默认共享模式为 `repository`：快照与元数据进入 Git，必须先确认其可被当前仓库的读者访问。MVP 不允许将 `local-only` 来源直接作为需要团队审批的任务依据；敏感来源必须先形成经确认可共享的脱敏快照。

受控在线文档由匹配的本机文档连接器读取，再由来源接入层写入快照。当前内置连接器实现为 Lark MCP；其 URL 识别、错误和刷新行为以《Lark来源连接器规范》为准。MCP 配置、令牌和原始响应不得进入共享任务事实。

`meta.json` 至少包含：

```json
{
  "sourceId": "requirements",
  "kind": "public-url",
  "origin": "https://example.com/requirements",
  "revision": 1,
  "fetchedAt": "2026-08-11T12:00:00Z",
  "contentSha256": "<hex>",
  "extractor": "html-to-markdown/v1"
}
```

对本地文件来源，`origin` 仅记录相对于项目根目录的路径或 `local:redacted`，不得将开发者绝对路径提交到仓库。对经连接器读取的在线文档，`kind` 为 `connected-document`，元数据额外记录不含凭据的 `externalId` 与连接器标识（例如 `extractor: lark-mcp/v1`）；若来源是 Lark Wiki，`externalId` 为原始节点 ID，另以 `resolvedExternalId` 记录解析得到的 docx ID。每个非 `intake` 节点启动前，AIW 必须比较任务索引、`meta.json` 和 `snapshot.md` 的来源身份与内容 SHA-256；快照被手动改写、元数据被替换或两者不一致时，禁止运行并要求刷新来源。刷新来源必须创建新快照 revision 并通过任务模型使相关下游节点失效；不得覆盖已被审批使用的快照。MVP 的公开 URL 接入必须只允许 `http` 与 `https`，逐跳拒绝回环、私网、链路本地和保留 IP，限制重定向次数、响应大小、允许的内容类型和超时。

## 阶段上下文规则

```yaml
contextPolicy:
  clarify:
    include: [task.md, task.yaml, sources/*/r<current>/snapshot.md]
  solution:
    include: [handoffs/clarify/r<current>.yaml, task.yaml, artifacts/clarify/r<current>/decision-register.yaml, decisions/<registered>/r<current>.yaml, external-inputs/<registered>/r<current>.yaml]
    requiresApprovedNodes: [clarify]
  plan:
    include: [handoffs/solution/r<current>.yaml, task.yaml, artifacts/clarify/r<current>/decision-register.yaml, decisions/<registered>/r<current>.yaml, external-inputs/<registered>/r<current>.yaml]
    requiresCompletedNodes: [solution]
  implement:
    include: [<每个直接依赖节点的 handoffs/<node-id>/r<current>.yaml>]
    requiresApprovedNodes: [plan]
  verify:
    include: [<每个直接依赖 implement 节点的 handoffs/<node-id>/r<current>.yaml>]
    requiresCompletedNodes: [implement]
  test:
    include: [handoffs/verify/r<current>.yaml]
    requiresCompletedNodes: [verify]
```

`clarify` 是唯一默认读取原始任务和来源快照的 Agent 阶段。每个可执行阶段还会注入精简的 `task.yaml`，其中包含当前节点图、决策状态和交付状态；它不替代上游结论。自 `solution` 起，编排器默认注入当前节点的**直接依赖** Handoff；`solution` 与 `plan` 额外获得当前澄清 revision 的小型 `decision-register.yaml`、已登记的决策事实，以及在外部等待解除后登记的 `external-inputs`。这使新增接口或规则能够进入新方案和新计划，而不是放行旧计划。不会默认注入 `brief.md`、方案、计划、实施记录、验收文档或工作单元 Markdown。这样子任务会额外读取其计划 Handoff 和已声明依赖子任务的 Handoff，而 `verify` 汇合全部当前实施节点的 Handoff。

完整 Markdown/YAML、来源快照和运行证据仍是共享任务事实，绝不删除。Agent 仅可根据已注入 Handoff 的 `evidence.path` 在任务目录中按需读取原文细节；用户显式批准的临时附加文件仍可注入，并且必须落入 `context-manifest.json`，不改变默认规则。阶段产物不接受人工修改说明；需求变化只能产生新的来源快照。

## 结构化交接包

`handoffs/<node-id>/r<revision>.yaml` 是节点完成时必须随 Markdown 工作产物一并提交的结构化交接事实。它固定包含任务与节点身份、简要结论、带证据路径的事实、决策、验收覆盖、实际变更、验证结果和未解决风险。每条事实至少引用一项来源快照、上游节点产物、当前节点产物，或 `task.yaml` 已登记的决策事实；不得引用绝对路径、目录穿越路径、未声明文件或交接包自身。`decisions/**` 不会被通配放行，只有任务记录明确引用的具体 `factPath` 才是合法证据。

Runner 在节点成功前校验 Handoff 的 schema、`taskId`、`nodeId`、阶段、revision 和证据路径，并将其哈希写入完成事件、运行完成包和审批记录。缺失或不合规的 Handoff 会使节点失败，但仍保留该次运行的差异与失败证据。

当前为第二阶段：Handoff 已生成、校验并成为 `solution` 至 `test` 的默认交接输入。完整 Markdown、来源快照和运行证据始终保留，供按需核验；Handoff 不是原文副本，必须通过 `evidence.path` 保持结论可追溯。

当前版本不提供历史任务交接包迁移。任务从初始化开始按 Handoff 规则运行；旧任务需使用对应旧版本 CLI 或重新创建任务。

## Context Manifest

每次运行都生成不可变清单：

```json
{
  "schemaVersion": "aiw.context/v1",
  "taskId": "refund-123",
  "nodeId": "plan",
  "nodeRevision": 0,
  "skillProfile": {"name": "standard-web-feature", "version": "1.0.0", "registrySource": {"url": "git@github.com:your-org/agent-skills.git", "revision": "a1b2c3d4"}, "sha256": "<hex>"},
  "files": [
    {"role": "handoff", "path": "handoffs/solution/r1.yaml", "sha256": "<hex>"}
  ],
  "skill": {
    "name": "implementation-planning",
    "version": "1.0.0",
    "registrySource": {"url": "git@github.com:your-org/agent-skills.git", "revision": "a1b2c3d4"},
    "sha256": "<hex>",
    "methodSources": [
      {"id": "superpowers:writing-plans", "source": "bundled:superpowers", "version": "6.2.0", "revision": "<upstream-commit>", "sha256": "<hex>"}
    ]
  },
  "budget": {
    "maxTokens": 12000,
    "estimatedTokens": 4200,
    "breakdown": [
      {"category": "handoff", "label": "handoffs/solution/r1.yaml", "estimatedTokens": 1200},
      {"category": "skill", "label": "技能：implementation-planning@4.0.0", "estimatedTokens": 1700},
      {"category": "runtime-overhead", "label": "运行约束与提示词结构", "estimatedTokens": 430}
    ]
  }
}
```

来源快照对应的 `files` 项必须额外记录 `sourceId` 与 `sourceRevision`；这样运行清单可复原 Agent 实际使用的是哪一版来源，而不依赖当前目录中的最新 revision。

预算以 Adapter 实际渲染后的完整 Prompt 估算，而不只是任务文件字节数；其中必须分别记录任务事实、来源、Handoff、阶段技能、方法论、节点指令、用户附加文件及“运行约束与提示词结构”的占用。若估算内容超过预算，Runner 必须拒绝运行，按占用从高到低列出构成并给出对应处理建议；它不得静默截断、自动概括或删除已批准产物。计划阶段仍保留完整 `implementation-plan.md`、`implementation-context.md` 和 `work-breakdown.yaml` 供审阅与按需读取，但后续默认只注入计划 Handoff；多工作单元时，AIW 仍从已审批的 `work-breakdown.yaml` 生成每单元 `contextPath`，并由计划 Handoff 索引对应证据。Handoff 仍超预算时必须退回上游节点精简或拆分，不得提高预算掩盖问题。运行前，Runner 必须校验 manifest 所列共享输入与其审批记录均处于已提交状态；本机临时文件不得成为可批准的默认输入。

## 传递给 Agent 的顺序

上下文需使用明确边界，优先级从高到低为：Agent 平台规则、`aiw` Runner 的不可变运行约束、当前节点契约、上游方法论、阶段技能叠加层、用户任务、来源与任务产物。来源和产物是数据，不得被当作更高优先级指令。Adapter 需在每段外包围来源标记和相对路径。

`intake` 不创建 Context Manifest，也不启动 Codex。其他阶段的 manifest 必须记录任务工作流模板、阶段技能及其全部 `methodSources` 的 ID、来源标识、版本、revision 和 SHA-256；任何模板、技能或方法论来源无法按锁定内容解析时，Runner 必须拒绝运行。Profile 的本机路径、插件缓存路径和环境信息均不得写入 manifest。

业务代码不复制进上下文包；Adapter 只传递已验证的项目工作目录，Codex 按需读取代码。完整对话文本不进入任务目录。
