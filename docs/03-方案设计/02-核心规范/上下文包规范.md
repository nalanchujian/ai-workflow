# 上下文包规范

## 核心问题

如何既保留完整事实供追溯，又避免在后续节点不断叠加 Markdown，最终超过上下文预算？

AIW 将“任务事实存储”和“单次运行注入”分开：完整产物始终保存在 `.aiw/`；默认只注入结构化 Handoff、当前单元上下文和必要的直接依赖。对大需求，先缩小来源范围，再缩小业务单元；不能靠删减关键事实换取可运行。

## 来源索引与领域切片

来源快照是审计原件，不等于每次都要注入的上下文。MVP 的目标是让接入阶段额外生成来源索引：章节、领域、可追溯片段和摘要之间的映射。

```text
完整来源快照（审计原件）
  → 章节/领域索引（定位入口）
  → 当前澄清或单元需要的来源片段
  → Handoff 中的事实与 evidence.path
```

规则：

- `clarify` 只读取当前任务所选的章节或领域片段；跨领域事实必须显式列为依赖；
- 原文、表格、图片说明等完整材料仍保留在快照中，只能根据索引或 `evidence.path` 按需读取；
- 任何摘要都必须能回链到快照片段，不能成为新的无来源事实；
- 来源规模超过澄清预算时，先要求切片或缩小任务范围，不能直接把全文注入。

## 默认注入规则

| 当前节点 | 默认输入 |
|---|---|
| `clarify` | `task.md`、当前需求快照、精简 `task.yaml` |
| `solution` | `clarify` Handoff、事实登记、验收清单、已确认决策事实 |
| `plan` | `solution` Handoff、事实登记、验收清单、已确认决策事实 |
| `delivery-<unit>` | `plan` Handoff、当前单元上下文、该单元引用的决策事实、直接依赖交付单元 Handoff |

默认不注入完整需求正文、完整 `task.yaml`、`brief.md`、`solution.md`、`implementation-plan.md`、候选 `decision-register.yaml`、历史交付报告、全量测试报告或其他非依赖单元的 Markdown。下游只读取已确认的 `decisions/<DEC-id>/r<n>.yaml`，不再重复读取决策候选项；完整文件仍保留在任务事实中，供追溯和按需定位。

## Handoff

除 `intake` 外，每个节点运行必须生成：

```text
handoffs/<node-id>/r<revision>.yaml
```

Handoff 固定包含：

- `summary`：本节点可供下游使用的结论；
- `facts`：对正式事实登记的简明投影。每项必须复用 `fact-register.yaml` 中已有的 `FACT-*` ID，不能在 Handoff 自行创造事实；
- `decisions`：已确认业务结论的简明投影。每项必须携带已登记的 `DEC-*` ID，并在 `evidence` 中引用对应当前 `decisions/<DEC-id>/r<n>.yaml`；待确认的候选方案只保留在 `decision-register.yaml`，不得写入 Handoff；
- `acceptance`：相关 AC 的当前覆盖状态；
- `changes`：业务代码变更摘要；
- `verification`：已执行命令、结果和证据；
- `openRisks`：尚未关闭的风险。

Handoff 不得复制完整 Markdown，也不得引用未声明或未提交的证据。AIW 在运行前校验证据范围、`FACT-*`/`DEC-*` 的正式身份和当前 revision。`intake` 没有正式事实登记时，仅记录来源快照的 `FACT-SOURCE-*` 操作事实；它不能替代后续澄清产生的业务事实。

## 单元上下文

计划批准后，AIW 根据 `work-breakdown.yaml` 生成：

```text
artifacts/work-units/r<plan-revision>/delivery-<unit-id>.md
```

每份上下文固定包含：

- `# 交付单元上下文`
- `## 交付目标`
- `## 验收项`
- `## 交付步骤`
- `## 工程验证与验收测试`
- `## 关联事实` 与 `## 关联决策`

它只描述一个业务单元，不包含其他无关单元，也不再存在全局 `implementation-context.md`。多个单元共同验收时，单独生成集成交付单元，并仅注入其依赖单元 Handoff。

## 预算和压缩

预算按 Adapter 实际渲染的 Prompt 估算，不只按文件大小。默认上限为 `20000` tokens，可由本机 `~/.aiw/config.yaml` 的 `context.maxTokens` 在 `1000` 至 `200000` 间调整。清单会分别记录来源、任务事实、Handoff、单元上下文、技能、方法来源、运行约束和显式附加文件的 token 占用。

超过预算时，AIW 不能静默截断已批准事实。处理顺序是：

1. 用来源索引选择当前领域片段，而不是完整来源快照；
2. 优先使用 Handoff 替代完整 Markdown；
3. 只为当前单元保留直接依赖的 Handoff；
4. 计划阶段把过大的业务范围拆成更多独立交付单元，或新增集成交付单元；
5. 仍超预算时，拒绝执行并生成“继续拆分建议”：指出最大占用、建议切分的来源领域或业务单元、应重跑的上游节点。

自动拆分建议不等于静默创建任务。它必须保留当前计划和预算诊断，供用户或计划阶段确认新的单元边界；新的单元仍需重新通过计划门禁。

## 完整性与更新

下游节点开始前，当前来源快照、依赖产物、成功运行记录和审批事实的哈希必须一致。任一不一致即使下游失效，不能继续使用被手动改写的内容。

需求变更通过 `task source refresh`；外部事实改变方案或计划时通过 `decision resolve --impact replan`。两种情况都会保留旧版本作为审计事实，并保守地重新生成澄清/方案/计划；当前上下文只使用重新生成后的有效 revision。影响图用来校验单元引用和定位候选影响边，不能在尚未实现来源领域切片前替代重新澄清。
