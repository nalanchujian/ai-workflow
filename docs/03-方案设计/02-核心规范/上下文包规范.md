# 上下文包规范

## 核心问题

如何既保留完整事实供追溯，又避免在后续节点不断叠加 Markdown，最终超过上下文预算？

AIW 将“任务事实存储”和“单次运行注入”分开：完整产物始终保存在 `.aiw/`；默认只注入结构化 Handoff、当前单元上下文和必要的直接依赖。

## 默认注入规则

| 当前节点 | 默认输入 |
|---|---|
| `clarify` | `task.md`、当前需求快照、精简 `task.yaml` |
| `solution` | `clarify` Handoff、决策登记、已确认决策事实、精简 `task.yaml` |
| `plan` | `solution` Handoff、决策登记、已确认决策事实、精简 `task.yaml` |
| `delivery-<unit>` | `plan` Handoff、当前单元上下文、直接依赖交付单元 Handoff、精简 `task.yaml` |

默认不注入完整需求正文、`brief.md`、`solution.md`、`implementation-plan.md`、历史交付报告、全量测试报告或其他非依赖单元的 Markdown。它们仍可通过 Handoff 的 `evidence.path` 按需定位和核验。

## Handoff

除 `intake` 外，每个节点运行必须生成：

```text
handoffs/<node-id>/r<revision>.yaml
```

Handoff 固定包含：

- `summary`：本节点可供下游使用的结论；
- `facts` 和 `decisions`：结论及可追溯证据路径；
- `acceptance`：相关 AC 的当前覆盖状态；
- `changes`：业务代码变更摘要；
- `verification`：已执行命令、结果和证据；
- `openRisks`：尚未关闭的风险。

Handoff 不得复制完整 Markdown，也不得引用未声明或未提交的证据。AIW 在运行前校验证据范围与当前 revision。

## 单元上下文

计划批准后，AIW 根据 `work-breakdown.yaml` 生成：

```text
artifacts/work-units/r<plan-revision>/delivery-<unit-id>.md
```

每份上下文固定包含：

- `# 交付单元上下文`
- `## 交付目标`
- `## 验收项`
- `## 交付步骤`
- `## 工程验证与验收测试`

它只描述一个业务单元，不包含其他无关单元，也不再存在全局 `implementation-context.md`。多个单元共同验收时，单独生成集成交付单元，并仅注入其依赖单元 Handoff。

## 预算和压缩

预算按 Adapter 实际渲染的 Prompt 估算，不只按文件大小。清单会分别记录来源、任务事实、Handoff、单元上下文、技能、方法来源、运行约束和显式附加文件的 token 占用。

超过预算时，AIW 不能静默截断已批准事实。处理顺序是：

1. 优先使用 Handoff 替代完整 Markdown；
2. 计划阶段把过大的业务范围拆成更多独立交付单元；
3. 只为当前单元保留直接依赖的 Handoff；
4. 仍超预算时，拒绝运行并显示占用最大的条目，要求重跑上游节点生成更短的交接包或更细的工作单元。

## 完整性与更新

下游节点开始前，当前来源快照、依赖产物、成功运行记录和审批事实的哈希必须一致。任一不一致即使下游失效，不能继续使用被手动改写的内容。

需求变更通过 `task source refresh`；外部事实改变方案或计划时通过 `decision resolve --impact replan`。两种情况都会保留旧版本作为审计事实，但当前上下文只使用重新生成后的有效 revision。
