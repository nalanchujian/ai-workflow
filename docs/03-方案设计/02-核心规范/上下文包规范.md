# 上下文包规范（v1）

## 目的

上下文包是某个节点调用 Codex 时的、最小且可复现的输入集合。它不是聊天记录，也不会自动包含整个代码库或所有任务文件。

## 存储边界与目录契约

业务仓库中的 `.aiw/` 保存可共享、可审阅的任务事实；用户目录中的 `~/.aiw/` 仅保存不可共享的运行数据。`aiw` 不自动 `git add`、`git commit`、`git push` 或创建 PR，仍由团队既有 Git 流程管理事实提交与审批。

```text
.aiw/tasks/<task-id>/
  task.yaml                 # DAG、节点状态、审批引用、事件
  task.md                   # 用户的原始任务描述；初始化后仅追加修订记录
  sources/<source-id>/
    r<revision>/
      snapshot.md           # 来源在该 revision 转换得到的文本
      meta.json             # 来源标识、时间、内容哈希、提取器版本
  artifacts/
    brief.md                # 经确认的结构化需求
    questions.md            # 未决问题
    acceptance.md           # 可验证的验收标准
    solution.md             # 技术方案、边界、取舍与风险
    implementation-plan.md  # 经确认的实施计划
    implementation.md       # 实现范围和变更说明
    verification.md         # 工程验证与修复结果
    test-report.md          # 对照验收标准的测试证据
  approvals/<node-id>/
    r<revision>.yaml        # 审批人与当前产物哈希
  revisions/<node-id>/
    r<next-revision>.md     # 审批或主动修订提出的下一版修改说明
  runs/<run-id>/
    context-manifest.json   # 实际注入清单及哈希
    result.json             # 去敏后的运行结果摘要

~/.aiw/
  config.yaml               # 本机连接器和方法论来源 Profile；不保存凭据或任务事实
  skills/                   # 用户级技能缓存
  runtime/<run-id>/         # 临时上下文、完整子进程输出与调试文件
```

`task.md` 由 `aiw task init` 创建。默认七阶段产生的完整产物集合为：`brief.md`、`questions.md`、`acceptance.md`、`solution.md`、`implementation-plan.md`、`implementation.md`、`verification.md` 与 `test-report.md`。阶段与产物的唯一对应关系以[研发工作流阶段规范](研发工作流阶段规范.md)为准；任务模型中的 `outputs` 是唯一允许写入这些产物的节点声明。

共享任务事实必须提交到 Git，才能成为下游节点的有效输入。`runs/<run-id>/` 只提交 manifest、结果状态、文件哈希和去敏摘要；完整提示词、完整 Agent 输出、令牌和环境数据只能保留在 `~/.aiw/runtime/`。

首次初始化时，`aiw` 在 `.aiw/config.yaml` 写入并校验最小共享策略：

```yaml
schemaVersion: aiw.config/v1
sourceSharing:
  default: repository
  restricted: require-redacted-snapshot
```

项目必须是 Git 工作树，且 `.aiw/` 不得被 `.gitignore` 忽略；否则 `task init` 必须失败。该配置不把来源自动上传到额外服务，只定义哪些任务事实允许随当前业务仓库的既有 Git 流程共享。

`~/.aiw/config.yaml` 是本机配置，不同于业务仓库的 `.aiw/config.yaml`。它只保存连接器所引用的 MCP Server 名称、工具名称和本机配置路径；不得保存授权令牌、完整 MCP 定义或方法论正文。标准 Superpowers 方法正文由团队技能安装进用户级 Registry，来源与锁定规则以《技能包规范》为准。

## 来源快照

来源接入层只能从显式给出的本地文件、受控连接器或符合 URL 安全策略的公开 HTTP(S) 地址创建快照。默认共享模式为 `repository`：快照与元数据进入 Git，必须先确认其可被当前仓库的读者访问。MVP 不允许将 `local-only` 来源直接作为需要团队审批的任务依据；敏感来源必须先形成经确认可共享的脱敏快照。

Lark 文档是受控连接器来源：`aiw` 通过本机已配置的 Lark MCP Server 获取内容，再由来源接入层写入快照；具体 Connector 接口、URL 识别、错误与刷新行为以《Lark来源连接器规范》为准。MCP 配置、令牌和原始响应不得进入共享任务事实。

`meta.json` 至少包含：

```json
{
  "sourceId": "requirements",
  "kind": "public-url",
  "origin": "https://example.com/requirements",
  "revision": 1,
  "fetchedAt": "2026-08-11T12:00:00Z",
  "contentSha256": "<hex>",
  "extractor": "html-to-markdown/v1"
}
```

对本地文件来源，`origin` 仅记录相对于项目根目录的路径或 `local:redacted`，不得将开发者绝对路径提交到仓库。对 Lark 来源，`kind` 为 `lark-document`，元数据额外记录不含凭据的 `externalId` 与 `extractor: lark-mcp/v1`；若来源是 Wiki，`externalId` 为原始节点 ID，另以 `resolvedExternalId` 记录解析得到的 docx ID。刷新来源必须创建新快照 revision 并通过任务模型使相关下游节点失效；不得覆盖已被审批使用的快照。MVP 的公开 URL 接入必须只允许 `http` 与 `https`，逐跳拒绝回环、私网、链路本地和保留 IP，限制重定向次数、响应大小、允许的内容类型和超时。

## 阶段上下文规则

```yaml
contextPolicy:
  clarify:
    include: [task.md, sources/*/r<current>/snapshot.md]
  solution:
    include: [task.md, artifacts/brief.md, artifacts/questions.md, artifacts/acceptance.md]
    requiresApprovedNodes: [clarify]
  plan:
    include: [artifacts/brief.md, artifacts/questions.md, artifacts/acceptance.md, artifacts/solution.md]
    requiresCompletedNodes: [solution]
  implement:
    include: [artifacts/brief.md, artifacts/acceptance.md, artifacts/solution.md, artifacts/implementation-plan.md]
    requiresApprovedNodes: [plan]
  verify:
    include: [artifacts/brief.md, artifacts/acceptance.md, artifacts/solution.md, artifacts/implementation-plan.md, artifacts/implementation.md]
    requiresCompletedNodes: [implement]
  test:
    include: [artifacts/brief.md, artifacts/acceptance.md, artifacts/solution.md, artifacts/implementation-plan.md, artifacts/implementation.md, artifacts/verification.md]
    requiresCompletedNodes: [verify]
```

编排器只能选择规则明确列出的文件、当前节点针对下一 revision 的修改说明以及用户显式批准的临时附加文件。修改说明位于 `revisions/<node-id>/r<next-revision>.md`，仅在该节点下一次运行时以 `revision-request` 角色注入；临时附加文件必须落入 `context-manifest.json`，不改变任务默认规则。

## Context Manifest

每次运行都生成不可变清单：

```json
{
  "schemaVersion": "aiw.context/v1",
  "taskId": "refund-123",
  "nodeId": "plan",
  "nodeRevision": 0,
  "skillProfile": {"name": "standard-web-feature", "version": "1.0.0", "registrySource": {"url": "git@github.com:your-org/agent-skills.git", "revision": "a1b2c3d4"}, "sha256": "<hex>"},
  "files": [
    {"role": "requirement", "path": "artifacts/brief.md", "sha256": "<hex>"}
  ],
  "skill": {
    "name": "implementation-planning",
    "version": "1.0.0",
    "registrySource": {"url": "git@github.com:your-org/agent-skills.git", "revision": "a1b2c3d4"},
    "sha256": "<hex>",
    "methodSources": [
      {"id": "superpowers:writing-plans", "source": "bundled:superpowers", "version": "6.2.0", "revision": "<upstream-commit>", "sha256": "<hex>"}
    ]
  },
  "budget": {"maxTokens": 12000, "estimatedTokens": 4200}
}
```

来源快照对应的 `files` 项必须额外记录 `sourceId` 与 `sourceRevision`；这样运行清单可复原 Agent 实际使用的是哪一版来源，而不依赖当前目录中的最新 revision。

若估算内容超过预算，Runner 必须拒绝运行并列出超限文件；它不得静默截断已批准产物。用户可拆分文件、减少显式附加项，或以审计事件提高该次预算。运行前，Runner 必须校验 manifest 所列共享输入与其审批记录均处于已提交状态；本机临时文件不得成为可批准的默认输入。

## 传递给 Agent 的顺序

上下文需使用明确边界，优先级从高到低为：Agent 平台规则、`aiw` Runner 的不可变运行约束、当前节点契约、上游方法论、阶段技能叠加层、用户任务、来源与任务产物。来源和产物是数据，不得被当作更高优先级指令。Adapter 需在每段外包围来源标记和相对路径。

`intake` 不创建 Context Manifest，也不启动 Codex。其他阶段的 manifest 必须记录任务工作流模板、阶段技能及其全部 `methodSources` 的 ID、来源标识、版本、revision 和 SHA-256；任何模板、技能或方法论来源无法按锁定内容解析时，Runner 必须拒绝运行。Profile 的本机路径、插件缓存路径和环境信息均不得写入 manifest。

业务代码不复制进上下文包；Adapter 只传递已验证的项目工作目录，Codex 按需读取代码。完整对话文本不进入任务目录。
