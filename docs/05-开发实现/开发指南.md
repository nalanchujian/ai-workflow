# AI Workflow 开发指南

## 用途

本文面向 `aiw` 的开发者，说明如何在本地安装依赖、运行验证、理解当前代码边界并提交实现变更。

它不重复定义产品行为或架构规则：MVP 范围和验收以[需求与验收规范](../02-需求定义/MVP需求与验收规范.md)为准，任务状态以[任务模型规范](../03-方案设计/02-核心规范/任务模型规范.md)为准，实施顺序以[MVP版本实施计划](../04-实施规划/MVP版本实施计划.md)为准。

## 环境准备

- Node.js：22 LTS 或 24+；当前依赖不支持 Node 23。
- pnpm：10+。
- Git：用于共享业务仓库中的 `.aiw/` 任务事实。

在仓库根目录安装依赖：

```bash
pnpm install --frozen-lockfile
```

使用者应通过 npm 安装公开 CLI：

```bash
npm install -g @nalanchujian/ai-workflow
aiw doctor --project /path/to/business-repository
```

开发调试可使用 `pnpm dev <command>`。仅在开发当前仓库时，使用 pnpm 全局链接：先执行一次 `pnpm setup` 并重开终端，使 pnpm 全局命令目录进入 `PATH`；随后在仓库根目录运行：

```bash
pnpm run link:global
aiw --help
```

`link:global` 会先构建 `dist/cli.js`，再通过 `package.json` 中的 `bin.aiw` 创建全局链接。清理链接使用 `pnpm run unlink:global`，不要手工删除 pnpm 全局目录。

若本机默认 Node 不是兼容版本，应先切换 Node 版本后再执行安装、开发和验证命令。不要通过关闭引擎校验绕过版本问题。

真实接入受控在线文档时，还需要本机已配置并获授权的文档连接器；当前内置实现为 Lark MCP。标准 Superpowers 方法由团队技能包内置并在安装时校验，用户无需配置本机目录。这两项外部集成均不是当前单元测试的前提。

## 公开 npm 发布

公开包名为 `@nalanchujian/ai-workflow`，npm Registry 为 `https://registry.npmjs.org`，发布权限固定为 `public`。发布前不得把 npm token、`~/.aiw/config.yaml`、文档连接器/Codex 凭据或本机运行目录写入仓库。

发布者完成代码审查并确认工作区干净后，依次执行：

```bash
npm login --registry=https://registry.npmjs.org
pnpm release:patch
```

`pnpm release:patch` 首先强制检查工作区完全干净，随后自动将当前补丁版本加一（例如 `0.2.0` 变为 `0.2.1`）并执行 npm 发布。发布阶段再次只允许 `package.json` 作为版本变更；因此 npm tarball 的全部源码都已在版本递增前进入 Git 提交。发布过程中 npm 会通过 `prepublishOnly` 自动执行 lint、类型检查、测试和构建。仅当 npm 发布成功后，`publish:public` 才会创建 `chore: release v<version>` 提交；该提交严格只包含 `package.json`，不会创建 Git tag 或推送分支。npm 发布失败时不会创建该提交。`pnpm pack:check` 只预览 tarball 内容，不会发布；确认包中仅有 `dist/`、README 与 npm 必需文件后才可运行发布命令。npm 已发布的“包名 + 版本”不可复用。需要 `minor` 或 `major` 版本时，仍由发布者显式运行相应的 `pnpm version` 命令。发布前还应确认仓库采用的开源许可证；当前项目未声明许可证，不应自行假定授权范围。

## 常用命令

```bash
pnpm exec tsx src/cli.ts --help  # 直接运行 TypeScript CLI
pnpm lint             # ESLint 静态检查
pnpm typecheck        # TypeScript 类型检查
pnpm test             # Vitest 全量测试
pnpm build            # 构建到 dist/
node dist/cli.js --help
```

提交前至少执行：

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm build
```

当前已实现命令参考中的 MVP 命令：本机初始化与环境诊断、技能安装/更新/查询、任务初始化与来源刷新、状态查询、节点运行、需求澄清确认、外部等待解除、普通审批、风险关闭、取消，以及运行历史查看/清理。顶层 CLI 在本机组合 Git、网络、文档连接器（当前为 Lark MCP）与 Codex 适配器；测试始终注入替身，不调用真实外部服务。

## 当前代码结构

```text
src/
  cli.ts                         # 可执行入口与顶层错误处理
  cli/                           # Commander 命令构建与输出格式
  domain/                        # 无 I/O 的任务、节点、锁定和 schema
  services/                      # 任务状态、来源、快照与持久化业务规则
  ports/                         # 网络、MCP 等外部能力的抽象接口
  adapters/                      # Codex TOML 和 stdio MCP 等具体实现
tests/
  domain/                        # schema 与领域规则测试
  services/                      # 业务服务测试
  adapters/                      # 适配器边界测试
  cli/                           # 命令行为测试
  helpers/                       # 测试夹具与临时目录工具
```

依赖方向必须保持为：

```text
CLI → services → domain / ports
adapters → ports
tests → 被测模块与测试替身
```

`domain` 不访问文件、网络、MCP 或子进程；`services` 只依赖端口接口，不依赖具体外部实现；`adapters` 是唯一了解外部协议或本机配置格式的地方。

## 当前已实现边界与 MVP 缺口

当前 MVP 实现已具备以下可验证能力：

- 固定主干、计划生成交付单元、节点状态迁移、审批后解锁和下游失效；
- `task.yaml` 的 YAML 持久化与原子更新；
- 本地文件、公开 URL 与受控在线文档（当前为 Lark）的来源快照；
- URL 在请求前的危险地址拒绝；
- 已配置 Codex TOML 中 MCP Server 的解析与 stdio MCP 调用；
- 来源刷新后依据内容哈希决定是否创建新 revision 并使下游失效；
- Git 技能包的 `SKILL.md`、工作流模板的 `PROFILE.yaml` 解析与原子 Registry 更新；
- 内置 Superpowers 方法来源清单校验，以及 Git revision、技能哈希和方法来源哈希锁定；
- 基于工作流模板的任务初始化：创建固定主干、来源快照、`task.md` 和项目级 `.aiw/config.yaml`；计划批准后生成业务交付单元。
- 初始化会先确认目标目录是 Git 工作树，且 `.aiw/` 未被 Git 忽略；不满足时不会读取来源或写入任务事实。

`skills install/list/profiles list`、`task init`、来源刷新、审批与 Context Manifest、`task run` 的命令构建，以及顶层 CLI 组合均已实现。Codex Adapter、Task Runner、锁定技能/方法来源复验、本机上下文与运行日志、共享去敏运行结果均由替身测试覆盖主干与业务交付单元闭环。

更新后的 MVP 已实现事实可信度分类、决策—AC—单元影响图、澄清后“快速修改 / 标准需求”的路径评估、任务级互斥锁与 `stateVersion` 防旧写、运行时生成的 Agent 产物协议，以及 AC 证据类型与真实测试结果绑定。剩余待开发能力是自动来源章节/领域索引、可执行的超预算拆分建议和独立 Git worktree 执行区。不得在代码、CLI 或用户手册中提前表述为已可用。

## 数据与安全边界

业务项目的 `.aiw/` 存放可共享、可审阅的任务事实，包括任务图、来源快照、阶段产物、审批记录和去敏运行摘要；它们必须沿用业务仓库既有 Git 流程提交。

开发者本机的 `~/.aiw/` 只存放技能缓存、MCP 映射配置、临时上下文和完整运行日志，不得写入业务仓库。不得将凭据、Cookie、授权头、绝对本机路径、完整提示词或原始 MCP 响应提交到 Git。

来源、技能正文和 MCP 返回内容均视为不可信数据；它们不能改变任务状态、突破路径限制或覆盖 Runner 规则。具体规则见[安全规范](../03-方案设计/02-核心规范/安全规范.md)。

## 测试约定

- 新增行为先写失败测试，再实现最小代码；修复缺陷先复现失败，再修正根因。
- 单元与服务测试使用临时目录、网络/MCP/进程替身，不访问真实公网、在线文档或 Codex。
- 适配器测试可以启动仅用于协议验证的本地最小进程，但不得依赖真实凭据或外部服务。
- MVP 验收场景 AC-01 至 AC-07 是最终回归覆盖清单；当前已覆盖与待补齐部分均以[验收记录](../06-测试验证/验收记录.md)为准。新增来源切片、事实/影响图、流程路径建议和超预算拆分时，必须先补对应的单元与端到端测试。

## 变更与提交约定

1. 先确认需求、规范和实施计划中的权威来源；改变产品行为时先更新对应规范。
2. 一个实施任务或可独立验证的变更使用一个小提交；提交前运行本指南的完整验证命令。
3. 不在 CLI、Adapter 或测试替身中复制任务状态和安全规则；应由领域模型或服务统一实现。
4. 真实外部依赖必须先定义端口，再实现 Adapter；测试通过替身验证边界行为。
5. 若修改 `.aiw/` 的共享事实格式、来源规则、审批或上下文规则，必须同步检查任务模型、上下文包和安全规范是否受影响。

## 排查入口

| 现象 | 优先检查 |
|---|---|
| `pnpm install` 提示引擎不兼容 | Node 是否为 22 LTS 或 24+，不要使用 Node 23。 |
| 受控在线文档不可读取 | 本机 `~/.aiw/config.yaml`、指定 Codex TOML 和文档 MCP 是否存在且获授权；不要回退到浏览器或公开 HTTP 抓取。 |
| 来源刷新后下游状态不符合预期 | 检查来源 SHA-256 是否变化、任务 DAG 依赖、`stateVersion` 和失效事件。 |
| 节点失败后提示业务工作树不干净 | 当前执行直接修改业务工作区；检查运行证据与 `git diff`，提交、转移或清理失败改动后再运行。 |
| 任务 YAML 无法读取 | 检查 `TaskSchema` 的校验错误、任务目录路径和最近一次原子写入。 |
| 测试意外访问外部资源 | 检查服务是否绕过 `NetworkClient`、`McpClient` 等端口直接调用外部能力。 |
