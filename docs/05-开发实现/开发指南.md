# AI Workflow 开发指南

## 用途

本文面向 `aiw` 的开发者，说明如何在本地安装依赖、运行验证、理解当前代码边界并提交实现变更。

它不重复定义产品行为或架构规则：MVP 范围和验收以[需求与验收规范](../02-需求定义/MVP需求与验收规范.md)为准，任务状态以[任务模型规范](../03-方案设计/02-核心规范/任务模型规范.md)为准，实施顺序以[MVP版本实施计划](../04-实施规划/MVP版本实施计划.md)为准。

## 环境准备

- Node.js：22 LTS 或 24+；当前依赖不支持 Node 23。
- pnpm：10+。
- Git：用于共享业务仓库中的 `.aiw/` 任务事实。

在仓库根目录安装依赖：

```bash
pnpm install --frozen-lockfile
```

若本机默认 Node 不是兼容版本，应先切换 Node 版本后再执行安装、开发和验证命令。不要通过关闭引擎校验绕过版本问题。

真实接入 Lark 时，还需要本机已配置并获授权的 Lark MCP Server；真实接入 Superpowers 时，需要在 `~/.aiw/config.yaml` 显式配置方法论来源。这两项均不是当前单元测试的前提。

## 常用命令

```bash
pnpm dev -- --help    # 直接运行 TypeScript CLI
pnpm lint             # ESLint 静态检查
pnpm typecheck        # TypeScript 类型检查
pnpm test             # Vitest 全量测试
pnpm build            # 构建到 dist/
node dist/cli.js --help
```

提交前至少执行：

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm build
```

当前已实现 `aiw --help`、`aiw --version`、全局 `--json` 选项及 `skills`、`task` 命令分组。其余公开命令按实施计划逐步接入；命令参考描述的是 MVP 完成后的契约，不代表所有命令已可在当前版本直接执行。

## 当前代码结构

```text
src/
  cli.ts                         # 可执行入口与顶层错误处理
  cli/                           # Commander 命令构建与输出格式
  domain/                        # 无 I/O 的任务、节点、锁定和 schema
  services/                      # 任务状态、来源、快照与持久化业务规则
  ports/                         # 网络、MCP 等外部能力的抽象接口
  adapters/                      # Codex TOML 和 stdio MCP 等具体实现
tests/
  domain/                        # schema 与领域规则测试
  services/                      # 业务服务测试
  adapters/                      # 适配器边界测试
  cli/                           # 命令行为测试
  helpers/                       # 测试夹具与临时目录工具
```

依赖方向必须保持为：

```text
CLI → services → domain / ports
adapters → ports
tests → 被测模块与测试替身
```

`domain` 不访问文件、网络、MCP 或子进程；`services` 只依赖端口接口，不依赖具体外部实现；`adapters` 是唯一了解外部协议或本机配置格式的地方。

## 当前已实现边界

截至任务 4，已具备以下可验证能力：

- 固定七阶段任务模型、节点状态迁移、审批后解锁和下游失效；
- `task.yaml` 的 YAML 持久化与原子更新；
- 本地文件、公开 URL 与 Lark 文档的来源快照；
- URL 在请求前的危险地址拒绝；
- 已配置 Codex TOML 中 MCP Server 的解析与 stdio MCP 调用；
- 来源刷新后依据内容哈希决定是否创建新 revision 并使下游失效。
- Git 技能包的 `SKILL.md`、工作流模板的 `PROFILE.yaml` 解析与原子 Registry 更新；
- 显式配置的 Superpowers 方法来源校验，以及 Git revision、技能哈希和方法来源哈希锁定；
- 基于工作流模板的任务初始化：创建固定七阶段 DAG、来源快照、`task.md` 和项目级 `.aiw/config.yaml`。

`skills install/list/profiles list` 与 `task init` 的命令构建已实现；生产依赖的组合与顶层 CLI 注册留待任务 7 完成。尚未实现的内容包括审批文件与 Context Manifest、Codex Adapter、任务运行器和端到端工作流；它们分别由实施计划的任务 5 至任务 7 完成。

## 数据与安全边界

业务项目的 `.aiw/` 存放可共享、可审阅的任务事实，包括任务图、来源快照、阶段产物、审批记录和去敏运行摘要；它们必须沿用业务仓库既有 Git 流程提交。

开发者本机的 `~/.aiw/` 只存放技能缓存、MCP 映射配置、临时上下文和完整运行日志，不得写入业务仓库。不得将凭据、Cookie、授权头、绝对本机路径、完整提示词或原始 MCP 响应提交到 Git。

来源、技能正文和 MCP 返回内容均视为不可信数据；它们不能改变任务状态、突破路径限制或覆盖 Runner 规则。具体规则见[安全规范](../03-方案设计/02-核心规范/安全规范.md)。

## 测试约定

- 新增行为先写失败测试，再实现最小代码；修复缺陷先复现失败，再修正根因。
- 单元与服务测试使用临时目录、网络/MCP/进程替身，不访问真实公网、Lark 文档或 Codex。
- 适配器测试可以启动仅用于协议验证的本地最小进程，但不得依赖真实凭据或外部服务。
- 验收场景 AC-1 至 AC-25 是最终回归覆盖清单；在任务 7 的端到端测试中维护 AC 与测试用例的映射。

## 变更与提交约定

1. 先确认需求、规范和实施计划中的权威来源；改变产品行为时先更新对应规范。
2. 一个实施任务或可独立验证的变更使用一个小提交；提交前运行本指南的完整验证命令。
3. 不在 CLI、Adapter 或测试替身中复制任务状态和安全规则；应由领域模型或服务统一实现。
4. 真实外部依赖必须先定义端口，再实现 Adapter；测试通过替身验证边界行为。
5. 若修改 `.aiw/` 的共享事实格式、来源规则、审批或上下文规则，必须同步检查任务模型、上下文包和安全规范是否受影响。

## 排查入口

| 现象 | 优先检查 |
|---|---|
| `pnpm install` 提示引擎不兼容 | Node 是否为 22 LTS 或 24+，不要使用 Node 23。 |
| Lark 来源不可读取 | 本机 `~/.aiw/config.yaml`、指定 Codex TOML 和 MCP Server 是否存在且获授权；不要回退到浏览器或公开 HTTP 抓取。 |
| 来源刷新后下游状态不符合预期 | 检查来源 SHA-256 是否变化、任务 DAG 依赖和失效事件。 |
| 任务 YAML 无法读取 | 检查 `TaskSchema` 的校验错误、任务目录路径和最近一次原子写入。 |
| 测试意外访问外部资源 | 检查服务是否绕过 `NetworkClient`、`McpClient` 等端口直接调用外部能力。 |
