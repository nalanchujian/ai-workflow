# 内置方法依赖设计

## 目标

将 Superpowers 从最终用户的本机依赖改为团队技能包的受控依赖。用户只需安装 `aiw` 与团队技能仓库；安装器自动获取、校验、缓存并锁定该技能包需要的上游方法内容。用户不再配置或理解 Superpowers 的目录、版本与哈希。

目标使用路径：

```bash
npm install -g @nalanchujian/ai-workflow
aiw init
aiw skills install https://github.com/nalanchujian/ai-workflow-skills.git --ref v1.0.0
aiw task init --project . --source ./requirements.md --skill-profile standard-web-feature@1.0.0
```

## 用户边界

- `aiw` 负责读取和验证团队技能包内置的方法依赖。
- `ai-workflow-skills` 负责选择、随版本发布并声明其依赖的上游方法。
- 用户只选择团队工作流模板；不安装、配置或更新 Superpowers。
- `~/.aiw/config.yaml` 不再包含 `methodSources`。它仅保留可选的本机连接器映射，例如 Lark MCP；不使用 Lark 的用户无需编辑任何字段。

## 团队技能包结构

```text
ai-workflow-skills/
├── skills/
│   └── requirements-clarification/SKILL.md
├── profiles/
│   └── standard-web-feature/PROFILE.yaml
├── method-sources/
│   └── superpowers/
│       └── 6.2.0/
│           ├── SOURCE.yaml
│           ├── brainstorming/SKILL.md
│           ├── writing-plans/SKILL.md
│           └── test-driven-development/SKILL.md
└── THIRD_PARTY_NOTICES.md
```

只内置工作流实际引用的三个方法，不镜像完整 Superpowers 仓库，也不执行其中任何脚本或二进制文件。

`SOURCE.yaml` 是上游来源清单，必须包含以下字段：

| 字段 | 值 |
| --- | --- |
| `id` | `superpowers` |
| `version` | 团队内置的方法版本，例如 `6.2.0` |
| `upstream.url` | `https://github.com/obra/superpowers.git` |
| `upstream.revision` | 与实际复制内容对应的、完整 40 位上游 Git commit |
| `upstream.license` | 经发布核验的许可证标识，例如 `MIT` |
| `methods` | 当前内置的 `brainstorming`、`writing-plans`、`test-driven-development` |

`THIRD_PARTY_NOTICES.md` 记录上游名称、URL、版本、commit、许可证文本和团队同步日期。每次更新内置方法时，必须同步更新 `SOURCE.yaml`、NOTICE 和团队技能的语义化版本。

## 技能声明与安装契约

阶段技能将方法引用由：

```yaml
source: configured:superpowers
```

改为：

```yaml
source: bundled:superpowers
```

安装器在同一次 Git 来源安装中执行原子校验：

1. 校验 `SOURCE.yaml` 的 ID、语义化版本、上游 URL、revision、许可证和方法列表。
2. 校验每个被技能引用的 `method-sources/<id>/<version>/<method>/SKILL.md` 存在、是普通 UTF-8 文件、front matter 名称匹配且位于声明根目录内。
3. 计算每个方法入口的 SHA-256；记录方法 ID、`bundled:<id>`、版本、上游 revision、哈希和正文。
4. 校验每个阶段技能引用的方法与已内置的方法匹配，再校验模板的六阶段映射。
5. 仅所有技能、模板和方法均通过时，才替换本机 Registry。

安装器将方法正文与元数据保存在用户级技能 Registry 中，而不是保存对插件缓存、临时克隆目录或上游 Git 工作区的引用。Runner 从 Registry 读取被任务锁定的正文并复核版本、revision 与哈希。任务事实继续只保存方法 ID、来源、版本、revision 与哈希；不保存本机缓存路径或完整方法正文。

## 任务锁定与运行

```text
团队技能仓库（技能 + 模板 + 内置方法）
  → aiw skills install
  → 用户级 Registry（方法正文与校验元数据）
  → aiw task init（锁定模板、技能、上游 revision 与哈希）
  → aiw task run（从 Registry 读取锁定方法并校验）
  → Codex CLI
```

一个任务同时具有两层可追溯来源：

- 节点技能的 `registrySource` 是 `ai-workflow-skills` 的 Git revision；
- 方法来源的 `revision` 是内置时声明的 Superpowers 上游 commit，`sha256` 是实际注入的 `SKILL.md` 内容。

安装新版本团队技能不会改写既有任务。若本机 Registry 缺少任务锁定的方法正文，或其上游 revision / 哈希不匹配，Runner 必须拒绝运行并提示重新安装对应的团队技能版本。

## `aiw init` 的调整

`aiw init` 仅初始化 `~/.aiw/config.yaml` 的安全本机模板：

```yaml
# AI Workflow 本机配置；不得提交到业务仓库。
schemaVersion: aiw.local/v1

# 仅在需要读取 Lark docx 时配置 connectors.lark。
connectors: {}
```

- 首次运行创建目录与模板；重复运行绝不覆盖已有配置。
- 不扫描 Superpowers、Codex 插件缓存、MCP Server 或凭据。
- 不使用 Lark 时，用户无需继续编辑该文件。
- 使用 Lark 时，用户只配置已有 Codex MCP Server 的映射；其真实命令、环境变量和凭据继续由 Codex 配置管理。

## 迁移与兼容性

- 新版标准团队技能只使用 `bundled:superpowers`，无需 `methodSources` 本机 Profile。
- 已创建的旧任务继续保留 `configured:superpowers` 锁定；其运行需要保留原本机配置，`aiw init` 不自动删除它。
- 新 Registry 与旧 Registry 格式不兼容时，必须进行显式 schema 升级；升级不得删除旧任务仍需要的方法记录。
- 公开的 `ai-workflow-skills` 当前 `v1.0.0` 仍是旧契约。引入内置方法依赖的首个发布为新主版本，避免同名版本改变方法来源语义。

## 安全与许可

- 内置方法仅作为声明式 UTF-8 Markdown 读取；安装和运行都不得执行方法目录中的脚本、依赖安装逻辑或二进制文件。
- 只允许 `SOURCE.yaml` 显式列出的入口文件，不递归加载上游方法所引用的其他本机资源。
- 上游方法的再分发必须保留适用许可证与版权声明；发布前由维护者核对上游仓库、commit 与许可证。
- Lark 凭据、Codex MCP 完整配置、用户绝对路径和运行日志仍不进入团队技能包或业务任务事实。

## 验收

1. 新用户在没有 Superpowers 本机配置或插件缓存的情况下，可安装新版团队技能并创建使用标准模板的任务。
2. 安装器拒绝方法缺失、名称不匹配、超出 `SOURCE.yaml` 列表、上游元数据不完整或哈希无法记录的技能包，且 Registry 保持原状。
3. 创建的任务锁定团队技能 Git revision、上游方法 revision 和每个方法正文哈希。
4. 删除或篡改用户级 Registry 中的方法正文后，Runner 拒绝执行被影响节点，不允许进入下游节点。
5. `aiw init` 不创建 Superpowers 配置；配置存在时不覆盖；没有 Lark 需求的用户执行 `aiw doctor` 时仅收到 Lark 可选警告。
6. `THIRD_PARTY_NOTICES.md` 与 `SOURCE.yaml` 覆盖每个再分发的上游方法版本与许可信息。
