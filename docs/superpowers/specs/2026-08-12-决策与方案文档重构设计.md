# 决策与方案文档重构设计

## 目标

在不改变下列四份文档名称的前提下，使每份文档只回答一个核心问题，并建立从决策到实现约束的清晰阅读链路：

```text
立项申请 → 方案调研 → 产品设计 → 架构设计 → 规范与参考
```

## 文档职责

| 文档 | 核心问题 | 面向读者 | 必须回答 | 明确不回答 |
|---|---|---|---|---|
| 立项申请 | 是否值得投入 MVP，以及需要批准什么？ | 管理层、试点负责人 | 问题、预期价值、MVP 边界、投入与风险、试点指标、继续或停止条件 | 技术选型细节、用户操作、系统实现 |
| 方案调研 | 为什么选择 `aiw + Superpowers + Codex`，而不直接采用 Trellis？ | 技术决策者、管理层 | 比较基线、选择原则、三条路径的分工、Trellis 的对标与降级定位、复核条件 | 业务工作流、产品交互、模块实现 |
| 产品设计 | 谁在什么场景下，如何用 aiw 推进复杂研发任务？ | 开发者、技术负责人、技能维护者 | 用户、场景边界、任务旅程、角色责任、阶段产物、审批与异常处理 | 命令参数、文件格式、进程调用细节 |
| 架构设计 | 系统如何保障复杂变更可信、可控、可追责？ | 架构师、实现者 | 系统边界、分层职责、共享事实与本机数据边界、关键数据流、架构不变量、外部依赖 | 立项收益、选型辩论、逐步操作说明 |

## 重构规则

1. 每个事实只在其归属文档完整解释一次；其他文档只保留一句结论并链接到原文。
2. 产品文档中的命令示例下沉到《CLI 命令参考》；数据结构、状态机和安全细节下沉到对应规范。
3. 架构文档中的 Superpowers、Codex、Trellis 只描述系统边界和集成约束；路径选择理由只在《方案调研》完整说明。
4. 《立项申请》只陈述管理决策所需的信息，不承担产品说明书或技术方案职责。
5. 四份文档结尾均增加“阅读下一步”或“权威来源”链接，确保读者能从上游决策自然进入下游实现约束。

## 目标结构

### 立项申请

1. 决策请求
2. 业务问题与机会
3. 拟投入的 MVP 及明确边界
4. 预期收益、资源与主要风险
5. 试点指标、阶段门槛与停止条件
6. 需要批准的事项

### 方案调研

1. 调研结论
2. 比较对象与评估标准
3. 直接使用 Codex、Superpowers、Trellis 的对比
4. 推荐组合及职责边界
5. Trellis 的对标、降级与高成本改造边界
6. 复核触发条件

### 产品设计

1. 产品命题与目标用户
2. 适用与不适用场景
3. 端到端任务旅程
4. 角色与责任
5. 阶段产物、审批与变更处理
6. 与规范、参考文档的边界

### 架构设计

1. 架构目标与非目标
2. 系统边界与外部依赖
3. 分层职责
4. Git 共享事实与本机运行数据
5. 关键数据流与架构不变量
6. 专项规范映射

## 验收标准

- 每份文档开篇明确其核心问题和读者。
- 不再出现完整重复的七阶段、工具对比、命令示例或技术细节。
- 所有细节都能追溯到唯一的权威文档。
- README 的四条说明与重构后的核心命题一致。
