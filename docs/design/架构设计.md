# 本地 Agent 技能与任务编排器设计

## 目标与范围

构建本地 CLI 工具 `aiw`（AI Workflow），让团队从 Git 共享声明式 `SKILL.md` 技能，并将复杂需求组织为可审阅、可恢复的子任务图，交由 Codex CLI 执行。业务仓库通过 Git 共享任务事实；技能缓存与原始运行数据仍保留在每位成员本机。

MVP 不构建新的模型、聊天系统、云端调度器或多 Agent 协作系统；不允许技能包携带可执行代码；不自动选择技能；不读取未经授权的登录态在线文档。

## 命令体验

```bash
aiw skills install git@github.com:your-org/agent-skills.git
aiw skills list
aiw task init req-123 --project . --source https://example.com/requirements
aiw task run req-123 clarify --skill requirements-clarification
aiw task approve req-123 clarify
aiw task run req-123 solution --skill technical-solution
aiw task run req-123 plan --skill implementation-planning
aiw task approve req-123 plan
aiw task run req-123 implement --skill implementation
aiw task run req-123 verify --skill implementation-verification
aiw task run req-123 test --skill acceptance-testing
aiw task approve req-123 test
```

`aiw skills install` 在首次运行时克隆技能仓库到本地缓存，验证结构并记录来源与锁定的 Git revision；对同一来源再次安装时更新该来源的锁定 revision，不创建重复记录。

## 七层架构

1. **交互层（aiw CLI）**：解析安装、任务、审批和执行命令，输出人类可读和机器可读结果。
2. **来源接入层**：读取本地文件、公开 URL 或受控连接器内容，转换为标准文本并生成来源快照。
3. **任务上下文与状态层**：在业务仓库 `.aiw/` 保存来源、已确认产物、上下文注入规则、任务 DAG、状态和审批记录。
4. **技能目录与方法层**：管理本地技能缓存及其上游方法论引用，按名称定位 `SKILL.md`，记录来源、版本、解析 revision 和内容哈希。
5. **任务编排层**：验证固定七阶段及其子任务依赖，选择当前阶段的已确认上下文、显式技能和锁定方法论，管理状态、失效和人工关卡。
6. **Agent 适配层**：将通用运行请求转换为 Codex CLI 的参数、提示词和临时上下文文件。未来可增加其他适配器。
7. **执行层（Codex CLI）**：外部执行者，负责分析、读写代码、调用工具和运行测试。

`aiw` 负责技能、任务图、上下文与关卡；Codex 负责实际执行。技能仓库由第 4 层读取，业务仓库只由第 7 层读写。

## 与 Superpowers、Trellis 的边界

`aiw` 的产品目标是治理复杂研发变更，而不是再实现一个 Agent Harness。三者的分工如下：

| 对象 | 在当前设计中的角色 | `aiw` 是否依赖 |
|---|---|---|
| Superpowers | 可版本锁定的通用研发方法论来源；由阶段技能按需引用 | 是，作为 MVP 的方法论来源，不复制其通用方法 |
| aiw | 来源、任务事实、审批、失效、上下文与运行清单的唯一治理层 | — |
| Codex CLI | 读取工作目录、调用工具、修改代码和执行验证的 Agent | 是，作为 MVP 首个执行 Adapter |
| Trellis | 任务、Spec、Skill、Hook 与子 Agent 组成的完整 Agent Harness | 否；作为替代方案和对标对象评估 |

Trellis 若被纳入同一任务，默认会同时维护自身的任务、上下文和工作流文件；这会与 `.aiw/` 的共享任务事实产生双重真相源。因此当前 MVP 不提供“部分复用 Trellis Skill”或“同时运行两套工作流”的模式。未来若评估 Trellis 作为执行提供方，必须由 `aiw` 保持审批、revision 与失效事实的唯一所有权，并单独设计 Adapter 契约。

## 技能包

```text
skills/
  requirements-clarification/SKILL.md
  technical-solution/SKILL.md
  implementation-planning/SKILL.md
  implementation/SKILL.md
  implementation-verification/SKILL.md
  acceptance-testing/SKILL.md
```

每个 `SKILL.md` 采用 YAML front matter，至少声明 `name`、`version`、`description`、适用阶段和上游方法论引用。阶段技能不复制 Superpowers 的通用研发方法，只叠加当前阶段的输入、产物、禁止事项和验证要求；MVP 仅加载 Markdown 与受限元数据，并锁定上游方法论的版本与哈希。Trellis 不是可单独摘取的默认方法来源：其 Skill 依赖任务、Spec、Hook 与平台适配等完整运行环境。

## 复杂任务、子任务和审批

任务是 DAG，而不是单条提示词。默认七阶段为资料接入、需求澄清、技术方案、实施计划、实现、工程验证和验收测试。实现阶段可继续拆成有依赖的 API、数据库、前端或迁移子任务；这仍可由单个 Codex 依次执行。

需求澄清、实施计划和最终测试后默认存在人工关卡：

```text
pending → ready → running → awaiting_approval → completed
                    │                 │
                    ├→ failed         └→ pending（要求修改）
                    └→ cancelled

任意节点 → invalidated（上游 revision 变化）
```

审批决定独立于节点状态；需要审批的节点仅在获批后进入 `completed`。每个子任务有 ID、标题、依赖、显式技能、状态、审批要求和产物路径。上游任务未完成时，下游任务不得执行；上游被修订后，已开始的下游任务会标记为 `invalidated`。

```text
intake
  → clarify → [人工确认]
  → solution
  → plan → [人工确认]
  → implement
  → verify
  → test → [人工确认]
```

## 任务上下文

`aiw` 不保存完整聊天记录。它保存可追溯任务产物，并仅向当前阶段注入最小、已确认的上下文：

```text
.aiw/tasks/req-123/
  task.yaml                         # DAG、状态、审批引用和上下文规则
  task.md                           # 原始任务与修订说明
  sources/<source-id>/snapshot.md   # 来源文本快照
  sources/<source-id>/meta.json     # URL、获取时间、内容哈希
  artifacts/brief.md                # 已确认的结构化需求
  artifacts/questions.md            # 待确认事项
  artifacts/acceptance.md           # 可验证的验收标准
  artifacts/solution.md             # 技术方案与风险
  artifacts/implementation-plan.md  # 已确认的实施计划
  artifacts/implementation.md       # 实现说明
  artifacts/verification.md         # 工程验证记录
  artifacts/test-report.md          # 测试证据
  approvals/<node-id>/r<revision>.yaml # 审批与产物哈希
  runs/<run-id>/                    # 共享 manifest 与去敏结果
```

上述 `.aiw/` 纳入业务仓库 Git；`~/.aiw/` 只保存技能缓存、临时上下文和原始运行日志。`aiw` 不取代现有 Git 提交、PR 或代码审查机制：它只校验共享任务事实已提交，再允许下游节点运行。

来源快照是在线文档在某一时刻的本地文本副本，不是图片。来源内容变更时，由哈希检测并提示重新分析，绝不静默混入下游阶段。

默认注入规则：

```yaml
contextPolicy:
  clarify:
    include: [task.md, sources/*/snapshot.md]
  solution:
    include: [artifacts/brief.md, artifacts/questions.md, artifacts/acceptance.md]
    requiresApproval: [clarify]
  plan:
    include: [artifacts/brief.md, artifacts/questions.md, artifacts/acceptance.md, artifacts/solution.md]
  implement:
    include: [artifacts/brief.md, artifacts/acceptance.md, artifacts/solution.md, artifacts/implementation-plan.md]
    requiresApproval: [plan]
  verify:
    include: [artifacts/implementation.md, artifacts/implementation-plan.md]
  test:
    include: [artifacts/acceptance.md, artifacts/verification.md]
```

系统可自动生成来源快照；`intake` 不调用 Agent。需求澄清、实施计划和测试报告必须经人工批准并提交 Git。上游方法论、阶段技能、用户任务和任务产物均记录在 Context Manifest 中；用户可显式增加上下文文件，所有覆盖都记录在运行记录中。

## 安全和验收

- 只读取显式提供的本地路径、公开 URL 或已授权连接器来源。
- 使用清晰分隔符传递来源文件、技能文本和用户任务，避免把不可信内容当作平台指令。
- 限制单个技能和单次注入上下文大小；超限时要求拆分。
- 记录技能版本、来源 revision、任务 ID、审批决定和注入文件清单，但默认不保存完整会话。

MVP 验收：能够安装并锁定引用 Superpowers 方法论的 Git 技能；从本地 Markdown 与公开 URL 创建快照；创建固定七阶段任务与实现子任务；阻止未批准或已失效的下游任务；组装限定上下文并通过 Codex Adapter 启动调用；记录可复现的本地运行元数据。
