# 研发工作流阶段规范（v1）

## 目的

本规范定义 `aiw` 管理复杂研发任务的固定七阶段工作流。它是阶段、产物、审批、上下文和失效传播的单一事实源。

`aiw` 不重新定义通用研发方法。每个阶段通过版本锁定的技能引用 Superpowers 等上游方法论；`aiw` 仅补充当前任务的输入、产物、审批和审计约束。

工作流终点为“测试验证完成并获批”。代码评审、合并、发布和线上运维继续使用团队既有流程，不属于 `aiw`。

## 默认工作流

```text
intake
  → clarify → 人工审批
  → solution
  → plan → 人工审批
  → implement
  → verify
  → test → 人工审批
```

七个节点 ID 是固定的，默认任务图为线性依赖。实现阶段可以在未来拆分为 API、前端、数据迁移等子任务，但子任务必须位于 `implement` 的下游范围内，并在进入 `verify` 前全部完成。

## 阶段定义

| 节点 | 目的 | 输入 | 必须产物 | 默认审批 | 方法论引用 |
|---|---|---|---|---:|---|
| `intake` | 固化任务和来源 | 用户任务、显式来源 | 来源快照、来源元数据 | 否 | 无；由 `aiw` 原生完成 |
| `clarify` | 澄清目标、范围、问题和验收 | 原始任务、来源快照 | `brief.md`、`questions.md`、`acceptance.md` | 是 | `superpowers:brainstorming` |
| `solution` | 形成技术方案、边界、取舍和风险 | 已批准的需求产物 | `solution.md` | 否 | `superpowers:brainstorming` 的方案设计方法 |
| `plan` | 拆分实施步骤、依赖和测试方式 | 需求产物、方案 | `implementation-plan.md` | 是 | `superpowers:writing-plans` |
| `implement` | 在业务仓库完成代码修改 | 已批准的需求、方案和实施计划 | `implementation.md`；业务代码由项目仓库保存 | 否 | `superpowers:using-git-worktrees`、`test-driven-development`、`executing-plans` |
| `verify` | 检查实现是否符合工程约束，并修复发现的问题 | 已批准方案、实施计划、实现说明；业务仓库 | `verification.md` | 否 | `superpowers:systematic-debugging`、`verification-before-completion` |
| `test` | 对照验收标准完成最终测试并汇总证据 | 已批准需求、方案、验收标准、验证结果；业务仓库 | `test-report.md` | 是 | `superpowers:verification-before-completion` |

`solution` 不单独设置默认人工审批：它作为 `plan` 的输入，技术负责人应在审批 `implementation-plan.md` 时一并审阅 `solution.md`。高风险任务可在任务模板中将 `solution.requiresApproval` 显式设为 `true`。

## 产物目录

```text
.aiw/tasks/<task-id>/
  task.yaml
  task.md
  sources/<source-id>/
    snapshot.md
    meta.json
  artifacts/
    brief.md
    questions.md
    acceptance.md
    solution.md
    implementation-plan.md
    implementation.md
    verification.md
    test-report.md
  approvals/<node-id>/
    r<revision>.yaml
  runs/<run-id>/
    context-manifest.json
    result.json
```

上述目录位于业务仓库并纳入 Git，是团队共享的任务事实。`request.json`、完整 `context.md`、完整 Codex 输出、会话运行态和临时文件只可写入 `~/.aiw/runtime/<run-id>/`；共享 `runs/` 中只保留去敏结果和可复现所需的 manifest、哈希与退出信息。

- `questions.md` 可以保留未决问题，但 `clarify` 获批前，必须明确哪些问题不阻塞后续阶段以及其假设。
- `implementation.md` 记录实现范围、关键变更、未解决限制和实际运行的验证命令；它不复制业务代码或替代 Git 提交记录。
- `verification.md` 记录代码级检查、失败项、修复结果和未覆盖风险。
- `test-report.md` 必须逐项对应 `acceptance.md`，记录测试方式、证据、结果和遗留问题。
- 任务模型中每个节点的 `outputs` 是该节点唯一允许写入的任务产物路径。

## 审批与状态

默认审批节点为 `clarify`、`plan` 和 `test`。

```text
clarify 获批后，solution 才能运行
plan 获批后，implement 才能运行
test 获批后，任务才能完成
```

审批必须绑定节点的确切 revision、全部输出哈希，并记录审批人、时间、结论和备注。待审批产物、`awaiting_approval` 状态和审批记录均须提交到当前 Git 分支；`changes_requested` 会将节点退回 `pending`；未获批或未提交的产物不得作为下游节点的默认输入。

`aiw` 写入审批事实但不替代 Git 审查。MVP 的审批人字段只是声明性身份；需要强身份与授权校验的团队，应使用受保护分支、CODEOWNERS、签名提交或 Git 平台 PR 审批。

## 最小上下文规则

业务代码始终由 Codex 在 `projectRoot` 内按需读取，不复制进任务上下文。每个运行只注入当前节点所需、处于当前 revision 且已满足审批条件的任务产物：

| 节点 | 默认注入的任务文件 |
|---|---|
| `clarify` | `task.md`、`sources/*/snapshot.md` |
| `solution` | `task.md`、`artifacts/brief.md`、`artifacts/questions.md`、`artifacts/acceptance.md` |
| `plan` | `brief.md`、`questions.md`、`acceptance.md`、`solution.md` |
| `implement` | `brief.md`、`acceptance.md`、`solution.md`、`implementation-plan.md` |
| `verify` | `brief.md`、`acceptance.md`、`solution.md`、`implementation-plan.md`、`implementation.md` |
| `test` | `brief.md`、`acceptance.md`、`solution.md`、`implementation-plan.md`、`implementation.md`、`verification.md` |

`intake` 不调用 Agent。用户可显式附加项目内文件，但附加文件必须写入 Context Manifest，并服从上下文预算和路径安全限制。Runner 仅将已提交的共享任务事实作为默认输入；本机临时文件不能成为可审批产物。

## 方法论引用与组合

阶段技能可以通过 `methodSources` 声明其复用的上游方法论：

```yaml
name: requirements-clarification
version: 1.0.0
phases: [clarify]
methodSources:
  - id: superpowers:brainstorming
    version: 6.2.0
```

`methodSources` 的规则如下：

1. 每项必须包含稳定 ID、版本和可解析来源；安装后记录其内容 SHA-256。
2. 阶段技能只允许增加当前节点的输入、产物、禁止事项和验证要求；不得复制、修改或伪造上游方法论正文。
3. Runner 依次注入不可变运行约束、节点契约、上游方法论、阶段技能叠加层、用户任务和来源/产物数据。
4. 上游方法、阶段技能、来源和任务产物均必须出现在 Context Manifest；任何版本、哈希或阶段不匹配都必须拒绝运行。
5. 上游方法与阶段叠加层发生冲突时，以 `aiw` 的不可变运行约束和节点契约为准；技能不得绕过审批、路径、预算或 sandbox 限制。

MVP 可先将 `methodSources` 作为强制记录与人工安装前提；自动解析、下载和组合上游技能可在确认使用模式后实现，不能静默替换已锁定的方法版本。

## 修订与失效传播

上游节点、来源快照或其实际产物产生新 revision 时，所有已开始的下游节点必须标记为 `invalidated`。旧产物只读保留，但不得继续自动注入。

| 变化来源 | 至少失效的下游范围 |
|---|---|
| 来源快照或 `intake` | `clarify` 至 `test` |
| `clarify` | `solution` 至 `test` |
| `solution` | `plan` 至 `test` |
| `plan` | `implement` 至 `test` |
| `implement` | `verify`、`test` |
| `verify` | `test` |

若 `test` 需要修改代码，开发者必须修订 `implement` 或更早的真实原因节点；不得只修改 `test-report.md` 以掩盖实现变化。

## 分阶段接入

固定七阶段是最终默认模型，但团队可按以下顺序启用，降低试点风险：

| 接入阶段 | 启用范围 | 验证目标 |
|---|---|---|
| 第一阶段：需求与方案治理 | `intake → clarify → solution → plan` | 验证来源快照、需求审批、方案与计划的可追溯性 |
| 第二阶段：受控实现 | 增加 `implement` | 验证 Codex Adapter 与 Superpowers 实施方法在真实仓库中的协作 |
| 第三阶段：质量闭环 | 增加 `verify → test` | 验证工程检查、验收证据与最终审批闭环 |

未启用的后续阶段不能被标记为完成或假定通过；试点任务可在已启用阶段结束，并明确记录其未覆盖范围。

## 非目标

- 不将 Superpowers 的每一个技能都建成独立任务节点；
- 不替代代码评审、PR、发布、CI/CD 或线上运维；
- 不要求所有小型改动进入七阶段工作流；
- 不允许 Agent 自动跳过阶段、审批或失效检查。
