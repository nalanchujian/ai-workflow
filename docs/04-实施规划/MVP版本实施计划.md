# MVP 版本实施计划

## 目标

完成一个本机、Git 原生的 AI 研发工作流 CLI：让研发需求沿“来源快照 → 事实/疑问拆分 → 决策关卡 → 业务单元图 → 单元交付 → 汇总交付状态”推进。目标不是让 AI 多生成文档，而是让大需求不因模糊输入、流程负担或上下文超限而失控。

## 已完成基座

1. CLI 基础：`init`、`doctor`、技能安装/升级、任务创建、状态、运行历史和安全清理。
2. 任务事实：任务 DAG、来源快照、节点当前产物、Handoff、决策、审批和运行证据均保存到 `.aiw/`。
3. 来源接入：本地文件、公开 URL 和经规则路由的受控文档连接器（当前 Lark MCP）。
4. 技能与方法：独立团队技能仓库、模板锁定、内置 Superpowers 方法来源、版本和哈希校验。
5. 任务治理：逐项需求决策、外部等待、来源刷新、下游失效、覆盖式重跑、风险接受。
6. Codex 执行：受控 Context Manifest、最小子进程环境、Git 基线/Diff/补丁证据与产物校验。
7. 交付单元：计划审批后为每个业务单元生成 `delivery-<unit-id>`；单元在一次运行内完成开发、工程验证、测试和验收，AIW 执行计划测试并将真实结果绑定到 AC，不再执行全局 `verify`、`test`。

## 为完成 MVP 目标仍需补齐的能力

### 1. 大来源的索引与分片

- 在 `intake` 后为大文档生成章节/领域索引和可追溯片段；
- 澄清与计划只加载当前领域片段，完整快照仅按需读取；
- 对表格、图片说明和跨章节引用保留回链，避免摘要失真。

### 2. 事实/疑问模型与决策影响图（已完成基础闭环）

- `clarify` 生成当前 `fact-register.yaml`，显式区分已确认事实、推断、待确认疑问和外部依赖，并要求每项事实回链来源快照；
- 决策、AC 和 `work-breakdown.yaml` 的每个交付单元都通过 `factRefs` / `decisionRefs` 建立引用；计划批准时生成并哈希绑定 `impact-graphs/plan.yaml`；
- 交付单元运行前校验当前影响图。新增会改变方案的外部事实或来源刷新仍保守地重新规划；基于领域片段的最小来源失效范围属于后续增强。

### 3. 按风险选择流程（已完成）

- 澄清完成后，而非任务创建时，基于来源大小、AC 数量、决策项和事实可信度生成可追溯的工作方式评估；
- 仅提供“快速修改 / 标准需求”两种路径。快速修改仍需要单元级代码、测试和变更证据，只跳过独立技术方案；
- 快速修改要求单来源、快照不超过 12,000 字、单一 AC、无决策和全部事实为已确认高可信。任一条件不满足即固定采用标准需求；
- 重新执行澄清或刷新来源会清除原选择并重新评估，避免旧结论继续影响新需求。

### 4. 超预算的拆分闭环

- 保留当前预算诊断；
- 自动给出可执行的来源切片、依赖收缩或业务单元拆分建议；
- 计划确认后才生成新单元，不能静默丢弃事实或自行改变业务范围。

### 5. 三层完成状态（已完成基础闭环）

- 明确区分节点运行状态、AC 验收状态和任务交付状态；
- 无 AIW 实际测试结果、无原始输出证据，或测试记录与批准的 AC 证据映射不一致时，不得显示“验收通过”；
- 风险接受始终保持显式的非绿色交付状态。

### 6. 独立执行区（尚未实现，不阻塞当前基础闭环）

- 当前 Codex 直接在干净的业务工作区执行，AIW 采集 Git 基线、Diff、补丁与哈希；
- 失败运行的业务改动会保留供用户检查，必须处理后才能继续；
- 后续可为每个交付单元创建临时 Git worktree，验证成功后再合入用户工作区，从根本上隔离失败副作用。

## 当前实施顺序

### 1. 领域与契约

- 标准需求主干为 `intake → clarify → solution → plan`；快速修改为 `intake → clarify → plan`，但后续共享同一交付单元闭环；
- 计划生成 `delivery-<unit-id>`，每个 AC 唯一归属；
- 用集成交付单元表达跨单元验收；
- 删除全局 `verify`、`test` 阶段及对应技能契约。

### 2. 执行与上下文

- 为每个单元生成隔离上下文；
- 默认只注入计划 Handoff、当前单元上下文和直接依赖 Handoff；
- 保留完整 Markdown 供审计，禁止将其默认汇总到末端节点；
- 运行前核验来源、上游产物和审批哈希，运行后保存 Diff 证据。

### 3. 用户体验

- `status` 显示业务单元名称而非内部 `implement` 锚点；
- `run` 是统一执行与重跑入口；
- `review` 专用于需求澄清；`approve` 专用于计划和交付单元；
- `close-with-risk` 仅作用于一个交付单元。

### 4. 验证

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm build
git diff --check
```

重点覆盖：单单元和多单元计划、依赖单元交接、唯一 AC 归属、阻塞/重跑、风险接受、来源/产物哈希失配，以及端到端的“来源切片→事实/决策→单元图→交付状态”闭环。
