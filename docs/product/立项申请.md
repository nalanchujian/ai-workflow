# AI Workflow 立项申请

## 一页结论

建议以 MVP 立项 `aiw`（AI Workflow）：一个运行在开发者本机、以 Git 共享任务事实的 AI 研发变更治理 CLI。它不替代 Codex，而是将团队的开发方法、需求资料、人工确认和执行记录组织为可复用、可审阅的工作流，再由 Codex 完成实际的代码工作。

`aiw` 也不以重写通用研发方法为目标：MVP 复用 Superpowers 的方法论，并将 Trellis 这类完整 Agent Harness 作为能力对标对象；在治理要求较低的场景，可作为降级选项评估。`aiw` 的独立价值是管理“当前哪些事实有效、谁已确认、变化后哪些结论必须重做”。

MVP 的目标不是提高单次提示词的生成量，而是降低复杂研发任务中“上下文丢失、过程不可审阅、结果不可复现”的交付风险。建议先面向一个开发团队、一个共享技能仓库和一类中等复杂度研发需求验证价值，再决定是否扩大投入。

本方案的“轻量工作流层”定位，以及与直接使用 Codex、Superpowers、Trellis 三条路径的取舍，见[AI Workflow 方案调研](方案调研.md)。

## 要解决的问题

复杂研发任务通常跨越需求理解、方案设计、实现与验证。当前依赖聊天记录、个人经验和手工交接时，容易出现：

- 团队方法分散，优秀实践难以复用和版本化；
- 在线需求与讨论上下文难以稳定传递，后续执行容易偏离；
- 需求、方案和实现之间缺少明确的人为确认点；
- 多步骤任务缺少状态、依赖和失效管理，上游变更后仍可能继续使用旧结论；
- 运行使用了哪些资料、技能和版本难以追溯，问题难以复现。

## 目标用户与核心场景

| 用户 | 主要诉求 | AI Workflow 提供的能力 |
|---|---|---|
| 开发者 | 用稳定方法推进复杂需求，减少重复整理上下文 | 本地技能缓存、Git 共享来源快照、分阶段任务与 Codex 调用 |
| 技术负责人 | 审阅关键结论，确保过程可追溯 | Git 可审阅的任务 DAG、审批 revision、版本和运行清单 |
| 团队管理者 | 让团队经验可复制，并控制 AI 研发过程风险 | Git 共享技能与任务事实、统一流程和可衡量的试点结果 |

典型场景：开发者收到一份在线需求文档，在业务分支创建任务；系统将经允许共享的来源固化为快照并提交 Git，依次推进需求澄清、技术方案、实施计划、实现、工程验证和验收测试；技术负责人在澄清、计划和最终测试阶段审阅确切 revision；每个阶段只获得经确认、已提交的必要上下文；Codex 在业务仓库中执行实际修改与测试。

## 产品方案

```text
共享技能仓库
    ↓ 安装并锁定版本
业务仓库中的共享任务事实：来源快照 + 子任务图 + 已确认产物 + 审批记录
    ↓ 按阶段选择最小上下文
人工审批关卡
    ↓
Codex CLI 执行分析、实现与验证
    ↓
Git 固化审计清单；本机保留原始运行数据
```

产品由四项能力组成：

1. **团队技能复用**：以 Git 管理声明式 `SKILL.md`，让方法可审阅、可版本化、可在团队内安装。
2. **复杂任务编排**：将需求固定为接入、澄清、方案、计划、实现、验证、测试七阶段；上游变更会使下游结果失效，避免沿用旧结论。
3. **人工关卡与最小上下文**：在需求澄清、实施计划和最终测试阶段由人确认；执行阶段仅注入当前节点所需、已确认的资料。
4. **Git 共享事实与本机执行**：业务仓库保存任务产物、审批 revision 和去敏运行清单；本机只保留技能缓存与原始运行数据。记录技能版本、来源版本、审批和执行输入。

### 与现有 AI 研发工具的分工

```text
Superpowers：提供通用研发方法
        ↓（被阶段技能锁定引用）
aiw：管理来源、审批、revision、失效与可信上下文
        ↓
Codex CLI：执行分析、编码与验证

Trellis：完整 Agent Harness 的能力对标对象；仅在不要求上述治理能力时，作为降级选项，不与 aiw 默认叠加
```

这一区分决定 MVP 不重复开发 Agent、子 Agent 调度或通用研发 Skill，也不同时维护 `.aiw/` 和 `.trellis/` 两套任务状态。管理层应以“复杂变更是否更可控、更可追溯、返工是否减少”判断 aiw 的投入价值，而不是比较单次代码生成量。

## MVP 范围

MVP 交付一个本机单 Agent CLI，覆盖：

- 从 Git 安装、校验和列出团队技能；
- 从本地 Markdown、公开 URL 或已配置 Lark MCP 创建来源快照，并在显式刷新后追踪来源 revision；
- 建立固定七阶段任务图，并允许在实现阶段扩展子任务；
- 对澄清、计划和测试设置人工审批；
- 锁定阶段技能引用的 Superpowers 方法论版本和内容哈希；
- 组装最小上下文并预演或调用 Codex CLI；
- 在业务仓库记录任务状态、审批、来源版本、技能版本和去敏运行结果。

MVP 明确不做：

- 云端调度、账号体系、权限平台或新的聊天系统；
- 多 Agent 自动协作或自动选择技能；
- 执行技能包内的任意脚本；
- 未经授权读取需登录的在线文档；
- 替代既有项目管理、代码评审或 CI/CD 系统。

## 预期价值与衡量方式

试点不以“调用次数”或“生成代码量”为成功标准，而以端到端研发结果衡量：

| 维度 | 试点观察指标 |
|---|---|
| 过程可控性 | 关键节点是否有明确产物、审批和责任人 |
| 可追溯性 | 是否能复原一次运行使用的来源、技能和上下文 |
| 交付效率 | 从需求资料确认到完成验证的总周期，以及重复整理上下文时间 |
| 质量 | 因需求理解偏差、漏用上下文或上游变更造成的返工次数 |
| 复用 | 团队技能被多个任务或成员使用的比例 |

试点结束后，与不使用 `aiw` 的同类任务进行对比；若未改善总交付周期、可追溯性或返工情况，则不扩大范围。

## 风险与前提

| 风险 | 管理要求 |
|---|---|
| 技能质量参差 | 技能以 Git 审阅和版本锁定管理，MVP 不执行技能附带脚本 |
| 不可信来源影响 Agent | 仅允许显式来源，使用快照、协议与大小限制，并隔离来源文本与平台指令 |
| 上下文过长或陈旧 | 限制上下文预算，仅传递当前阶段已确认产物；上游变更使下游失效 |
| 被误解为全自动研发 | 保留澄清、计划和测试的人工审批；Codex 仍是执行者而非决策替代者 |
| 审批记录不等于强身份认证 | MVP 使用 Git 提交共享事实；高可信团队通过受保护分支、CODEOWNERS 或 Git 平台 PR 审批加强认证 |
| 需求资料敏感 | 仅提交可由仓库读者访问的快照；敏感来源需先脱敏，不上传本机原始日志 |
| 试点范围失控 | 限定为一个团队、一类需求和单 Agent 串行流程 |

## 分阶段路线图与决策点

### 阶段一：MVP 验证

先完成 `intake → clarify → solution → plan`，验证来源快照、需求审批、方案和计划的可追溯性。

**决策点：** 是否能稳定完成需求与方案治理，并保留完整的来源、审批和计划追溯信息。

### 阶段二：团队试用

增加 `implement`，以真实业务仓库验证 Codex Adapter 与 Superpowers 实施方法的协作；沉淀首批高频技能并收集开发者反馈。

**决策点：** 是否降低了重复上下文整理和返工，同时没有引入新的交付瓶颈。

### 阶段三：扩大或停止

增加 `verify → test`，验证工程检查、验收证据和最终审批闭环；仅在指标明确改善时，评估扩展任务模板、更多来源接入或其他 Agent 适配器，否则保留为受限工具或停止继续投入。

## 当前需要的管理层决策

1. 批准以“本机单 Agent + Git 共享任务事实与团队技能仓库”为边界开展 MVP。
2. 指定一个试点团队与一类中等复杂度需求，并提供技术负责人作为审批责任人。
3. 同意以端到端交付结果、可追溯性和返工情况作为阶段性验收依据，而非代码生成量。
