# AI Workflow 研发使用与协作方案

## 目的

本方案说明研发团队如何使用 `aiw` 推进复杂需求，以及各角色在任务、技能、审批和业务代码中的责任边界。

它不定义底层数据结构、命令参数或 Codex 调用细节；这些以专项规范和 CLI 命令参考为准。

## 适用场景

`aiw` 适合需求资料较多、需要经过需求澄清与方案评审、并且实现结果需要可追溯的研发任务，例如：

- 根据在线需求文档实现一个中等复杂度功能；
- 对跨前端、后端和测试的改动形成统一实施方案；
- 复用团队已验证的需求分析、方案设计或测试方法；
- 在上游需求变化后，明确哪些结论和实现需要重新确认。

它不适合替代快速的小型代码修改、日常即时沟通、代码评审或 CI/CD。

## 角色与责任

| 角色 | 主要责任 | 不负责 |
|---|---|---|
| 任务发起开发者 | 在任务分支创建并提交任务事实、提供来源、选择显式技能、推进节点并在业务仓库执行 | 代替技术负责人批准关键结论 |
| 技术负责人 | 审阅 Git 中的需求澄清、实施计划和最终测试 revision；批准、要求修订或继续 | 代替开发者执行日常代码修改 |
| 技能维护者 | 维护阶段叠加层、上游方法论引用、版本和验证要求 | 直接修改每个业务任务的产物 |
| `aiw` | 管理 Git 共享的快照、任务状态、依赖、审批、上下文和运行清单 | 判断业务结论、执行 Git 提交或替代人工审批 |
| Codex | 在指定业务仓库中分析、修改代码并运行测试 | 管理任务状态、绕过审批或自行选择技能 |

## 日常工作流

```text
需求资料
  ↓
开发者创建任务和来源快照
  ↓
需求澄清 → 技术负责人审批
  ↓
技术方案 → 实施计划 → 技术负责人审批
  ↓
实现 → 工程验证 → 验收测试 → 技术负责人审批
  ↓
完成或根据上游变更重新推进
```

### 1. 准备技能

开发者安装团队审核过的技能仓库，并确认所需技能可用：

```bash
aiw skills install git@github.com:your-org/agent-skills.git
aiw skills list
```

技能不是自动匹配的。任务发起者应根据阶段和实际目标明确选择技能；技能版本会随任务记录，保证后续可追溯。

### 2. 创建任务与固化来源

开发者在业务任务分支中以业务项目和需求来源初始化任务：

```bash
aiw task init refund-123 --project . --source https://example.com/requirements
```

系统将可共享的来源固化为业务仓库 `.aiw/` 中的快照，避免在线文档后续修改被静默带入已有结论。开发者先按既有 Git 流程提交初始化事实；任务默认包含 `intake → clarify → solution → plan → implement → verify → test` 七阶段；`intake` 自动完成，不调用 Agent。

### 3. 逐阶段推进与审批

开发者依次运行已就绪节点；每次运行生成的阶段产物须先提交 Git。`clarify`、`plan` 和 `test` 结束后必须由技术负责人确认当前 revision，并提交审批记录，才能推动下游节点或完成任务。阶段技能引用已锁定的 Superpowers 方法论，`aiw` 只补充当前阶段产物和审批约束。

```bash
aiw task run refund-123 clarify --skill requirements-clarification
aiw task approve refund-123 clarify
aiw task run refund-123 solution --skill technical-solution
aiw task run refund-123 plan --skill implementation-planning
aiw task approve refund-123 plan
```

审批的对象是当前节点 revision 的产物哈希，而不是一次笼统同意。需要补充内容时，技术负责人要求修订；系统会标记已开始的下游节点失效，避免继续使用旧结论。MVP 中审批文件的身份字段是协作记录；需要强校验时，团队以受保护分支、CODEOWNERS 或 PR 审批作为外部凭据。

### 4. 实现与验证

在方案获批后，开发者启动实现节点。Codex 在指定业务仓库中读取必要代码、修改文件并运行测试；`aiw` 负责保留任务上下文与运行结果。

```bash
aiw task run refund-123 implement --skill implementation
aiw task run refund-123 verify --skill implementation-verification
aiw task run refund-123 test --skill acceptance-testing
aiw task approve refund-123 test
```

业务代码的提交、代码评审、发布和 CI/CD 仍遵循团队既有流程，不由 `aiw` 取代。

## 任务产物与协作规则

| 阶段 | 主要产物 | 使用规则 |
|---|---|---|
| `intake` | 来源快照与元数据 | 提交 Git 后作为澄清依据；来源变化需重新确认。 |
| `clarify` | 需求摘要、待确认问题、验收标准 | 产物和审批 revision 均提交后才可作为方案输入。 |
| `solution` | 技术方案、边界、取舍与风险 | 作为计划输入；与计划一并审阅。 |
| `plan` | 实施计划 | 产物和审批 revision 均提交后才可作为实现输入。 |
| `implement` | 业务代码与实现说明 | 由开发者与既有代码评审流程负责。 |
| `verify` | 工程验证与修复记录 | 作为测试输入。 |
| `test` | 验收测试证据 | 经审批后任务完成。 |

协作时遵循四条规则：

1. 不把聊天记录当作任务上下文；关键结论应沉淀为任务产物。
2. 不绕过审批使用未确认的上游产物。
3. 上游需求、方案或来源发生变化时，使用修订流程，而不是手动继续沿用旧结果。
4. 技能改动通过技能仓库审阅和版本管理；不得为了单个任务直接修改已锁定的技能内容。
5. 共享 `.aiw/` 是任务事实，不提交完整提示词、原始 Codex 输出、令牌或本机路径；这些数据保留在 `~/.aiw/`。

## 常见场景

### 需求文档更新

需求来源或澄清结论改变后，开发者修订受影响节点。系统使 `solution` 至 `test` 的已开始节点失效；开发者重新运行并按需重新审批，而不是混用旧方案和新需求。

### 实现阶段发现方案缺口

开发者应修订 `solution`、`plan` 或更早的真实原因节点并说明原因。计划重新获批前，不应把临时实现直接当作最终结论；这样可让后续测试使用正确的验收依据。

### 紧急小修改

无需拆解、没有关键审批或上下文沉淀价值的小修改，可以直接使用现有开发流程与 Codex，不强制进入 `aiw`。

## MVP 使用边界

- 仅支持本机、单 Agent、单节点串行执行；
- 仅使用显式安装和选择的声明式技能；
- 仅接入本地文件、公开 URL 或已授权来源；
- 关键结论仍由人批准，业务代码最终质量仍由开发团队负责。
