# AI Workflow 研发使用与协作方案

## 目的

本方案说明研发团队如何使用 `aiw` 推进复杂需求，以及各角色在任务、技能、审批和业务代码中的责任边界。

它不定义底层数据结构、命令参数或 Codex 调用细节；这些以专项规范和 CLI 命令参考为准。

## 适用场景

`aiw` 适合需求资料较多、需要经过需求澄清与方案评审、并且实现结果需要可追溯的研发任务，例如：

- 根据在线需求文档实现一个中等复杂度功能；
- 对跨前端、后端和测试的改动形成统一实施方案；
- 复用团队已验证的需求分析、方案设计或测试方法；
- 在上游需求变化后，明确哪些结论和实现需要重新确认。

它不适合替代快速的小型代码修改、日常即时沟通、代码评审或 CI/CD。

## 角色与责任

| 角色 | 主要责任 | 不负责 |
|---|---|---|
| 任务发起开发者 | 创建任务、提供来源、选择显式技能、推进节点并在业务仓库执行 | 代替技术负责人批准关键结论 |
| 技术负责人 | 审批需求、方案和验证产物；决定修订或继续 | 代替开发者执行日常代码修改 |
| 技能维护者 | 维护 `SKILL.md` 的内容、版本、适用阶段和验证要求 | 直接修改每个业务任务的产物 |
| `aiw` | 管理快照、任务状态、依赖、审批、上下文和运行记录 | 判断业务结论或替代人工审批 |
| Codex | 在指定业务仓库中分析、修改代码并运行测试 | 管理任务状态、绕过审批或自行选择技能 |

## 日常工作流

```text
需求资料
  ↓
开发者创建任务和来源快照
  ↓
需求分析 → 技术负责人审批
  ↓
方案设计 → 技术负责人审批
  ↓
实现 → 测试与验证 → 技术负责人审批
  ↓
完成或根据上游变更重新推进
```

### 1. 准备技能

开发者安装团队审核过的技能仓库，并确认所需技能可用：

```bash
aiw skills install git@github.com:your-org/agent-skills.git
aiw skills list
```

技能不是自动匹配的。任务发起者应根据阶段和实际目标明确选择技能；技能版本会随任务记录，保证后续可追溯。

### 2. 创建任务与固化来源

开发者以业务项目和需求来源初始化任务：

```bash
aiw task init refund-123 --project . --source https://example.com/requirements
```

系统将来源固化为本地快照，避免在线文档后续修改被静默带入已有结论。任务默认包含资料接入、分析、设计、实现和测试节点。

### 3. 逐阶段推进与审批

开发者依次运行已就绪节点；分析、设计和测试结束后必须由技术负责人确认，才能推动下游节点。

```bash
aiw task run refund-123 analysis --skill requirements-analysis
aiw task approve refund-123 analysis
aiw task run refund-123 design --skill architecture-design
aiw task approve refund-123 design
```

审批的对象是当前节点 revision 的产物，而不是一次笼统同意。需要补充内容时，技术负责人要求修订；系统会标记已开始的下游节点失效，避免继续使用旧结论。

### 4. 实现与验证

在方案获批后，开发者启动实现节点。Codex 在指定业务仓库中读取必要代码、修改文件并运行测试；`aiw` 负责保留任务上下文与运行结果。

```bash
aiw task run refund-123 implementation --skill implementation
aiw task run refund-123 testing --skill testing
aiw task approve refund-123 testing
```

业务代码的提交、代码评审、发布和 CI/CD 仍遵循团队既有流程，不由 `aiw` 取代。

## 任务产物与协作规则

| 阶段 | 主要产物 | 使用规则 |
|---|---|---|
| 资料接入 | 来源快照与元数据 | 作为分析依据；来源变化需重新确认。 |
| 分析 | 需求摘要、待确认问题、验收标准 | 经审批后才可作为设计输入。 |
| 设计 | 技术方案与实施计划 | 经审批后才可作为实现输入。 |
| 实现 | 业务代码与任务声明的产物 | 由开发者与既有代码评审流程负责。 |
| 测试 | 验证结果 | 经审批后任务完成。 |

协作时遵循四条规则：

1. 不把聊天记录当作任务上下文；关键结论应沉淀为任务产物。
2. 不绕过审批使用未确认的上游产物。
3. 上游需求、方案或来源发生变化时，使用修订流程，而不是手动继续沿用旧结果。
4. 技能改动通过技能仓库审阅和版本管理；不得为了单个任务直接修改已锁定的技能内容。

## 常见场景

### 需求文档更新

需求来源或分析结论改变后，开发者修订受影响节点。系统使已开始的下游节点失效；开发者重新运行并按需重新审批，而不是混用旧方案和新需求。

### 实现阶段发现方案缺口

开发者应修订设计节点并说明原因。方案重新获批前，不应把临时实现直接当作最终结论；这样可让后续测试使用正确的验收依据。

### 紧急小修改

无需拆解、没有关键审批或上下文沉淀价值的小修改，可以直接使用现有开发流程与 Codex，不强制进入 `aiw`。

## MVP 使用边界

- 仅支持本机、单 Agent、单节点串行执行；
- 仅使用显式安装和选择的声明式技能；
- 仅接入本地文件、公开 URL 或已授权来源；
- 关键结论仍由人批准，业务代码最终质量仍由开发团队负责。
