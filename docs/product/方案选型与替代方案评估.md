# AI Workflow 方案对比

## 决策结论

MVP 选择构建 `aiw` 这一层轻量、Git 原生且本机执行的研发任务工作流：复用 Codex CLI 与 Superpowers，而不将 Trellis 作为产品本体。

这不是从零实现编码 Agent：`aiw` 复用 Codex CLI 的代码分析、修改与测试能力，复用 Superpowers 的通用研发方法论；它只负责团队研发中缺少的技能版本、来源快照、任务依赖、人工审批、上下文控制和运行追溯。

该结论应在 MVP 试点后复核。若已有工具经验证能以更低成本满足这些治理要求，应优先采用或集成，而不是继续扩展自研能力。

## 要回答的管理问题

| 问题 | 本文回答 |
|---|---|
| 为什么不直接使用 Codex？ | 直接使用适合单次编码；`aiw` 补充跨阶段任务和团队治理，不替代 Codex。 |
| 为什么不直接采用 Trellis？ | Trellis 是完整 Agent Harness；若要满足 `aiw` 的治理契约，仍需承担较高的持续改造成本。 |
| 为什么不是搭建大型平台？ | MVP 的目标是验证工作流价值，故选择单 Agent、本机 CLI，避免过早引入云端、账号和运维复杂度。 |
| 什么时候应停止自建？ | 试点中若现有工具能以更低总成本满足关键约束，或 `aiw` 未改善端到端结果，就停止扩大。 |

## 评估原则

选型不以“功能数量”或“是否开源”作为首要标准，而以是否满足以下约束为准：

1. **本机执行与业务仓库优先**：能在开发者指定的真实仓库中工作；任务事实随 Git 共享，不要求迁移到云端新平台。
2. **团队方法可治理**：技能可经 Git 审阅、版本锁定，并可追溯某次运行实际使用的内容。
3. **复杂任务可控**：支持阶段产物、依赖、人工审批，以及上游变更后的下游失效。
4. **上下文最小且可追溯**：能记录来源、注入文件和版本，避免把整段聊天记录或不可信资料直接混入执行。
5. **低引入成本**：MVP 不新增云端服务、账号体系、运行集群或多 Agent 调度。
6. **可替换执行器**：业务工作流不绑定单一模型或 Agent；Codex 是首个 Adapter，而非不可替换的系统核心。

## 与直接使用 Codex、Superpowers、Trellis 的对比

| 路径 | 已解决的核心问题 | 相对 `aiw` 的缺口或成本 | `aiw` 的定位 |
|---|---|---|---|
| 直接使用 Codex CLI、`AGENTS.md` 和 Skills | 单个开发者在本地理解、修改和测试代码 | 缺少项目外的统一任务快照、审批产物、依赖与失效记录 | **直接复用为执行层**，不重复实现编码能力 |
| Superpowers | 为 Coding Agent 提供通用研发方法与 Skill | 不管理团队级来源 revision、审批事实和失效传播 | **直接复用为方法论来源**，由 aiw 阶段技能锁定引用，不重写通用方法 |
| Trellis | 为 Coding Agent 提供任务、Spec、Skill、Hook、子 Agent 与多平台工作流 | 若要满足 `aiw` 的版本化审批、可信来源、失效传播，需持续改造任务模型、上下文注入与执行门禁；叠加使用还会形成两套任务事实 | **能力对标对象**；仅在不要求上述治理能力时，作为降级选项。MVP 不作为依赖或部分 Skill 来源 |

结论不是“用 `aiw` 替掉三者”：Codex 继续执行代码工作，Superpowers 继续提供通用方法，Trellis 作为完整 Harness 的能力对标。`aiw` 只补齐三者都不以团队级事实治理为核心的部分：版本化事实、审批与失效传播。[Superpowers](https://github.com/obra/superpowers)、[Trellis](https://github.com/mindfold-ai/Trellis)

## 三者的产品边界

```text
Superpowers：通用方法论层
aiw：复杂研发变更治理层
Codex：代码执行层

Trellis：完整 Agent Harness 的能力对标对象；
         不要求变更治理时可作为降级选项，但不应在 MVP 中与 aiw 共同维护同一任务。
```

当前决策是：`aiw + Superpowers + Codex`。这不是否定 Trellis，而是避免在 MVP 同时引入两套任务状态、上下文注入和工作流规则。若要让 Trellis 承担 `aiw` 的治理职责，需要对任务模型、上下文注入和执行门禁做高成本、持续性的改造；因此不将其视为现成的同级替代方案。它应保持独立使用，或仅在明确的低治理要求场景作为降级选项；若需与 `aiw` 集成，必须设计单向 Adapter，不能让两者共同成为任务事实源。

## 为什么不是“直接使用 Codex”

Codex 负责在工作目录中分析、修改和测试代码，已经解决“谁来执行”的问题。`aiw` 解决的是复杂研发任务中“执行前后如何被团队管理”的问题：

```text
直接使用 Codex
  用户任务 + 当前对话 / 本地说明
  → 代码执行

使用 aiw + Codex
  Git 技能 + Git 共享来源快照 + 任务 DAG + 已确认产物 + 审批记录
  → 受控上下文
  → Codex 代码执行
  → 可追溯运行结果
```

Codex CLI 是本地运行的编码 Agent，具备多模态输入等执行能力；本项目不复制这些能力，而通过 Adapter 保持执行器可替换。[Codex CLI 官方说明](https://help.openai.com/en/articles/11096431)

## 为什么当前不采用 Trellis 作为主路径

Trellis 是完整 Agent Harness，但要使其承担 `aiw` 的治理职责，仍需完成以下工作：

- 将团队任务模型、审批和失效规则翻译为平台的状态模型；
- 建立本地项目路径、来源安全、技能版本锁定与日志脱敏的约束；
- 为团队成员提供 CLI 或界面、权限和故障处理方式；
- 维护平台升级、依赖漏洞、部署和运行环境。

当这些工作量接近 `aiw` 自身时，直接依赖 Trellis 不会减少总体成本，反而会扩大 MVP 的运行边界。因此 MVP 先以 Node.js CLI 实现必要的治理契约；只有在需要长时间运行、多 Agent、服务化调度或跨团队共享状态时，再重新比较采用 Trellis 与扩展现有实现的成本。

## 试点验证与退出条件

MVP 必须与“直接使用 Codex”的同类任务对照，并记录：

| 维度 | 验证问题 |
|---|---|
| 交付周期 | 从需求确认到验证完成，是否缩短或至少不显著增加？ |
| 返工 | 是否减少因上游变更、遗漏上下文和未确认方案导致的返工？ |
| 可追溯性 | 是否能复原每次运行使用的来源、技能、审批和上下文？ |
| 使用成本 | 开发者创建与推进任务的额外操作是否可接受？ |
| 技术成本 | 是否保持本机优先，且未引入额外服务运维负担？ |

出现以下任一情况时，不应扩大 `aiw` 的自研范围：

- 试点未改善交付、返工或可追溯性；
- 开发者绕开工作流，说明任务粒度或操作成本不匹配；
- 现有工具经过验证可满足关键约束，且迁移、部署和维护成本更低；
- 新需求已超出本机单 Agent 边界，需要重新进行平台化选型。

## 需要管理层确认的原则

1. 以“复用执行器、补齐治理缺口”为投入边界，不以自建 Agent 平台为目标。
2. 允许在试点后根据数据选择集成、替换或停止，而非预设必须长期自研。
3. 将直接使用 Codex作为基线方案；任何自研能力都必须证明其带来额外的过程可控性或交付收益。
