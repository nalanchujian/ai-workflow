# AI Workflow 方案选型与替代方案评估

## 决策结论

MVP 选择构建 `aiw` 这一层轻量、Git 原生且本机执行的研发任务工作流，而不直接以某个通用开源 Agent 平台作为产品本体。

这不是从零实现编码 Agent：`aiw` 复用 Codex CLI 的代码分析、修改与测试能力，只负责团队研发中缺少的技能版本、来源快照、任务依赖、人工审批、上下文控制和运行追溯。

该结论应在 MVP 试点后复核。若已有工具经验证能以更低成本满足这些治理要求，应优先采用或集成，而不是继续扩展自研能力。

## 要回答的管理问题

| 问题 | 本文回答 |
|---|---|
| 为什么不直接使用 Codex？ | 直接使用适合单次编码；`aiw` 补充跨阶段任务和团队治理，不替代 Codex。 |
| 为什么不直接使用开源 Agent 平台？ | 先判断它能否满足本机、研发仓库、任务审批和可追溯性要求；不能仅因“开源”而忽略集成与运维成本。 |
| 为什么不是搭建大型平台？ | MVP 的目标是验证工作流价值，故选择单 Agent、本机 CLI，避免过早引入云端、账号和运维复杂度。 |
| 什么时候应停止自建？ | 试点中若现有工具能以更低总成本满足关键约束，或 `aiw` 未改善端到端结果，就停止扩大。 |

## 评估原则

选型不以“功能数量”或“是否开源”作为首要标准，而以是否满足以下约束为准：

1. **本机执行与业务仓库优先**：能在开发者指定的真实仓库中工作；任务事实随 Git 共享，不要求迁移到云端新平台。
2. **团队方法可治理**：技能可经 Git 审阅、版本锁定，并可追溯某次运行实际使用的内容。
3. **复杂任务可控**：支持阶段产物、依赖、人工审批，以及上游变更后的下游失效。
4. **上下文最小且可追溯**：能记录来源、注入文件和版本，避免把整段聊天记录或不可信资料直接混入执行。
5. **低引入成本**：MVP 不新增云端服务、账号体系、运行集群或多 Agent 调度。
6. **可替换执行器**：业务工作流不绑定单一模型或 Agent；Codex 是首个 Adapter，而非不可替换的系统核心。

## 替代方案对比

| 方案 | 适合解决的问题 | 关键不足或成本 | 对 `aiw` 的选择 |
|---|---|---|---|
| 直接使用 Codex CLI、`AGENTS.md` 和 Skills | 单个开发者在本地理解、修改和测试代码 | 缺少项目外的统一任务快照、审批产物、依赖与失效记录 | **直接复用为执行层**，不重复实现编码能力 |
| OpenHands 等编码 Agent 平台 | 使用通用软件开发 Agent 或 SDK 执行工程任务 | 仍需验证其是否符合本机任务数据、团队技能治理和审批模型；引入新运行时与运维边界 | **保留为未来 Adapter 候选**，不作为 MVP 前提 |
| LangGraph 等 Agent 编排框架 | 需要以代码构建持久执行、人机协作和状态化流程 | 提供底层编排原语，不直接提供本项目的 CLI、任务契约、技能供应链或本机安全边界；仍需研发和维护应用层 | **后续可评估为内部实现底座**，MVP 不引入 |
| Flowise、Dify 等可视化 LLM 工作流平台 | 快速搭建聊天、RAG、业务自动化或可视化 Agent 流程 | 主要面向 LLM 应用和服务化工作流，与“本地业务仓库中的研发任务”并不完全匹配；需额外评估部署与安全面 | **不作为当前主路径** |
| 自建完整 Agent 平台 | 对模型、工具、调度和权限有强控制要求 | 成本、运维和安全责任显著扩大，超出 MVP 验证目标 | **明确不做** |

OpenHands 定位为可执行实际软件工程工作的开发 Agent 平台；LangGraph 提供持久化执行与 human-in-the-loop 等编排能力；Flowise 则定位为构建 LLM 应用和 Agent 工作流的平台。它们可作为组件或替代路径被评估，但不是对当前问题的同一层级答案。[OpenHands](https://www.openhands.dev/)、[LangGraph](https://langchain-ai.github.io/langgraph/index.html)、[Flowise](https://docs.flowiseai.com/)

## 为什么不是“直接使用 Codex”

Codex 负责在工作目录中分析、修改和测试代码，已经解决“谁来执行”的问题。`aiw` 解决的是复杂研发任务中“执行前后如何被团队管理”的问题：

```text
直接使用 Codex
  用户任务 + 当前对话 / 本地说明
  → 代码执行

使用 aiw + Codex
  Git 技能 + Git 共享来源快照 + 任务 DAG + 已确认产物 + 审批记录
  → 受控上下文
  → Codex 代码执行
  → 可追溯运行结果
```

Codex CLI 是本地运行的编码 Agent，具备多模态输入等执行能力；本项目不复制这些能力，而通过 Adapter 保持执行器可替换。[Codex CLI 官方说明](https://help.openai.com/en/articles/11096431)

## 为什么不先引入通用编排平台

通用平台并不等于零成本方案。引入它们仍需完成以下工作：

- 将团队任务模型、审批和失效规则翻译为平台的状态模型；
- 建立本地项目路径、来源安全、技能版本锁定与日志脱敏的约束；
- 为团队成员提供 CLI 或界面、权限和故障处理方式；
- 维护平台升级、依赖漏洞、部署和运行环境。

当这些工作量接近 `aiw` 自身时，直接依赖通用平台并不会减少总体成本，反而会扩大 MVP 的运行边界。因此 MVP 先以 Node.js CLI 实现必要的治理契约；只有在需要长时间运行、多 Agent、服务化调度或跨团队共享状态时，再重新比较引入框架与扩展现有实现的成本。

## 试点验证与退出条件

MVP 必须与“直接使用 Codex”的同类任务对照，并记录：

| 维度 | 验证问题 |
|---|---|
| 交付周期 | 从需求确认到验证完成，是否缩短或至少不显著增加？ |
| 返工 | 是否减少因上游变更、遗漏上下文和未确认方案导致的返工？ |
| 可追溯性 | 是否能复原每次运行使用的来源、技能、审批和上下文？ |
| 使用成本 | 开发者创建与推进任务的额外操作是否可接受？ |
| 技术成本 | 是否保持本机优先，且未引入额外服务运维负担？ |

出现以下任一情况时，不应扩大 `aiw` 的自研范围：

- 试点未改善交付、返工或可追溯性；
- 开发者绕开工作流，说明任务粒度或操作成本不匹配；
- 现有工具经过验证可满足关键约束，且迁移、部署和维护成本更低；
- 新需求已超出本机单 Agent 边界，需要重新进行平台化选型。

## 需要管理层确认的原则

1. 以“复用执行器、补齐治理缺口”为投入边界，不以自建 Agent 平台为目标。
2. 允许在试点后根据数据选择集成、替换或停止，而非预设必须长期自研。
3. 将直接使用 Codex作为基线方案；任何自研能力都必须证明其带来额外的过程可控性或交付收益。
