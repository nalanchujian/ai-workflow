# AI Workflow 用户使用手册

## 这份手册解决什么问题

本手册面向使用 `aiw` 推进研发任务的开发者，说明如何从安装、环境检查到完成一个可追溯的七阶段任务。

`aiw` 不是替代 Git、Codex 或团队技能包的工具：它将需求快照、任务状态、阶段产物和审批记录保存在业务仓库的 `.aiw/` 中；Codex 与可选文档连接器仍在使用者本机运行，但标准技能所依赖的方法由团队技能包随版本提供。

普通开发者首次使用只需完成“安装 → 初始化 → 创建任务 → 按每次命令给出的下一步推进 → 提交 `.aiw/`”这条主路径。技能升级、连接器排障、风险关闭、历史迁移和运行记录清理都放在后文按需查阅。

## 1. 安装与检查

需要 Node.js 22 LTS 或 24+，不要使用 Node.js 23。

```bash
npm install -g @nalanchujian/ai-workflow
aiw --version
aiw init

# 在业务仓库中执行
cd /path/to/business-repository
aiw doctor --project .
```

`doctor` 会检查 Git、业务仓库是否允许提交 `.aiw/`、Codex CLI、本机配置、已安装的团队方法和文档连接器。按输出中的修复建议解决 `failed` 项；未使用在线文档连接器时，相关的 `warning` 不阻止本地或公开 URL 来源的任务。

## 命令执行进度

`aiw` 在交互式终端中会为可能耗时的操作显示当前状态和等待时间，例如初始化、技能安装或更新、创建/刷新任务来源、运行节点、环境检查和运行记录清理。进度写入 stderr，不影响最终结果输出。

`status`、审批、修订等瞬时命令直接显示结果，避免无意义地闪烁进度。默认输出统一为“结论 → 关键信息 → 下一步”，方便直接阅读；使用 `--json` 时 stdout 始终只输出一个 JSON 文档，适用于脚本、CI 和管道。非交互环境会自动关闭进度，但仍保持默认的可读输出；需要机器解析时请显式传入 `--json`。

常用的升级和卸载命令：

```bash
npm update -g @nalanchujian/ai-workflow
npm uninstall -g @nalanchujian/ai-workflow
```

## 首次完成一个任务：主路径

在业务仓库中按下面步骤执行。`<task-id>` 由创建任务后的输出提供，无需手动编写；每次会写入 `.aiw/` 的操作后都应提交，才能成为下一节点的可信输入。

```bash
# 1. 初始化本机环境并检查业务仓库
aiw init
cd /path/to/business-repository
aiw doctor --project .

# 2. 创建任务并固化需求来源
aiw task init --project . --source ./requirements.md
git add .aiw && git commit -m "chore(aiw): initialize task"

# 3. 澄清需求并逐项确认
aiw task run <task-id> clarify
git add .aiw && git commit -m "chore(aiw): record clarify result"
aiw task review <task-id>
git add .aiw && git commit -m "chore(aiw): review clarification"

# 4. 形成方案和计划；每个节点完成后先提交
aiw task run <task-id> solution
git add .aiw && git commit -m "chore(aiw): record solution result"
aiw task run <task-id> plan
git add .aiw && git commit -m "chore(aiw): record plan result"
aiw task approve <task-id> plan --note "实施计划确认"
git add .aiw && git commit -m "chore(aiw): approve plan"

# 5. 后续直接执行每次命令输出的下一步
```

计划批准后，单一实施目标使用 `implement`；复杂任务会拆成多个 `implement-*` 工作单元，原始 `implement` 不再对用户展示或执行。不要手工猜测节点名称：复制当前命令输出的下一条 `aiw task run ...` 命令执行。实施单元完成后，先检查本次业务代码 diff，并将业务代码与 `.aiw` 一并按团队 Git 流程提交；验证或测试节点完成后提交 `.aiw`，再执行输出中的审批或下一节点命令。测试待审批时，命令会直接引导你查看报告、提交事实并批准；全部验收通过后任务闭环。

## 按需配置：受控在线文档连接器

个人配置文件位于 `~/.aiw/config.yaml`。它不应提交到业务仓库，也不能包含在团队技能仓库中。

执行 `aiw init` 后，文件会带有中文注释，并自动安装配置中默认的 `standard-web-feature@4.0.0` 工作流。标准团队技能包已随版本提供和锁定所需的 Superpowers 方法，因此不要添加 `methodSources`，也无需单独安装 Superpowers。

如果 Codex 已配置唯一兼容的文档 MCP，`aiw init` 会读取其工具清单并自动写入本机连接器映射；不复制凭据，也无需填写 Server 或工具名称。当前自动发现支持 Lark MCP。若出现多个候选，命令会列出名称，使用者只需选择一次：

```bash
aiw init --connector-server <命令输出中的候选名称>
```

未发现候选时，先在 Codex 配置团队使用的文档 MCP 后重新运行 `aiw init`。自动发现不会覆盖已有连接器映射。完成后可验证：

```bash
aiw doctor --project .
```

从旧版本升级时，若配置中存在 `methodSources`，请先删除该字段及其全部内容；当前版本会明确拒绝它，也不会继续读取本机 Superpowers 目录。旧任务需要使用内置方法版技能包重新创建。

如需以受控在线文档为需求来源，先运行上述自动发现流程；当前内置连接器支持 Lark `docx` 或 Wiki。只有自动发现不支持团队的 MCP 时，才由维护者在 `~/.aiw/config.yaml` 补充映射。字段和限制见 [Lark 来源连接器规范](../03-方案设计/03-接入与接口/Lark来源连接器规范.md)。不要把连接器凭据、token 或 Codex 配置复制到 `.aiw/`。

## 按需维护：默认工作流与技能更新

首次 `aiw init` 已自动安装官方默认技能包，无需输入技能仓库地址、版本或模板名称。默认配置保存在 `~/.aiw/config.yaml`，而安装后的 revision、哈希与许可证校验结果保存在本机 Registry。

```bash
aiw skills profiles list
```

团队发布新技能 tag 后，使用者需要采用新版时才显式更新：

```bash
aiw skills update --ref v4.0.0
```

更新先完成技能安装和校验，再将本机默认 Git tag 与同名工作流模板的新版本一并切换；例如 `standard-web-feature@3.0.0` 会切换为新包提供的 `standard-web-feature@4.0.0`。新包缺少同名模板时配置保持不变。新建任务默认使用本机配置的模板；需要采用其他已安装模板时，才显式传入 `--skill-profile <name@version>`。模板会一次锁定 `clarify` 至 `test` 的方法和版本；不要在任务进行中以“当前安装的最新技能”替代任务已经锁定的技能。Registry 按 Git revision 保留同一来源的多个已安装版本，因此旧任务可以继续解析自己的技能锁定；仅在确认没有未完成任务引用时才应清理旧版本。

## 创建任务的详细规则

在业务仓库中准备好可共享的需求来源后创建任务。来源可以是仓库内 Markdown 文件、符合安全规则的公开 HTTP(S) 地址，或已配置文档连接器支持的在线文档地址；当前内置连接器支持 Lark `docx` / Wiki URL。

```bash
aiw task init \
  --project . \
  --source ./requirements.md
```

较大的需求文档可只固化一个章节（前提是对应连接器支持章节读取）：

```bash
aiw task init \
  --project . \
  --source https://<tenant>.larksuite.com/wiki/<node-token> \
  --section "订单退款流程"
```

章节标题必须在文档中唯一；快照包含该标题及其子标题内容。后续 `source refresh` 会继续刷新同一章节，而不是整篇文档。`--section` 仅适用于地址可被已配置连接器识别的文档；本地文件和公开 URL 会明确拒绝该参数。当前 Lark 实现首次使用章节功能前，需要在 Codex 的 Lark MCP 启动参数中添加 `-t` 与 `preset.default,docx.v1.documentBlock.list`，然后重启 MCP；这是开启文档块读取工具，不需要新增 Lark 权限或填写凭据。

命令默认会显示“需求已固化，任务已创建”，并列出任务 ID、锁定的工作流和下一步提交命令，例如：

```text
任务 ID：task-20260813-120000-000
默认工作流：standard-web-feature@4.0.0
整体状态：进行中
```

脚本或 CI 需要机器读取时，才加全局参数 `--json`，此时 stdout 输出单个 JSON 对象。

无需、也不能手动指定任务 ID。复制该 `taskId` 用于后续命令；下面以 `<task-id>` 表示它。

如果同一需求来源和章节已有未完成任务，AIW 会直接提示已有的 `taskId`，不会重复读取文档或创建第二份任务。请使用该 ID 继续；只有确实需要并行或重新开始时才显式添加 `--force-new`。

创建成功后立即提交共享任务事实：

```bash
git add .aiw
git commit -m "chore(aiw): initialize task"
```

`.aiw/` 是业务仓库的一部分，保存来源快照、任务状态、产物、审批和去敏运行摘要，必须随正常 Git 流程提交。`~/.aiw/` 存放个人配置、完整运行日志和临时上下文，绝不能提交。

## 推进固定七阶段的详细规则

任务固定按以下顺序推进：

```text
intake → clarify → solution → plan → implement → verify → test
```

`intake` 在创建任务时完成，不能手动运行。执行阶段前后使用 `status` 确认状态：

```bash
aiw task status <task-id>
aiw task run <task-id> clarify
git add .aiw && git commit -m "chore(aiw): clarify task"
aiw task review <task-id> --actor <your-name>
git add .aiw && git commit -m "chore(aiw): review clarification"

aiw task run <task-id> solution
git add .aiw && git commit -m "chore(aiw): record solution result"
aiw task run <task-id> plan
git add .aiw && git commit -m "chore(aiw): record plan result"
aiw task approve <task-id> plan --actor <your-name>
git add .aiw && git commit -m "chore(aiw): approve plan"

# 计划可能自动拆出 implement-*；先查看实际可执行节点
aiw task status <task-id>
aiw task run <task-id> <status 输出的节点 ID>
git add .aiw && git commit -m "chore(aiw): record node result"

# 每个实现节点完成后重复 status → run → commit；全部完成后依次执行 verify、test
aiw task status <task-id>
```

`clarify`、`plan` 和 `test` 运行完成后会进入 `awaiting_approval`。`clarify` 一律使用 `task review` 确认；它会以“问题 → 原因 → 影响 → 推荐方案 → 备选方案”的短卡片逐项展示，确认后一次性写入决策和澄清审批记录。选择“等待接口”等外部依赖方案时，命令只额外询问负责团队（可直接回车，后续补充）。`plan` 和 `test` 使用普通 `approve`。所有审批或确认记录都必须再提交一次，下游节点才可运行。

### 提前处理 AI 发现的疑问与阻塞

`clarify` 完成后，AI 会把不能直接确认、且影响范围或验收的事项写入决策登记。日常只需执行 `task review`，按序号逐项选择即可；不要手写决策编号或选项编号：

```bash
aiw task review <task-id>
```

需要在澄清确认后补充外部等待、拆期、风险豁免或解除等待时，再使用高级命令：

```bash

# 采用一个方案
aiw task decision choose <task-id> DEC-API-01 --option mock-only --note "先完成 UI 验证"

# 等待外部接口，但其他不相关工作单元仍可推进
aiw task decision wait <task-id> DEC-API-01 \
  --option wait-api \
  --owner backend \
  --unblock-condition "接口契约与联调样例已确认"

# 明确不在本版本完成
aiw task decision defer <task-id> DEC-API-01 \
  --option defer-scope \
  --note "接口能力拆至下一版本"
git add .aiw && git commit -m "chore(aiw): record decision"
```

AIW 会只阻塞该决策关联的工作单元。外部条件满足后执行 `aiw task decision resolve <task-id> DEC-API-01 --note "接口已就绪"`，提交后继续该单元。

### 测试未全部通过时

普通 `aiw task approve <task-id> test` 只适用于所有验收项满足的结果。若报告明确存在 `failed` 或 `blocked` 项，应先修复并重新测试；只有业务负责人明确接受风险时才可执行：

```bash
aiw task close-with-risk <task-id> \
  --owner product-owner \
  --reason "后端接口尚未交付，先按已知风险发布" \
  --expires-at 2026-09-01T00:00:00.000Z
git add .aiw && git commit -m "chore(aiw): accept test risk"
```

任务会显示“流程已闭环”，但交付状态会明确标为“风险已接受”，不会误报为可发布。

先预览某个阶段而不调用 Codex：

```bash
aiw task run <task-id> plan --dry-run
```

需要将业务仓库内的额外文件加入本次运行上下文时，显式声明：

```bash
aiw task run <task-id> implement --include docs/api-contract.md
```

## 遇到变化、疑问或阻塞时

来源内容更新后，主动创建新的来源快照：

```bash
aiw task source refresh <task-id> requirements
git add .aiw && git commit -m "chore(aiw): refresh requirement source"
```

内容没有变化时不会创建新版本；内容发生变化时，AIW 会保留旧产物、重新排队受影响流程，并从 `clarify` 开始重新形成结论。方案、计划、实现和测试产物均不能人工退回或修改。

如果执行进程异常退出、节点停留在 `running`，先明确记录失败，再直接重试：

```bash
aiw task fail <task-id> clarify --note "Codex CLI 异常退出"
git add .aiw && git commit -m "chore(aiw): record clarify failure"
aiw task run <task-id> clarify
```

仅在团队确认需要替换节点方法时，才使用 `task skill rebind`；该操作会记录原因并使已开始的下游节点失效。

## 高级维护：查看记录与清理本机运行数据

查看某次运行的摘要、状态和本机日志位置：

```bash
aiw run show <task-id> <run-id> --project .
```

清理本机已过期运行目录时先预览，再明确删除：

```bash
aiw run prune --older-than 30d
aiw run prune --older-than 30d --apply
```

该命令只处理 `~/.aiw/runtime/` 下符合规则的运行目录；不会删除业务仓库 `.aiw/`、技能缓存或任意用户路径。

## 常见问题

| 现象 | 处理方式 |
|---|---|
| `aiw: command not found` | 重新执行 `npm install -g @nalanchujian/ai-workflow`；确认 npm 全局 bin 目录已在 `PATH`。 |
| `doctor` 显示 Codex CLI 失败 | 安装并登录 Codex CLI，或设置 `AIW_CODEX_BIN` 后重新检查。 |
| `task init` 提示没有模板 | 先执行 `aiw skills install <team-skill-repository>`，再通过 `aiw skills profiles list` 确认模板名称和版本。 |
| 在线文档来源不可读取 | 先使用 `aiw doctor --project . --source <文档地址>` 验证对应连接器配置和文档权限。当前内置的 Lark 连接器支持 docx 或 Wiki 链接；不要改用浏览器复制内容绕过错误。 |
| 节点不能运行 | 执行 `aiw task status <task-id>`；通常是上游未完成、待审批产物或任务状态未提交，或来源/技能变化导致节点失效。 |
| 节点长期停在 `running` | 使用 `aiw task fail <task-id> <node-id> --note "<原因>"` 记录异常，提交 `.aiw` 后直接重试同一 `task run`。 |
| `approve` 失败 | 确认节点为 `awaiting_approval`，且产物和等待审批状态已经 `git commit`。 |

完整参数与错误行为见 [CLI 命令参考](../03-方案设计/03-接入与接口/CLI命令参考.md)。
