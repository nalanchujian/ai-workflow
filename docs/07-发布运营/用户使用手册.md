# 用户使用手册

## 这套工具做什么

`aiw` 将一次研发需求固化为 Git 中可追溯的任务事实，并把实施计划拆成按业务边界划分的交付单元。每个单元自行完成代码、工程验证、测试和验收，不再在最后汇总执行全局验证或测试。

## 首次使用

准备：Git 业务仓库、Node.js、Codex CLI；在线文档需要在 Codex 中已经配置可读取该文档的 MCP。

```bash
npm install -g @nalanchujian/ai-workflow
cd <业务仓库>
aiw init
aiw doctor --project .
```

`aiw init` 在 `~/.aiw/config.yaml` 写入无凭据的本机默认配置，并安装默认技能包。当前默认配置为：

```text
默认工作流：standard-web-feature@11.0.0
技能包来源：ai-workflow-skills（Git 标签：v11.0.0）
```

用户不需要单独安装或配置 Superpowers；团队技能包已锁定实际使用的方法来源。

## 创建任务

在业务仓库根目录执行：

```bash
aiw task init --project . --source "<需求文档地址或本地文件>"
```

需要只处理文档中的一个章节时：

```bash
aiw task init --project . --source "<需求地址>" --section "<章节标题>"
```

CLI 接收通用来源地址，内部自动路由：识别为飞书/Lark 地址时使用已配置连接器，其他公开地址作为网页来源处理，本地路径作为本地文件处理。创建成功后提交任务事实：

```bash
git add .aiw && git commit -m "chore(aiw): initialize task"
```

## 推进主干

```bash
aiw task run <task-id> clarify
git add .aiw && git commit -m "chore(aiw): record clarify result"
aiw task review <task-id>
git add .aiw && git commit -m "chore(aiw): review clarify"

aiw task run <task-id> solution
git add .aiw && git commit -m "chore(aiw): record solution result"

aiw task run <task-id> plan
git add .aiw && git commit -m "chore(aiw): record plan result"
aiw task approve <task-id> plan --note "计划确认"
git add .aiw && git commit -m "chore(aiw): approve plan"
```

`task review` 是澄清阶段唯一的人工确认入口。它逐项展示待确认的业务结论：先选择“本期继续”或“等待外部条件”；选择继续后再选择 AI 推荐或输入人工结论。不要在后续方案、计划或交付报告中手改需求结论。

## 交付业务单元

计划批准后，运行：

```bash
aiw task status <task-id>
```

输出会列出一个或多个业务单元，例如：

```text
实施单元（2）：
- 主列表导出：可执行（delivery-list-export）
- 详情页趋势：等待决策（delivery-performance）
```

对每个“可执行”单元按以下顺序操作：

```bash
aiw task run <task-id> delivery-list-export
git add .aiw <业务代码路径> && git commit -m "feat: deliver list export"
aiw task approve <task-id> delivery-list-export --note "交付确认"
git add .aiw && git commit -m "chore(aiw): approve delivery-list-export"
```

一个交付单元的运行会同时生成：

- `artifacts/delivery.md`：实际变更、工程验证、测试命令、结果、逐项验收和风险；
- `artifacts/acceptance-results.yaml`：仅当前单元所拥有 AC 的机器可读结论；
- `handoffs/delivery-<unit>/r<n>.yaml`：供依赖单元使用的精简交接。

没有全局 `verify` 或 `test` 命令。需要跨单元验证时，计划会生成一个依赖前置单元的集成交付单元，按同样方式运行和审批。

## 失败、重跑和风险

节点失败后，先按输出提交 `.aiw` 失败证据，再直接重跑同一命令：

```bash
git add .aiw && git commit -m "chore(aiw): record delivery failure"
aiw task run <task-id> <node-id>
```

同一 `run` 命令也可覆盖式重跑已完成节点；系统保留旧 revision，仅将新版本设为当前有效结果，并使下游当前结果失效。

若单元中存在无法通过的 AC，默认应修复并重跑。只有业务明确接受风险时才可关闭该单元：

```bash
aiw task close-with-risk <task-id> <delivery-node-id> \
  --owner "<责任人>" \
  --reason "<风险与接受原因>" \
  --expires-at "2026-12-31T00:00:00.000Z"
git add .aiw && git commit -m "chore(aiw): accept delivery risk"
```

## 需求和外部条件变化

需求正文变化只能刷新来源：

```bash
aiw task source refresh <task-id> requirements
git add .aiw && git commit -m "chore(aiw): refresh requirements"
```

外部等待解除时使用高级命令：

```bash
aiw task decision resolve <task-id> <decision-id> \
  --impact execution-only \
  --note "测试环境恢复，方案和验收不变"
```

如果新接口、规则或字段口径会改变方案、计划或验收，必须使用 `--impact replan --fact ... --evidence ...`。AIW 会要求重新运行 `solution → plan`，不能直接按旧计划执行。

## 升级技能

团队发布新的技能包 tag 后，显式升级：

```bash
aiw skills update --ref v11.0.0
```

升级只影响新任务。进行中的任务仍使用创建时锁定的模板、技能与方法来源版本。当前工作流从早期七阶段升级为交付单元模式时，旧任务应重新创建，避免混用节点模型。
