# AI Workflow 用户使用手册

## 这份手册解决什么问题

本手册面向使用 `aiw` 推进研发任务的开发者，说明如何从安装、环境检查到完成一个可追溯的七阶段任务。

`aiw` 不是替代 Git、Codex 或团队技能包的工具：它将需求快照、任务状态、阶段产物和审批记录保存在业务仓库的 `.aiw/` 中；Codex 与 Lark 仍在使用者本机运行，但标准技能所依赖的方法由团队技能包随版本提供。

## 1. 安装与检查

需要 Node.js 22 LTS 或 24+，不要使用 Node.js 23。

```bash
npm install -g @nalanchujian/ai-workflow
aiw --version
aiw init

# 在业务仓库中执行
cd /path/to/business-repository
aiw doctor --project .
```

`doctor` 会检查 Git、业务仓库是否允许提交 `.aiw/`、Codex CLI、本机配置、已安装的团队方法和 Lark MCP。按输出中的修复建议解决 `failed` 项；未使用 Lark 时，Lark 相关的 `warning` 不阻止本地或公开 URL 来源的任务。

常用的升级和卸载命令：

```bash
npm update -g @nalanchujian/ai-workflow
npm uninstall -g @nalanchujian/ai-workflow
```

## 2. 配置个人环境

个人配置文件位于 `~/.aiw/config.yaml`。它不应提交到业务仓库，也不能包含在团队技能仓库中。

执行 `aiw init` 后，文件会带有中文注释，并自动安装配置中默认的 `standard-web-feature@2.0.0` 工作流。标准团队技能包已随版本提供和锁定所需的 Superpowers 方法，因此不要添加 `methodSources`，也无需单独安装 Superpowers。

如果 Codex 已配置唯一的 Lark MCP Server，`aiw init` 会读取其工具清单并自动写入 Lark 映射；不复制凭据，也无需填写 Server 或工具名称。若出现多个候选，命令会列出名称，使用者只需选择一次：

```bash
aiw init --lark-server <命令输出中的候选名称>
```

未发现候选时，先在 Codex 配置 Lark MCP 后重新运行 `aiw init`。自动发现不会覆盖已有 `connectors.lark` 配置。完成后可验证：

```bash
aiw doctor --project .
```

从旧版本升级时，若配置中存在 `methodSources`，请先删除该字段及其全部内容；当前版本会明确拒绝它，也不会继续读取本机 Superpowers 目录。旧任务需要使用内置方法版技能包重新创建。

如需以 Lark `docx` 或 Wiki 文档为需求来源，先运行上述自动发现流程；只有自动发现不支持团队的 MCP 时，才由维护者在 `~/.aiw/config.yaml` 补充映射。字段和限制见 [Lark 来源连接器规范](../03-方案设计/03-接入与接口/Lark来源连接器规范.md)。不要把 Lark 凭据、token 或 Codex 配置复制到 `.aiw/`。

## 3. 默认工作流与技能更新

首次 `aiw init` 已自动安装官方默认技能包，无需输入技能仓库地址、版本或模板名称。默认配置保存在 `~/.aiw/config.yaml`，而安装后的 revision、哈希与许可证校验结果保存在本机 Registry。

```bash
aiw skills profiles list
```

团队发布新技能 tag 后，使用者需要采用新版时才显式更新：

```bash
aiw skills update --ref v2.1.0
```

更新先完成技能安装和校验，再将本机默认 Git tag 与同名工作流模板的新版本一并切换；例如 `standard-web-feature@2.0.0` 会切换为新包提供的 `standard-web-feature@2.1.0`。新包缺少同名模板时配置保持不变。新建任务默认使用本机配置的模板；需要采用其他已安装模板时，才显式传入 `--skill-profile <name@version>`。模板会一次锁定 `clarify` 至 `test` 的方法和版本；不要在任务进行中以“当前安装的最新技能”替代任务已经锁定的技能。当前本机 Registry 尚不保留同一来源的多个版本：升级不会改写旧任务事实，但会替换旧任务运行所需的本机技能副本，进行中的旧任务可能无法继续运行。请先完成旧任务再升级；如已升级，切回旧 tag 后再继续，或基于新版重新创建任务。

## 4. 创建任务

在业务仓库中准备好可共享的需求来源后创建任务。来源可以是仓库内 Markdown 文件、符合安全规则的公开 HTTP(S) 地址，或已配置 Lark MCP 的 `docx` / Wiki URL。

```bash
aiw task init \
  --project . \
  --source ./requirements.md
```

较大的 Lark 需求文档可只固化一个章节：

```bash
aiw task init \
  --project . \
  --source https://<tenant>.larksuite.com/wiki/<node-token> \
  --source-section "订单退款流程"
```

章节标题必须在文档中唯一；快照包含该标题及其子标题内容。后续 `source refresh` 会继续刷新同一章节，而不是整篇文档。首次使用章节功能前，在 Codex 的 Lark MCP 启动参数中添加 `-t` 与 `preset.default,docx.v1.documentBlock.list`，然后重启 MCP；这是开启文档块读取工具，不需要新增 Lark 权限或填写凭据。

命令会自动返回任务 ID，例如：

```json
{"taskId":"task-20260813-120000-000","status":"active"}
```

无需、也不能手动指定任务 ID。复制该 `taskId` 用于后续命令；下面以 `<task-id>` 表示它。

如果同一需求来源和章节已有未完成任务，AIW 会直接提示已有的 `taskId`，不会重复读取文档或创建第二份任务。请使用该 ID 继续；只有确实需要并行或重新开始时才显式添加 `--force-new`。

创建成功后立即提交共享任务事实：

```bash
git add .aiw
git commit -m "chore(aiw): initialize task"
```

`.aiw/` 是业务仓库的一部分，保存来源快照、任务状态、产物、审批和去敏运行摘要，必须随正常 Git 流程提交。`~/.aiw/` 存放个人配置、完整运行日志和临时上下文，绝不能提交。

## 5. 推进固定七阶段

任务固定按以下顺序推进：

```text
intake → clarify → solution → plan → implement → verify → test
```

`intake` 在创建任务时完成，不能手动运行。执行阶段前后使用 `status` 确认状态：

```bash
aiw task status <task-id>
aiw task run <task-id> clarify
git add .aiw && git commit -m "chore(aiw): clarify task"
aiw task approve <task-id> clarify --actor <your-name>
git add .aiw && git commit -m "chore(aiw): approve clarification"

aiw task run <task-id> solution
aiw task run <task-id> plan
git add .aiw && git commit -m "chore(aiw): plan task"
aiw task approve <task-id> plan --actor <your-name>
git add .aiw && git commit -m "chore(aiw): approve plan"

aiw task run <task-id> implement
aiw task run <task-id> verify
aiw task run <task-id> test
git add .aiw && git commit -m "chore(aiw): test task"
aiw task approve <task-id> test --actor <your-name>
git add .aiw && git commit -m "chore(aiw): approve test"
```

`clarify`、`plan` 和 `test` 运行完成后会进入 `awaiting_approval`，必须先提交当前产物和状态，再执行 `approve`。审批记录与状态变化也必须再提交一次，下游节点才可运行。

先预览某个阶段而不调用 Codex：

```bash
aiw task run <task-id> plan --dry-run
```

需要将业务仓库内的额外文件加入本次运行上下文时，显式声明：

```bash
aiw task run <task-id> implement --include docs/api-contract.md
```

## 6. 需求或方案发生变化时

来源内容更新后，主动创建新的来源快照：

```bash
aiw task source refresh <task-id> requirements
git add .aiw && git commit -m "chore(aiw): refresh requirement source"
```

内容没有变化时不会创建新版本；内容发生变化时，已经开始的下游节点会变为 `invalidated`，需要重新执行。

如果审批人要求修改等待审批的产物，使用：

```bash
aiw task request-changes <task-id> plan \
  --actor <reviewer-name> \
  --note "补充数据迁移回滚方案"
git add .aiw && git commit -m "chore(aiw): request plan changes"
```

如果不是审批场景下的修订，使用：

```bash
aiw task revise <task-id> clarify --note "补充权限和异常场景"
git add .aiw && git commit -m "chore(aiw): revise clarification"
```

如果执行进程异常退出、节点停留在 `running`，先明确记录失败，再修订重试：

```bash
aiw task fail <task-id> clarify --note "Codex CLI 异常退出"
git add .aiw && git commit -m "chore(aiw): record clarify failure"
aiw task revise <task-id> clarify --note "修复执行环境后重试"
git add .aiw && git commit -m "chore(aiw): retry clarification"
```

仅在团队确认需要替换节点方法时，才使用 `task skill rebind`；该操作会记录原因并使已开始的下游节点失效。

## 7. 查看记录与清理本机运行数据

查看某次运行的摘要、状态和本机日志位置：

```bash
aiw run show <task-id> <run-id> --project .
```

清理本机已过期运行目录时先预览，再明确删除：

```bash
aiw run prune --older-than 30d
aiw run prune --older-than 30d --apply
```

该命令只处理 `~/.aiw/runtime/` 下符合规则的运行目录；不会删除业务仓库 `.aiw/`、技能缓存或任意用户路径。

## 8. 常见问题

| 现象 | 处理方式 |
|---|---|
| `aiw: command not found` | 重新执行 `npm install -g @nalanchujian/ai-workflow`；确认 npm 全局 bin 目录已在 `PATH`。 |
| `doctor` 显示 Codex CLI 失败 | 安装并登录 Codex CLI，或设置 `AIW_CODEX_BIN` 后重新检查。 |
| `task init` 提示没有模板 | 先执行 `aiw skills install <team-skill-repository>`，再通过 `aiw skills profiles list` 确认模板名称和版本。 |
| Lark 来源不可读取 | 先使用 `aiw doctor --project . --lark-url <lark-url>` 验证 MCP 配置和文档权限；`lark-url` 可为 docx 或 Wiki 链接。不要改用浏览器复制内容绕过错误。 |
| 节点不能运行 | 执行 `aiw task status <task-id>`；通常是上游未完成、待审批产物或任务状态未提交，或来源/技能变化导致节点失效。 |
| 节点长期停在 `running` | 使用 `aiw task fail <task-id> <node-id> --note "<原因>"` 记录异常，再用 `task revise` 重试。 |
| `approve` 失败 | 确认节点为 `awaiting_approval`，且产物和等待审批状态已经 `git commit`。 |

完整参数与错误行为见 [CLI 命令参考](../03-方案设计/03-接入与接口/CLI命令参考.md)。
