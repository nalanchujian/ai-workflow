# Figma 设计分析第一阶段设计

## 目标

在不改变现有无设计稿任务的前提下，让 AIW 可以把一个 Figma 父节点固化为开发前的设计事实，并将直接设计引用传递到各个开发单元。

## 第一阶段流程

```text
需求来源 + 可选 Figma 父节点
  ↓
intake
  ↓
design-analysis（仅在传入 Figma 时出现）
  ↓
clarify
  ↓
solution
  ↓
plan
  ↓
development-unit-*
```

## 范围

第一阶段包含：

- `task init` 接收一个可选 Figma 节点地址，仅登记地址并决定是否创建 `design-analysis` 节点。
- `design-analysis` 是可见、可单独执行和重试的独立可选节点；不将设计分析隐藏在 `task init` 内部。
- 执行 `design-analysis` 时，AIW 通过已配置的 Figma MCP 读取父节点元数据和概览截图，再识别与当前需求相关的页面、弹窗、状态和共享规则。
- 设计中无法确定的业务问题交给 `clarify`，不在设计节点内自行定案。
- `plan` 为每个开发单元保存直接 Figma 节点引用。
- 开发节点按需读取当前单元的 Figma 上下文，不注入整个大设计稿。

第一阶段不包含：

- 开发完成后的浏览器截图对比。
- Playwright 视觉回归。
- 每个开发单元的 `design-review-*` 节点。
- Chrome 账号、Profile 36 或其他个人浏览器配置。
- 修改 Figma 文件。

## 节点产物

`design-analysis` 产出：

```text
artifacts/design/
├─ design-catalog.yaml
├─ design-rules.yaml
└─ design-context.md
```

- `design-catalog.yaml`：仅列出与当前需求有关的 Figma 子节点，保留直接地址、节点 ID、用途和状态说明。
- `design-rules.yaml`：记录跨页面的布局、组件、交互、内容和状态规则，以及需交给需求澄清的问题。
- `design-context.md`：供人工快速阅读的中文摘要；YAML 仍是程序读取的权威产物。

## 开发单元的设计引用

`aiw.development-plan/v1` 增加可选 `designReferences`：

```yaml
designReferences:
  - figmaUrl: https://www.figma.com/design/file-key/file-name?node-id=9272-292811
    nodeId: "9272:292811"
    purpose: 默认页面和筛选状态
```

引用直接嵌入开发单元，不建立跨节点的 AIW 业务 ID 映射。

## 上下文原则

- `design-analysis`：需求快照 + Figma 父节点元数据 + 概览截图。
- `clarify`：需求快照 + 设计目录 + 设计规则，不重复注入大截图。
- `solution`：仍只读事实登记和已确认决策。
- `plan`：技术方案 + 设计目录，用于绑定各开发单元的设计引用。
- `development-unit-*`：只读当前单元 YAML，再按其 `designReferences` 向 Figma MCP 请求精确节点上下文。

## 成功标准

- 不传 `--design` 时，现有任务流程和产物不变。
- 传入合法 Figma 节点时，任务图自动增加独立的 `design-analysis`，创建任务后由用户通过 `task run` 显式执行。
- 大父节点只作为目录入口，开发单元不会接收整份设计上下文。
- 澄清阶段能看到设计中的待确认问题。
- 每个有 UI 变更的开发单元至少包含一个直接 Figma 节点引用。
- 仓库中不出现 Chrome Profile 或个人登录信息。
