# 交付单元化工作流设计

> **文档状态：历史研发记录。** 本文保留当时的设计语境，不代表当前 CLI、任务模型、路径或版本。现行规则以 `docs/01-立项与规划` 至 `docs/07-发布运营` 为准。

## 目标

将原有“实施 → 工程验证 → 测试验证”的全局串行链路改为按业务单元闭环的交付模型，消除全局 `verify`、`test` 在复杂任务中汇总全部实施产物而导致的上下文膨胀。

## 对外流程

```text
intake → clarify → solution → plan → delivery-<业务单元>
```

- `intake` 仍由 AIW 原生固化需求来源。
- `clarify`、`solution`、`plan` 保持原有职责和审批规则。
- `plan` 获批后不再解锁固定 `implement`、`verify`、`test` 节点，而是始终生成一个或多个 `delivery-<unit-id>`。
- 每个交付单元独立完成代码修改、工程验证、验收测试、验收结果和结构化交接；成功后等待审批。
- 所有交付单元获批后，任务闭环。不存在读取全部单元 Markdown 的全局验证或测试节点。

## 任务图与验收归属

1. `work-breakdown.yaml` 的每个 `unit` 是一个可独立交付的业务单元。
2. 每个本期验收项只能归属一个交付单元；交付单元仅输出其 `acceptanceRefs` 对应的验收结果。
3. 若验收项依赖多个实现单元，计划必须增加一个显式的集成交付单元，并以 `dependsOn` 连接前序单元。该集成单元拥有对应验收项并执行集成测试。
4. 每个交付单元均强制进入待审批，避免“代码已写但测试结论无人确认”。
5. 普通审批只允许该单元所有验收项为 `passed`；失败或阻塞只能先修复重跑，或用 `close-with-risk <task-id> <delivery-node-id>` 记录责任人、原因和到期时间。

## 产物与上下文

每个交付单元输出：

- `delivery.md`：实际变更、工程验证、验收测试、逐项验收结论和风险；
- `acceptance-results.yaml`：仅包含该单元所属验收项；
- `handoffs/<node-id>/r<revision>.yaml`：供后续依赖单元读取的结构化摘要。

计划阶段不再生成全局 `implementation-context.md`。AIW 为每个交付单元生成独立的 `work-units/r<plan-revision>/<delivery-node-id>.md`，只含该单元的目标、验收项、步骤、验证方式、前置单元和风险。运行时默认注入计划 Handoff、直接依赖单元 Handoff、该单元上下文和任务索引；完整计划、其他单元报告和原始需求仅在 Handoff 证据路径明确指向时按需读取。

## 交付状态

- 尚有交付单元未审批：`not_assessed`；
- 全部交付单元获批且所属验收项均通过：`ready`；
- 任一单元以风险接受方式关闭：`risk_accepted`；
- 外部等待、失败或阻塞单元未处理：任务保持未闭环，不产生“可发布”结论。

## 兼容性

这是工作流和技能模板的破坏性变更。旧任务图含有 `verify` 或 `test` 时不继续兼容；升级后应重新创建任务，并使用新的团队技能模板。历史任务事实保留在原业务仓库中供追溯。
