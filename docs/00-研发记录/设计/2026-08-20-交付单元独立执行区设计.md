# 交付单元独立执行区设计

## 目标

为计划生成的 `delivery-*` 交付单元创建独立 Git worktree。Codex、工程验证和验收测试全部在隔离区完成；只有全部校验通过后，AIW 才把业务代码变更一次性发布到用户当前工作区。失败、取消、超时和产物校验失败不得污染用户业务代码。

## 范围

- `clarify`、`solution`、`plan` 继续在当前业务仓库运行，因为它们只允许生成受控的任务事实。
- `generatedFromPlan: true` 的 `implement` 节点必须使用独立执行区。
- 保持现有人工提交模型：AIW 发布成功后，CLI 继续提示用户将业务代码与 `.aiw` 一次提交。
- 不在本次改造中自动创建业务提交、切换用户分支或推送远端。

## 架构

新增 `DeliveryWorkspaceManager` 端口和 Git 实现。Runner 在交付单元开始前，以当前已提交 `HEAD` 在本机运行目录中创建 detached worktree，并获得：

- `projectRoot`：Codex 和测试的隔离工作目录；
- `taskStore`：隔离工作目录内的临时任务事实存储，仅承载 Agent 暂存产物和平台测试结果；
- `publish()`：提取排除 `.aiw/` 的二进制 Git 补丁，校验源工作区仍处于原始 HEAD 且无业务改动，再原子应用补丁；
- `rollback()`：发布后的平台收尾失败时，使用同一补丁反向恢复源业务工作区；
- `dispose()`：移除 worktree 并清理 Git worktree 管理记录。

共享任务状态、运行证据、审批和最终正式产物仍由原 `TaskStore` 管理。隔离区中的 `.aiw` 只作为当前运行暂存区，不会整体合回。

## 执行流程

```text
校验任务事实与源工作区
  → 创建 detached worktree
  → Codex 在隔离区修改业务代码并写暂存产物
  → AIW 在隔离区执行批准的测试与验收
  → 校验隔离区 Git 历史、任务事实写入范围和全部产物
  → 生成排除 .aiw 的业务补丁
  → 再次校验源 HEAD 与业务工作区
  → 应用业务补丁到源工作区
  → 发布正式任务产物、证据和节点成功状态
  → 清理隔离 worktree
```

任何失败发生在“应用业务补丁”之前时，源业务工作区必须保持不变。失败证据使用隔离区 Diff 和文件哈希写入原任务目录，供用户追溯。

## 依赖与工具环境

worktree 位于 `~/.aiw/runtime/<task-id>/<run-id>/workspace`。Node 项目若源工作区存在 `node_modules`，执行区创建一个不进入 Git 的 `node_modules` 符号链接，以复用本机依赖；没有可复用依赖时，测试能力健康检查或正式测试必须明确失败，AIW 不静默安装依赖。

## 发布约束

发布前必须同时满足：

1. 源工作区的 `HEAD` 与创建执行区时一致；
2. 源工作区除 AIW 当前运行产生的 `.aiw/` 文件外没有业务改动；
3. 隔离区没有 Git 提交、分支切换或历史变化；
4. 业务补丁不包含 `.aiw/`、`.git/` 或运行目录；
5. 补丁通过 `git apply --check` 后才能应用。

若源分支在运行期间发生变化，发布失败并保留证据，不自动 rebase 或覆盖他人修改。

## 失败与恢复

- Codex、测试、验收或产物校验失败：不发布业务补丁，记录隔离区证据并清理 worktree。
- 用户取消或进程超时：同上。
- 发布前源仓库发生变化：标记运行失败，提示基线已经变化。
- 进程被强制杀死：worktree 可能残留在运行目录；下一次创建执行区前执行 `git worktree prune`，运行记录清理也必须允许移除对应目录。
- 补丁应用后平台事实写入异常：AIW 立即反向应用同一补丁；若源 HEAD 在这一极短窗口内再次变化而无法安全回滚，节点失败并明确记录回滚失败原因，不静默覆盖并发修改。

## 测试

- 使用真实临时 Git 仓库验证 worktree 创建、隔离、补丁发布和清理。
- 验证失败和取消不会修改源业务文件。
- 验证 `.aiw` 暂存文件不会进入业务补丁。
- 验证源 HEAD 或业务文件变化会阻止发布。
- Runner 测试验证只有交付单元使用隔离目录，非交付节点保持现状。
- 端到端测试验证交付单元成功后业务修改只在验收通过后出现于源工作区。
