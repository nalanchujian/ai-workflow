# MVP 节点重构实施计划

状态：待实施。本文依据本次逐节点确认的目标编写，不表示代码已实现。

## 1. 目标与范围

将现有工作流直接替换为：

```text
requirement-analysis
  → 有待决策问题时通过 CLI 确认或延期
  → CLI 收集是否提供接口文档、是否提供设计图
  → api-analysis（有接口 URL 才创建）
  → design-slicing（有设计图片才创建）
  → solution
  → plan
  → development-unit-*
```

- 需求输入仅一个需求文档地址；接口输入仅多个接口文档 URL；设计输入仅一张本地 PNG/JPEG。
- 不保留旧节点别名、旧参数、旧任务格式兼容层和迁移逻辑；旧任务提示重新创建，不能静默转换或删除。
- 仅需求中的待决策问题需要人工处理。无问题自动完成需求分析；技术方案和开发计划均无需批准。
- 图片只裁切和建索引；开发计划绑定图片；技术方案不读取设计图片或索引。
- CLI 继续逐节点给出精准执行命令，不额外建设全流程自动执行器、并行调度器或通用可配置工作流框架。
- AIW 自身仍做自动化测试；不增加业务代码测试、验收、PR 或发布节点。

## 2. 当前实现与改造点

| 当前实现 | 改造要求 |
| --- | --- |
| 初始化时接入需求，生成独立 intake、clarify 节点 | 合并为 requirement-analysis，读取文档和分析都属于该节点 |
| task init 接受本地需求文件、章节、接口 ID、多张设计图片 | 需求入口仅保留 URL；接口和图片移到需求完成后的 CLI 对话 |
| api-document-recognition 在初始化时生成且直接完成 | 删除，新增真正执行文档读取与分析的 api-analysis |
| clarify 默认注入全部来源，固定待批准 | 只注入需求快照；按 pendingDecisions 是否为空决定状态 |
| plan 批准动作生成开发单元 | 改为计划执行成功、产物校验后生成单元 |
| design-analysis 在计划之后切图、绑定单元 | 改为计划之前 design-slicing，仅切图；绑定移入 plan |
| 设计索引要求 developmentUnits | 删除此字段，增加原图裁切位置；计划持有绑定关系 |
| 开发上下文仅直接加载单元 YAML | 显式解析并装配单元关联的方案、接口资料和图片 |

主要影响范围：两个仓库 ai-workflow、ai-workflow-skills。

## 3. 固定节点契约

| 节点 | 输入 | 输出与完成条件 |
| --- | --- | --- |
| requirement-analysis | 一个需求文档 URL；Agent 只读取该文档快照 | 需求快照、事实登记、决策登记；保存成功且待确认问题为零 |
| api-analysis | CLI 收集的多个接口文档 URL；Agent 只读取相应快照 | 全部接口快照、接口分析结果；所有 URL 均读取成功，产物保存成功 |
| design-slicing | 一张本地 PNG/JPEG | 原图、切割图片、索引；图片可读取，裁切位置有效 |
| solution | 需求事实、本期决策、接口分析结果（如有）、项目代码与约束 | 中文技术方案；覆盖本期需求、保存成功且无未处理的阻塞业务决策 |
| plan | 技术方案、项目代码与结构、相关接口资料、切割图片及索引（如有） | 开发计划 YAML、单元上下文及动态节点；唯一标识、无循环、引用有效、生成成功 |
| development-unit-* | 单元定义、关联技术方案、绑定接口资料和图片、项目代码及依赖改动 | 代码补丁、开发结果；开发完成且补丁应用、结果保存均成功 |

资料分析不读取需求结果；需求分析不注入接口资料、图片或仓库代码。该边界通过上下文装配、运行提示词和测试共同落实，不宣称上下文清单等同于文件系统隔离。

## 4. 实施顺序

### 第一步：重定义任务模型和产物协议

修改 src/domain/task.ts、workflow-profile.ts、design.ts、work-breakdown.ts、fact-register.ts、output-contract.ts，以及 src/services/agent-artifact-protocol.ts。

1. 用新阶段替换 intake、clarify、design 等旧定义；同步技能阶段枚举与模板字段。
2. 更新任务及有破坏性变化的产物版本，只接受新版本；移除旧别名和兼容解析。
3. 保存需求 URL、接口 URL 清单和单张图片信息。资料选择用最小字段区分“尚未回答”“不提供”“已提供”，避免把未回答当作否。
4. 设计索引只包含图片 ID、路径、名称、原图引用及 x/y/width/height；不包含开发单元、交互规则或设计报告。
5. 计划单元增加接口引用和图片引用。以索引中的有效标识解析文件路径，避免任意路径注入。
6. 用同一份 Zod Schema 驱动 Agent 协议、运行结束校验和计划校验命令，技能不复制字段定义。

验证：新增或更新领域测试，覆盖单张图片约束、无效 URL、重复标识、图片裁切边界、接口/图片引用及循环依赖。

### 第二步：合并需求接入与需求澄清

修改 src/cli/task-init-command.ts、src/services/task-initializer.ts、source-intake.ts、task-runner.ts、task-decision-service.ts 和 task-state-machine.ts。

1. 保留 task init 作为创建任务的管理命令，仅登记需求 URL、创建新任务和 requirement-analysis 节点；不再创建独立接入节点。
2. task run <task-id> requirement-analysis 在节点内部读取 URL、固化需求快照，然后调用 Agent 分析。接入失败计为该节点失败，不产生假完成状态。
3. 删除需求本地文件、--section、--api-doc-id 和初始化阶段 --design-image 的入口及仅服务这些旧路径的代码；沿用现有 URL 读取能力，不新增接入框架。
4. 无待决策问题时直接 completed，不生成虚构的人工批准记录，不要求空 review。
5. 有问题时等待 task review；确认写入本期决策，延期写入延期事项。全部处理后完成节点。
6. 保留合法的已确认决策；技术方案后续发现新业务问题时，通过需求决策处理路径追加待确认项，不盲目重跑分析覆盖已有结论，也不把它变成方案批准关卡。

验证：URL 成功/失败、只注入需求快照、零问题直通、有问题确认/延期、待确认时禁止后续执行。

### 第三步：CLI 对话与动态节点创建

修改 src/cli/task-run-command.ts、task-state-commands.ts、review-prompter.ts、create-runtime.ts，新增窄职责的资料收集服务和 CLI 对话入口。

1. 需求分析无疑问完成后，或 task review 处理完全部问题后，使用同一入口询问接口资料，再询问设计图片。
2. 接口选择“有”后逐个输入 URL，空行结束；至少一个有效 URL，规范化后去重。仅收集文档地址，不尝试调用业务 API。
3. 设计选择“有”后输入一个本地 PNG/JPEG 路径，检查格式并保存原件。不接受第二张图和设计平台地址。
4. 回答“无”只保存选择结果，不创建 skipped 占位节点。接口分析与设计图切割各最多创建一个节点。
5. 增加 task inputs <task-id> 作为同一 CLI 对话的恢复入口，不增加另一种资料接入形式。逐项保存已完成回答；中断后继续未完成部分，不重复创建节点。
6. 未完成两个资料选择前不开放 solution。非交互终端明确提示在交互终端执行 task inputs，不将 EOF/缺少终端解释成“不提供”。
7. 使用现有任务锁与 stateVersion 完成选择保存和节点变更，避免重复执行或旧状态覆盖。

MVP 按已确认的展示顺序串行推进：需求分析 → 已选择的接口分析 → 已选择的设计图切割 → 技术方案。只有接口节点时直接接方案；只有图片节点时切图后接方案；均无时直接接方案。顺序依赖不代表允许读取上游全部产物。

验证：四种资料组合、中途退出恢复、重复调用、非法输入、未完成选择时的推进限制。

### 第四步：实现接口分析与纯图片切割

修改 URL 来源读取与现有接口连接器、src/services/task-runner.ts、src/domain/design.ts、Agent 产物协议；在技能仓库新增接口分析技能并改写图片切割技能。

1. api-analysis 读取全部 URL 并保存快照，再分析路径、方法、参数、响应、错误码及明确的调用约束。
2. 接口结果保留稳定引用与来源对应关系，供计划绑定；缺失内容明确记录，不猜测、不访问业务接口。
3. 任一 URL 读取失败不将节点标记成功；重试不得引入重复资料或过期产物引用。
4. design-slicing 不再读取开发计划，仅对原图裁切并生成索引。沿用现有图像传入能力，不增加图像生成或外部设计平台接入。
5. 校验图片实际可解码、文件存在、原图引用与裁切范围合法。不得要求预先存在开发单元。
6. 删除运行完成时 applyDesignBindings 的调用与“至少绑定一个开发单元”的旧切割协议。

验证：多 URL 分析与读取失败、输入隔离、单图切割、缺失/损坏图片、越界裁切、切图不依赖开发计划。

### 第五步：重建上下文、自动完成计划与单元生成

修改 src/services/context-builder.ts、implementation-work-planner.ts、task-runner.ts、src/internal/validate-development-plan.ts 及相关 CLI 输出。

1. 按节点显式装配允许的输入，禁止继续按所有 sources 批量注入。约束 --include，不能绕过已确认的资料节点输入边界，也不能给 solution 注入设计资料。
2. solution 增加接口分析结果，不注入设计原图、切割图片、索引；本期输入排除延期事项。
3. plan 接收方案、接口资料及切割图片和索引；通过实际图片与名称进行开发单元关联，不另写设计分析报告。
4. 将接口与图片绑定直接写入计划。先做完整结构与引用校验，再写入单元上下文并生成节点。
5. 删除 plan 的人工批准要求和 CLI approve 入口；将 materializeDevelopmentWork 从批准动作迁入计划执行成功路径。
6. 在现有锁和持久化机制中保证“计划完成、上下文有效、节点生成”一致；失败不能留下 completed 计划和缺失单元。重试保持幂等。
7. 无单元依赖的开发单元依赖 plan；有依赖的单元等待对应单元完成，不再依赖旧 design-analysis。
8. 开发上下文明确定向加载方案、绑定接口和图片，依赖改动沿用已有 worktree/补丁路径。保留失败、取消、补丁冲突处理。
9. 同步 source refresh、重跑失效逻辑与状态统计，防止旧单元或旧绑定继续执行。全部延期导致本期无开发范围时明确报告，不伪造开发单元。

验证：solution 无设计输入、plan 有图片且绑定正确、计划无人工批准即生成单元、引用错误不开放开发、重跑无重复节点、依赖正确、补丁失败不完成。

## 5. 验证与验收

各行为改动先补失败测试，再实现。每步执行相关测试，最终运行：

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm pack:check
git diff --check
```

更新 tests/e2e/simplified-mvp-workflow.test.ts，使用可重复的来源和 Codex 替身覆盖：

| 场景 | 关键预期 |
| --- | --- |
| 仅需求、无疑问 | 不 review、不创建资料分析节点；方案→计划→单元 |
| 需求有疑问 | 等待确认或延期；处理完才询问补充资料 |
| 仅接口 | 创建一个 api-analysis；支持多 URL；方案收到接口结果 |
| 仅设计 | 创建一个 design-slicing；方案无设计上下文；计划与开发收到相关图片 |
| 接口和设计都有 | 各一个动态节点，顺序正确，输入边界不混合 |
| 对话中断 | 保留有效回答，可继续，不默认为无、不重复建节点 |
| 计划无批准 | 校验成功即生成开发单元，后续提示无 approve |
| 失败与重跑 | 无失效资料引用、重复单元或错误完成状态 |
| 旧任务与旧参数 | 明确拒绝并提示使用新流程，不兼容转换、不删除旧事实 |
| 开发执行 | 依赖生效，输入精确，独立 worktree 与补丁发布路径有效 |

CLI 自身测试通过不等于所生成业务代码已通过测试或验收。若补充真实 Codex 手工烟测，应在隔离的临时业务仓库中执行并单独记录结果。
